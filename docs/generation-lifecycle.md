# Generation lifecycle

Status: writer serialization, conservative recovery scanning and opt-in retention pruning (`keep_generations`, S2-T5) are implemented in `zig/src/core/lifecycle.zig`. Nothing is deleted unless the caller asks, apart from a failed publish removing the section files it had itself just written before its `MANIFEST` rename (`publication.publishWithExtrasRecorded`).

## The files of a generation

A generation `N` is up to six section files, named with `N` in plain decimal, plus the directory's control files (`MANIFEST`, which names the current generation's sections, `WRITER.LOCK` and `INDEX-STATE.json`), which belong to no generation. What a reader does with each file when it opens a generation through `ss_open` (`snapshot_open.openScopedWith`, `abi.zig`; `serve` and `mcp` open the same way, `rpc.zig`):

| File | Written when | Read by a reader opening the generation | Removed by pruning | Counted in `pruned_files` |
| --- | --- | --- | --- | --- |
| `documents-N.hybseg` | always | read whole into memory at open | yes | yes |
| `lexical-N.hyblex` | always | read whole into memory at open | yes | yes |
| `source-N.hybsrc` | when the manifest binds a source section (`has_source`); `import-json` never writes one | opened, not read, at open; its header, file table and line maps are read through that descriptor at the first source use, and its text per call | yes | no |
| `filenames-N.hybseg` | with the opt-in file-name channel (manifest v2.2 bit 3) | opened, not read, at open; read through that descriptor by the first file-name or `both` query | yes | no |
| `filename-lexical-N.hyblex` | with the file-name channel, beside `filenames-N.hybseg` | as `filenames-N.hybseg` | yes | no |
| `state-N.hybstate` | by every folder writer since manifest v2.2 (bit 4); `import-json` never writes one | never; only the next writer reads it, with the previous generation | yes | no |

References: the open reads the documents and lexical sections in `snapshot_open.zig` (`loadEngine`) and opens the source and file-name files in `openScopedFrom`; the deferred reads are `scope.Loads` (`zig/src/core/scope.zig`). "The reader never reads the section" for the state section is pinned by `zig/src/tests/apply_test.zig` (a damaged state section, after which the generation still opens and answers). Since manifest v2.4 a `HYBSRC02` source section is read together with the documents section, which the open already holds in memory (`snapshot_open.Loaded.documents_encoded`). The eager one-shot open, `snapshot_open.open` (which `searchd query` and `searchd evidence` use for a content-field query, `cli.zig`), reads the documents, lexical and file-name sections at open and does not touch the source section.

Retention and the scan go by file name and never read a superseded section, so they treat every format alike: manifest v1 (`import-json`) and v2.0 to v2.5, documents records v1 to v5, lexical `HYBLEX01` to `HYBLEX04`, source `HYBSRC01` and `HYBSRC02` ([`manifest-format-v2.md`](manifest-format-v2.md)).

## Single-writer rule

Publishers acquire an advisory exclusive lock on the persistent `WRITER.LOCK` file (`lifecycle.tryAcquireWriter`). Every folder writer (`searchd index`, `ss_index_folder`, `searchd apply`, `ss_apply_changes`, and `apply_changes` through `serve --allow-write` or `mcp --allow-write`) publishes through `apply.zig`, which takes the lease before it reads the current generation and holds it through the choice of the generation number (since [S6-T20](tasks/S6-T20.md) for a full rebuild too), the publication and any pruning; it fails with `WriterBusy` when another writer holds it. Only the folder walk that lists a full rebuild's or an `--update`'s candidate files runs before the lease; it reads the folder, not the index directory. Readers never take the lease (no open calls `tryAcquireWriter`), so holding it through a build blocks no reader. `import-json` and `init-demo` take it through `publishSerialized` and its `…Keeping` variants, which fail with `WriterBusy` the same way, then check the caller's number (S6-T21, below), and then delegate to the validated immutable-section/manifest publication path.

The lock file itself persists; the operating system releases the lock if the process exits. The test suite (`lifecycle.zig`, "writer lease serializes publication attempts") opens a second handle in the same process while the first lease is held, verifies acquisition fails, releases the first lease, and verifies acquisition succeeds again.

Advisory locking protects cooperating writers. A process that ignores the protocol can still mutate the directory, so section/manifest checksums and immutable filenames remain necessary defenses.

## Recovery scan

`lifecycle.scan` is a library function: no `searchd` command or `ss_*` function calls it today; its callers are tests. The directory must be opened with iteration capability. Only regular files are counted. The scanner:

1. attempts to load `MANIFEST` and the documents and lexical sections it names, and validates those two against it (the reads and checks of `publication.loadCurrent`); the source, file-name and state sections are matched by name only, never read;
2. records the selected generation; `current_files` counts its documents and lexical files, and `current_source_files`, `current_filename_files` and `current_state_files` count its other files apart;
3. counts other `*.hybseg` files as unreferenced document generations (canonical `filenames-N.hybseg` names are counted with the file-name kind, in 6);
4. counts other `*.hyblex` files as unreferenced lexical generations (canonical `filename-lexical-N.hyblex` names likewise);
5. reports unrelated files separately;
6. (S2-T5) splits 3 and 4: a canonical `documents-N.hybseg` / `lexical-N.hyblex` whose `N` is **below** the current generation is retained history and is reported as `superseded_document_files` / `superseded_lexical_files`; only the rest (at or past the current generation, oddly named, or every section file when there is no valid `MANIFEST`) stays in `orphan_document_files` / `orphan_lexical_files`. A crash leftover older than the current generation therefore also shows as superseded, and `keep_generations` removes it with the rest. The total of unreferenced files is unchanged. The other kinds are split the same way and counted apart: `superseded_source_files` / `orphan_source_files` (any `*.hybsrc`; an oddly named one is an orphan), `superseded_filename_files` / `orphan_filename_files` and `superseded_state_files` / `orphan_state_files` (canonical names only: an oddly named `filenames-…` or `filename-lexical-…` file is counted by its suffix as a document or lexical orphan, an oddly named `state-…` file as unrelated);
7. ignores the control files `MANIFEST`, `WRITER.LOCK`, and `INDEX-STATE.json`
   (S1-T4, `docs/tasks/S1-T4.md` criterion 3: the incremental indexer's own
   bookkeeping file is not an operator-facing anomaly, so it no longer counts
   toward "unrelated files").

If no manifest exists, every recognized generation file is classified as unreferenced. If a manifest exists but is invalid, scanning returns the validation error rather than guessing at recovery. A `MANIFEST` whose documents or lexical file is missing is such a manifest: `scan` returns `FileNotFound` ([S6-T13](tasks/S6-T13.md)). Only a missing `MANIFEST` itself means no manifest. Before S6-T13, `scan` took every `FileNotFound` for a missing `MANIFEST` and classified every recognized file, the current generation's included, as unreferenced. Tested by `zig/src/core/manifest_read_test.zig` (a missing documents file, a missing lexical file, then no `MANIFEST`).

## Generation numbering (S2-T14)

A publish that picks its own number (`ss_index_folder`, `searchd index` without `--generation`) uses one rule, in `generation_alloc.zig`: **the highest generation the directory has any trace of, plus one.** The traces are the `MANIFEST`'s generation, every canonical regular file `documents-N.hybseg` / `lexical-N.hyblex` / `filenames-N.hybseg` / `filename-lexical-N.hyblex` / `state-N.hybstate` present (complete or not), and the generation `INDEX-STATE.json` names; the first number above that whose six section names (those five and `source-N.hybsrc`) are all free is used, and a fresh directory starts at 1. (`source-N.hybsrc` is probed but is not a trace: a publish links it after `documents-N` and `lexical-N`, which are.) A lost `MANIFEST` therefore never makes the counter start over: with only generation 2 on disk the recovery publishes generation 3, generation 2 shows as superseded (not orphaned) and `keep_generations` can prune it. At `u64` max there is no next number and the publish fails with `NoFreeGeneration` instead of overflowing; it fails the same way after 1,000,000 occupied candidates in a row (`nextFreeGeneration`; not tested). `ss_import_json`, `searchd import-json`, `init-demo` (always 1) and `--generation` are numbered by the caller (`--generation` is ignored with `--update`, which always uses the rule). **Since [S6-T21](tasks/S6-T21.md) a caller's number must be above the same floor** ([decision 0004](decisions/0004-callers-generation-number.md)): the highest generation the directory has any trace of, as above, except that a `MANIFEST` that cannot be decoded counts as absent there (its section files still count). The check runs under `WRITER.LOCK` (`generation_alloc.requireAboveFloor`: called by `apply.zig`'s `applyParsed` before any file is read, and by `lifecycle`'s serialized publishes before any link). At or below the floor the call fails with `StaleGeneration` (`SS_ERR_INVALID_ARGUMENT` through `ss_import_json`; one stderr line and exit 1 from `searchd`, no error trace), the line names the floor and its traces in the order `NoFreeGeneration` uses (below), and nothing on disk changes. Above the floor, a name taken by something that is not a trace (a `source-N.hybsrc` leftover, a link or a directory) still fails with `PathAlreadyExists` and publishes nothing. Before S6-T21 any free number was published as given, even below the current `MANIFEST`'s, so through these paths the generation could go backwards: an import numbered 10 from an open at 9, held before its lock while two rebuilds with `keep_generations = 1` published 10 and 11, published 10 again and `MANIFEST` went 11 to 10 (S6-T20's Verdict). Tested by `zig/src/tests/cli_test.zig` (the four "S6-T21: ..." tests: 5 and 9 over 9 through `--generation` and an import, the race above through both, a damaged and a missing `MANIFEST`, a lone leftover at 10), `zig/src/tests/abi_index_folder_test.zig` ("S6-T21: ss_import_json refuses ...") and `tests/test_cli_process.py` (`test_caller_number_at_or_below_the_floor_is_one_line_and_changes_nothing`). Over a damaged `MANIFEST`, `--generation` still fails as every folder writer does there (`apply.zig` reads `MANIFEST` before the check); an import above the floor replaces it, as before. A publish that picks its own number chooses it under `WRITER.LOCK` and publishes under the same lease ([S6-T20](tasks/S6-T20.md); `apply.zig`'s `applyParsed`, which takes the lease before it reads the current generation): a full rebuild (`ss_index_folder` without `update`, `searchd index` without `--update` or `--generation`) as well as `--update` and `apply_changes`. Before S6-T20 a full rebuild chose its number before it took the lock (`nextFreeGeneration` in `cli.zig` and `abi.zig`), and a writer that published in between made it fail with `PathAlreadyExists`, or, when that writer also pruned the chosen number's sections with `keep_generations = 1`, publish the used number again with `MANIFEST` going back (11 to 10; S6-T17's verifier, [probes](evidence/s6-t17/verifier/probes.txt)). Now another writer that tries to publish after the rebuild has chosen its number gets `WriterBusy`, and one that published before (while the rebuild was still walking the folder, which happens outside the lease) is seen, so the rebuild takes a number above it. Tested by `zig/src/tests/cli_test.zig` ("S6-T20: another writer racing a full rebuild ..."): `--update` once, `--update` twice with `keep_generations = 1`, another full rebuild and `import-json`, each run inside `searchd index` after its choice and during its walk; in every case the rebuild publishes, no number is published twice and `MANIFEST` never goes back. So, argued from the code (each such publish chooses above `MANIFEST`'s generation while no other cooperating writer can move it), for writers that all number themselves and all honour the lock, `MANIFEST` only goes up and no number is published twice; a writer that ignores the lock is outside that ([decision 0003](decisions/0003-full-rebuild-numbers-under-writer-lock.md), section 6). Since S6-T21 the same holds with callers' own numbers among them, argued from the code: such a number is published only above every trace, and with `MANIFEST` intact every number published before is at or below `MANIFEST`'s ([decision 0004](decisions/0004-callers-generation-number.md)). One consequence for callers: when the lock is held and the directory has no number left, a full rebuild answers `WriterBusy` rather than `NoFreeGeneration` (`zig/src/tests/abi_index_folder_test.zig`). A caller that numbers its own publishes must stay above every section file present; after a lost `MANIFEST`, `ss_open` cannot tell it that number, so the `StaleGeneration` line names it.

Candidate checks inspect the directory entry without following symlinks ([S1-T23](tasks/S1-T23.md), from pull request #11). A dangling link, or a link to itself, under any of the six names reserves that name just as any other entry does, and the allocator tries the next number. Links are not traces: the highest-generation scan counts regular files only, so a link at a distant number does not by itself raise the counter. Neither the link nor its target is read, repaired, deleted or overwritten. If a link occupies the final `u64` candidate, allocation fails through the existing `NoFreeGeneration` channel, whose line names the entry under any of the six names (a `source-N.hybsrc` entry there is named since [S5-T5](tasks/S5-T5.md); S1-T23 recorded it missing).

`NoFreeGeneration` reports the exhausted generation and every matching canonical trace, in the fixed order `MANIFEST`, `INDEX-STATE.json`, `documents-N.hybseg`, `lexical-N.hyblex`, `source-N.hybsrc`, `filenames-N.hybseg`, `filename-lexical-N.hyblex`, `state-N.hybstate`. `source-N.hybsrc` is named only at the exhausted candidate, where it blocks the number; it is never a trace of the highest generation. The CLI and C ABI use the same single-line diagnostic, with file names rather than the caller's directory. Lower generations and malformed aliases are excluded. The failed publish leaves the existing snapshot unchanged.

A fresh output directory permits a new index starting at generation 1 while preserving the old directory. Inspect all listed traces before attempting a repair of the old directory; removing one listed file does not necessarily clear the others, and removing an active manifest or section can damage a readable snapshot. Diagnostics perform no deletion or renumbering. See [S1-T20](tasks/S1-T20.md) for the complete regression and verification record.

## Retention pruning: `keep_generations` (S2-T5)

Opt-in. `"keep_generations": N` (N >= 1) in the options of `ss_index_folder` and `ss_apply_changes`, as an optional top-level field of the `ss_import_json` payload (that function has no options argument), and `--keep-generations N` on `searchd index` and `searchd import-json`; the Dart binding passes it as `IndexFolderOptions.keepGenerations`, `ApplyChangesOptions.keepGenerations` and `SnapshotInterchangeV1.keepGenerations`. `0` is an error: `InvalidKeepGenerations` / `SS_ERR_INVALID_ARGUMENT` for `ss_index_folder` and `ss_import_json`, "keep_generations must be at least 1" for `ss_apply_changes` (`ops.zig`), a usage error on the command line. `searchd apply` and the `apply_changes` of `serve` and `mcp` take no such option and never prune. Absent: nothing is deleted, as before.

After a **successful** publish, still holding `WRITER.LOCK`, every publish path that takes the option ends in `lifecycle.publishLeasedKeepingWithExtras`, which calls `lifecycle.pruneSupersededWithSource` to delete the files of generations older than the newest N:

- all six kinds of section file are removed with their generation: `documents-N.hybseg`, `lexical-N.hyblex`, `source-N.hybsrc`, `filenames-N.hybseg`, `filename-lexical-N.hyblex` and `state-N.hybstate`;
- the kept set is the current generation plus the N-1 newest older **complete** generations (both `documents-N.hybseg` and `lexical-N.hyblex` present); a kept generation keeps all of its files. The other four kinds never make a generation complete. An incomplete older leftover (a lone section file from a crash between the links) is never counted toward N and is always deleted, so `keep_generations: 2` after a crash leaves the current generation plus the newest complete older one;
- only regular files directly in the index directory with one of the six canonical names (plain decimal, no leading zeros) and `N` strictly below the current generation are ever candidates. `MANIFEST`, `WRITER.LOCK`, `INDEX-STATE.json`, temp files, oddly named files, links, directories and any section file at or past the current generation (a crash leftover) are never touched;
- the current generation's files are never touched: they are not below its number, and its documents, lexical and source files are also excluded by the names in its manifest;
- a failed unlink does not fail the publish: it is counted in `prune_failures`, the file stays, and the next pruned publish retries it. A failed directory listing counts one failure and deletes nothing;
- the directory is fsynced once more after the unlinks (best effort; a failure there is also counted in `prune_failures`).

What a report says. `pruned_files` and `prune_failures` appear only when the option is set, and only in the `ss_index_folder` report and the `searchd index` output (summary line, and the `--update` JSON; `abi.zig`, `cli.zig`). `ss_import_json` returns only the generation number, `searchd import-json` prints a line without them (`main.zig`), and the `ss_apply_changes` result follows the closed `apply_changes` schema, which has no such field. **Known limit:** `pruned_files` counts only the documents and lexical files deleted (`PruneReport.deleted`, copied in `apply.zig` and `importer.zig`); the source, file-name and state deletions are counted in `PruneReport.deleted_source`, `deleted_filename` and `deleted_state`, which no report prints. `prune_failures` counts the failures of every kind. For example, in the 20-publish test (`zig/src/core/incremental_indexing_test.zig`, "keep_generations=2 leaves exactly two generations over 20 publishes; absent keeps all") the last publish reports `pruned_files` 2, and the directory ends with two source and two state files, so that publish also removed one source and one state file it does not count. [CAP-23](requirements/cap-23-cli-generation-retention.md) (Proposed) asks the maintainer how a run should report this.

`keep_generations: 1` keeps only the current generation. `2` keeps one previous generation as a fallback for a reader that is mid-open.

Tests that pin the deletions: documents and lexical files, `zig/src/core/incremental_indexing_test.zig` ("pruning touches only superseded canonical section files", and the complete-generation and lost-`MANIFEST` cases there); source files, `lifecycle.zig` ("pruning removes superseded source sections and scan counts them apart (S3-T1)"); source and state files over 20 publishes, the test named above; a state file through `apply_changes`, `zig/src/tests/apply_test.zig`. Removing the file-name sections is shown by the code only (`lifecycle.filenameGeneration` in `pruneSupersededWithSource`): no test checks it. Neither does any test plant a link or a directory under a section name.

### A reader holding an older generation

- **Already open, same process:** a handle opened before a publish that prunes its generation keeps answering that generation. Tested by `zig/tests/abi_test.c` (S4-T6): a handle opened cold, then `ss_apply_changes` with `keep_generations: 1`, which removes `source-1.hybsrc`; the old handle answers `ss_status`, `read_span`, `find`, `outline`, `query` and `list_files` from generation 1, and a fresh `ss_open` answers generation 2. The documents and lexical sections are in memory from the open; the source section is read through the descriptor the open holds. That directory has no file-name channel, so a file-name query on a pruned generation is not tested. CI runs this test on Linux only (`.github/workflows/checks.yml`); macOS, Android and iOS are not tested.
- **Already open, another process:** on macOS, Linux and Android, unlinking a file that is open removes the name only; the reader's descriptor, and any memory it already read, stay valid until it closes. Since a handle reads the source and file-name sections through descriptors it opened at `ss_open` (table above), it should keep answering as in the same-process case. Not tested across processes ([CAP-23](requirements/cap-23-cli-generation-retention.md) acceptance test A6 proposes one).
- **Mid-open, another process:** the open reads `MANIFEST` through the handle whose `stat` sized its buffer (`snapshot_open.readManifest`, [S6-T13](tasks/S6-T13.md)), so a publish that replaces `MANIFEST` while the open reads it leaves the open on the `MANIFEST` it opened, read whole. Before S6-T13 the open read the file again by name, and a new `MANIFEST` longer than the old came back cut to the old size: the open failed with `Truncated` where opening again succeeded (never with a cut manifest accepted: its length and checksum refuse it). Tested by `zig/src/core/manifest_read_test.zig`, which runs a publish between the open's `stat` and its read (new `MANIFEST` one byte shorter, as long, one byte longer and 2,048 bytes longer, and a folder publish from generation 9 to 10), for `open`, `openScoped` and `openSource`. A reader that read an old `MANIFEST` and has not yet read the documents and lexical sections can find them gone and fail with `FileNotFound` (`snapshot_open.loadEngine`); retry reads the new `MANIFEST`. If only the source or file-name files are gone when the open reaches them, the open succeeds and records the error: `read_span` and `outline` then answer `CAPACITY`, and every file-name or `both` query fails with it, while content queries are unaffected (`snapshot_open.openScopedFrom`, `scope.Loads.source_error` and `filename_error`). Neither of these two races (sections removed while the open reaches them) is tested. `keep_generations >= 2` keeps the newest complete older generation, so only a reader that is a whole publish behind can lose them.
- **Windows:** not tested; no CI job builds or runs on Windows. Whether deleting a section file that a reader holds open fails there is not shown by any test. What the code does with any failed unlink is the rule above: it is counted in `prune_failures`, the file stays, and the publish succeeds.
- **In-process (the phone app):** the app knows when no `ss_handle` uses an old generation. A handle holds its documents and lexical sections in memory and its source and file-name section files open, so pruning in the same process removes only their names; the same-process case above is the tested one, on Linux. The app passes `keepGenerations = 2` on every change ([`index-size.md`](index-size.md) § E) and reopens on the new generation afterwards.

The 20-generation, `keep_generations: 2` result is in the `S2-T5` Report, and the test named above pins it.

## Why scanning does not delete

“Not referenced by the current manifest” does not mean “safe to remove.” A reader may have loaded generation `G` immediately before generation `G+1` replaced `MANIFEST` and may still be reading `G`’s immutable files.

Production cleanup needs one of:

- reader leases with expiration and renewal;
- process-local reference counts plus a single service owner;
- epoch-based reclamation;
- conservative time/generation retention large enough for the maximum query lifetime;
- object-store lifecycle rules combined with snapshot retention guarantees.

The scanner itself still performs no destructive action. The one deletion policy that exists is the explicit, opt-in retention above, which is generation-number based and never deletes by "unreferenced".

## Remaining recovery decisions

- whether an invalid current manifest causes fail-closed startup or rollback to the newest retained valid manifest;
- how generation numbers are allocated under writer failover;
- how long orphaned and superseded generations are retained;
- whether a manifest history or append-only commit log is maintained;
- Windows directory durability (POSIX directory fsync is done, see `docs/publication-recovery.md`).
