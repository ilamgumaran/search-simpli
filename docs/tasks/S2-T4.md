# S2-T4 · Warnings, opt-in profile, and the effective request in the query report

**State:** verified (second round; see the second Verdict) · **Series:** S2 (research doc, learnings 6 and 13) · **Depends on:** S2-T3 · **Size:** S · **Builder:** Sonnet 5 · **Tester:** Opus

`ss_query` cannot say why a list is empty or poor: a query word that matches
nothing is dropped silently (`zig/src/lexical_build.zig:139`), a query that is
only punctuation, a `candidate_k` that cut ranks, a vector ignored in lexical
mode (`zig/src/abi.zig:287-293`). The app wants to tell a child "I couldn't
find *dinosaurus*"; a tester wants per-phase timings without a profiler.

## Acceptance criteria
1. The report gains `warnings`: an array of `{code, message, term?}` with
   codes `query_term_unmatched`, `query_empty_after_analysis`,
   `vector_ignored`, `candidate_depth_cut`; and, when `"profile": true` is in
   `options_json`, `profile{tokenize_us, score_us, rank_us, serialize_us,
   matched_chunks}`; and `request{analyzer_id, retrieval_mode, top_k,
   candidate_k, path_prefix}` echoing what was actually used. All additive
   JSON: `contracts/search-tool.schema.json` and `CONTRACTS_VERSION` minor
   bump; Dart types mirrored; header documented.
2. **Bar (a):** with `warnings`, `profile` and `request` stripped, the output
   is byte-identical to the previous library on every golden.
3. **Bar (b):** every query word that matches no chunk appears in `warnings`
   (checked over the 200 random queries of S2-T3 plus 50 with planted unknown
   words).
4. **Bar (c):** with profile off, p50 changes by ≤ 2 %; with it on, by ≤ 10 %
   (same harness as S2-T3).
5. **Plants:** each code has a test that fails when its emission is removed.
6. All five suites green after the Report; libraries rebuilt last.

### Deviations and judgement calls to check
1. **Scope.** A word that is in the dictionary but occurs only in chunks outside `path_prefix` or needing labels the caller lacks is also `query_term_unmatched` (ruling 2 wording: "the term was not found in the files this query may search"; a dictionary miss says "the term was not found in the searched files"), because it matches no chunk the request may see. The check reads at most the postings up to the first in-scope chunk. In `check_unmatched_warnings.py` the vector snapshot's labelled chunks (every 11th file) are therefore excluded from "the corpus has this word"; without that, 6 of 1,750 runs disagreed with a naive corpus-words oracle, all of them words found only in labelled chunks.
2. **`candidate_depth_cut`** (narrowed per ruling 1): hybrid mode warns for each channel that offered more than `min(candidate_k, chunks)`; lexical or vector mode only when `candidate_k < top_k` as well. `ss_query` rejects `candidate_k < top_k` (`InvalidCandidateDepth`), so single-channel `ss_query` calls never warn; the single-channel positive case is tested on `report.write` directly (`depthCutCount`). Negative case on the real library: 10k corpus, `the and of to in`, lexical, defaults, 9,875 matched chunks: `warnings: []`. The test-abi tail did **not** change: the demo query is hybrid with `candidate_k` 2 over 3 vector candidates, so its `candidate_depth_cut` warning is still emitted (same text in `abi_test.c` and Dart `conformance_test.dart`).
3. `serialize_us` covers writing the report up to the `profile` field (it cannot time its own text). `tokenize_us` includes dictionary lookup and the scope check. The four phases do not sum to the call (open arena, result arrays, final copy are outside).
4. `request.top_k` and `candidate_k` are the validated values with defaults filled (100); `candidate_k` is not clamped to the chunk count. `path_prefix` is `null` when absent. The term in a warning is the analysed term (lowercased; NFC and simple-case-folded under `analyzer-v2`).
5. `warnings` and `request` are always present in `ss_query` output (`warnings` may be `[]`). The JSON-RPC result has neither, by choice, to keep `serve` byte-identical (checked: `serve` and `searchd query --json` md5 equal between the `c055c80` and new binaries on one request).
6. The request and the empty-warnings case are written with one `print` call each instead of field-by-field `Stringify` calls (measured: the field-by-field version cost about +2 % on the one-word query).

## Rulings on the Report (orchestrator, 2026-10-08)

Written before verification so the tester judges against them.

1. **`candidate_depth_cut` is too literal in single-channel modes: narrow it
   before the merge.** In lexical or vector mode the cut can change the
   returned list only when `candidate_k < top_k`; a default-depth query on a
   common word must not warn ("kept 100 of 9,875 candidates" tells the app
   nothing it can act on). Rule: in a single-channel mode emit it only when
   `candidate_k < top_k` and the channel offered more than `candidate_k`; in
   hybrid mode emit it for each channel that offered more than `candidate_k`
   (there the cut changes the fusion). The builder makes this change on the
   branch (one more commit, plant kept, libraries rebuilt last) and the tester
   verifies the narrowed rule; bar (a) is unaffected because the warning is
   stripped. If the builder has gone, the tester may make the change and say so.
2. **A dictionary term filtered out by `path_prefix` or the caller's labels
   is `query_term_unmatched`: accepted.** From the caller's side the word was
   not found in the files this query was allowed to see, which is what the
   app will say to a child. The message wording must not claim the word is
   absent from the corpus; "not found in the searched files" or similar.
3. **Only `ss_query` carries the new keys; `serve` and the CLI do not:
   accepted for this task.** They are developer tools and their goldens are
   untouched. Record it as a finding; a later task may add `--json` parity.

   than the run-to-run noise the builder measured (±4 %) on the one-word
   query. Ruling: the tester measures old, new and new-with-profile
   interleaved in ≥ 5 independent runs on a quiet machine (load average

   judged on the median across runs; a difference inside the old-vs-old
   band passes. Anything above 2 % outside that band on the three longer

## Verdict (tester fills in)

**Rejected** (Opus 5.5 tester, 2026-10-08). Most of the task holds in my own runs. Bar (a) is byte-identical over 73,703 calls. Bar (c) is inside 2 % on every query, and every plant is caught. Two defects in the new `query_term_unmatched` path block the merge, and both are small.

**R1. The `term` of a filtered-out word is the dictionary's spelling, not the query word.** `Engine.noteOutOfScopeTerms` (`zig/src/engine.zig`) appends `entry.term`. An `ascii-alnum-v1` import stores the first spelling the corpus used ("Belela"), and `findTerm` matches it case-insensitively. So the query `belela` with `path_prefix` `"zzz/"` on my 1k import gets `{"term":"Belela"}`. The dictionary-miss path lowercases (`postings.resolveQueryTraced`). The header says the term is "lowercased/NFC-folded as the index stores terms", and Report deviation 4 says "the analysed term (lowercased …)". Neither holds here. My scope-aware oracle (below) finds **48 of 7,500** runs where the warned term is not the query word; compared case-insensitively, it finds 0. That fails bar (b) as written ("every query word … appears in `warnings`") and criterion 1's "header documented". No test catches it: the scope test's corpus words are all lowercase.

**R2. The two messages tell a caller which hidden files hold a word.** A word that is only in chunks the caller's labels exclude gets "the term was not found in the files this query may search". A word in no chunk at all gets "the term was not found in the searched files". Probe on a 3-chunk import: `secretword` exists only in a `tenant:acme` chunk; `zzmiss` exists nowhere. Without labels, both return 0 results, but the messages differ. That is a per-word existence test across the label wall. The repository's own rules say the opposite: `docs/authorization.md` says "denied and unknown chunk ids return the same not-found result", and `docs/zig-rpc-service.md` says "out-of-scope ids are indistinguishable from unknown ids". Ruling 2 frames the warning "from the caller's side": the word was not found in the files this query was allowed to see. That is one fact, so it needs one message. (R1 also leaks: the echoed casing comes from the hidden chunk.)

### Rework (exact)
1. In `noteOutOfScopeTerms`, record the analysed query term: the lowercased token for `ascii-alnum-v1`/`analyzer-v1`, the folded token for `analyzer-v2`. Do not record the dictionary entry's bytes. Add a test with a capitalised first occurrence in the corpus (e.g. `"Belela"` in a chunk outside the prefix, query `belela`), and plant it.
2. Use one message for both kinds of unmatched word (e.g. "the term was not found in the searched files"). Drop `Unmatched.in_dictionary` or keep it internal. Test that a label-hidden word and an absent word produce byte-identical warnings, and plant it.
3. `profile.matched_chunks` counts chunks before the path and label scope. On the same probe it is 1 for `secretword` and 0 for `zzmiss`, so it is the same oracle, though only on request. Either count in-scope chunks, or document the leak in the header and in `docs/authorization.md` "Known limits". The orchestrator may choose; I lean to counting in scope.

Each run is one process with four variants interleaved and rotated each round: old (the `aba0303` dylib), a **second copy** of old (a distinct image), new, and new + profile. Each run is 400 calls × 15 rounds and takes the median of the per-round p50s. I made 6 independent runs per corpus, and each started only when the 1-minute load average was < 2 (1.58 to 1.98 at start; the bench's own process keeps it near 2). The results are medians across runs. This is the first timing of the rework, which moved the scope check into the resolver.

### Timing side channel (R2, finding)
This is not blocking, but the orchestrator should see it. I measured on the 6,007-chunk v1 probe snapshot, lexical, `path_prefix` `pub/`, no labels: 5 interleaved blocks of 200 calls per word, medians.

| word | new: wall µs | new + profile: `tokenize_us` / `score_us` | old (`aba0303`): wall µs |
|---|---|---|---|
| `hiddencommon` (3,000 label-hidden chunks) | 109.7 | 39 / 67 | 69.9 |
| `zorblax` (1 label-hidden chunk) | 3.0 | 0 / 0 | 2.5 |
| `belela` (2 prefix-hidden chunks) | 3.0 | 0 / 0 | 2.5 |
| `zzmissing`, `qqwwzz` (absent) | 3.0 | 0 / 0 | 2.5 |

A word hidden in a few chunks cannot be told from an absent word, by the fields or by the clock. A word hidden in **many** chunks can. Wall time is 110 µs against 3 µs, and with `"profile": true` the report itself carries the difference: `tokenize_us` 39 against 0, and `score_us` 67 against 0. This channel is older than the task. The old library already takes 70 µs against 2.5 µs, because the scorer walks every posting of the word before the scope filter. The rework widens it by about 40 µs (`hasInScopePosting` walks every posting of a word that has none in scope) and makes it readable from the report when profile is on. It needs a word in thousands of hidden chunks, and a caller who can repeat the query. It reveals roughly how common the word is in hidden files, not which files hold it. Options for a later task: document it in `docs/authorization.md` "Known limits" next to `index_status`'s corpus-size leak; make `profile` coarser or drop it for callers with a label scope; or keep per-label posting bounds so that neither the scorer nor the resolver walks hidden postings.

### Findings (non-blocking)
- **T1 (timing side channel).** Described above. The fields and the messages are clean; the cost of a word hidden in thousands of chunks is visible in wall time (older than this task) and in the opt-in `profile` µs.
- **T2 (older than this task, `analyzer-v2`).** U+1E9E `ẞ` is not simple-folded to `ß` (CaseFolding.txt `1E9E; S; 00DF`). So `STRAẞE` does not find `straße`, in old and new alike. The new warning faithfully echoes the analysed term `straẞe`. Separately, Tamil vowel signs split tokens (`மழை` → `மழ`), as `analyzer_v2.zig` documents. The warning echoes `மழ`, which is the analysed term but not what a child typed. Worth knowing for the app's "I couldn't find …" message on Tamil.
- **T3.** Hybrid on a vector snapshot with an all-zero vector, or with an empty query, is one channel and gives no depth cut. The zero vector also gives no `vector_ignored`. This is consistent with N1. The app would see results without any hint that the vector contributed nothing.
- Carried, not in this task (orchestrator's list): N2 (hang on a byte that cannot start UTF-8 under `analyzer-v2`, S2-T11), N3 (invalid-UTF-8 query echoed as a byte array on v1), N5 (vector mode without a vector on a zero-dimension snapshot is silent), ruling 3 (`serve`/CLI carry none of the new keys).
