# S2-T4 · Warnings, opt-in profile, and the effective request in the query report

**State:** built · **Series:** S2 (research doc, learnings 6 and 13) · **Depends on:** S2-T3 · **Size:** S · **Builder:** Sonnet 5 · **Tester:** Opus

`ss_query` cannot say why a list is empty or poor: a query word that matches
nothing is dropped silently (`zig/src/lexical_build.zig:139`), a query that is
only punctuation, a `candidate_k` that cut ranks, a vector ignored in lexical
mode (`zig/src/abi.zig:287-293`). The app wants to tell a child "I couldn't
find *dinosaurus*"; a tester wants per-phase timings without a profiler.

## Acceptance criteria
1. The report gains `warnings`: an array of `{code, message, term?}` with
   codes `query_term_unmatched`, `query_empty_after_analysis`,
   `vector_ignored`, `candidate_depth_cut`; and, when `"profile": true` is in
   `options_json`, `profile{tokenize_us, score_us, rank_us, serialize_us,
   matched_chunks}`; and `request{analyzer_id, retrieval_mode, top_k,
   candidate_k, path_prefix}` echoing what was actually used. All additive
   JSON: `contracts/search-tool.schema.json` and `CONTRACTS_VERSION` minor
   bump; Dart types mirrored; header documented.
2. **Bar (a):** with `warnings`, `profile` and `request` stripped, the output
   is byte-identical to the previous library on every golden.
3. **Bar (b):** every query word that matches no chunk appears in `warnings`
   (checked over the 200 random queries of S2-T3 plus 50 with planted unknown
   words).
4. **Bar (c):** with profile off, p50 changes by ≤ 2 %; with it on, by ≤ 10 %
   (same harness as S2-T3).
5. **Plants:** each code has a test that fails when its emission is removed.
6. All five suites green after the Report; libraries rebuilt last.

### What each mode emits
| code | lexical | hybrid | vector |
|---|---|---|---|
| `query_term_unmatched` | yes | yes | **no** (terms not used; the dictionary lookup is also skipped now, which closes S2-T3 finding 4; `analyzer-v2` still tokenizes, so an invalid-UTF-8 query still errors as before) |
| `query_empty_after_analysis` | yes | yes | no |
| `vector_ignored` | when a vector was passed | when a vector was passed and the snapshot has 0 vector dimensions | same as hybrid |
| `candidate_depth_cut` | lexical list | one per channel that was cut | semantic list |

`matched_chunks` is the number of chunks with at least one query term, before the path and label scope (0 in vector mode).

### Deviations and judgement calls to check
1. **Scope.** A word that is in the dictionary but occurs only in chunks outside `path_prefix` or needing labels the caller lacks is also `query_term_unmatched` (message "...in the searched scope"), because it matches no chunk the request may see. The check reads at most the postings up to the first in-scope chunk. In `check_unmatched_warnings.py` the vector snapshot's labelled chunks (every 11th file) are therefore excluded from "the corpus has this word"; without that, 6 of 1,750 runs disagreed with a naive corpus-words oracle, all of them words found only in labelled chunks.
2. **`candidate_depth_cut`** fires whenever a channel offered more positive, in-scope candidates than `min(candidate_k, chunks)`, as the criterion words it. In a single-channel mode a cut cannot change the returned `top_k` (`top_k <= candidate_k`), so a default-depth lexical query on a common word warns ("candidate_k 100 kept 100 of 9875 lexical candidates"). That is literal but noisy; the app may want to show it only in hybrid mode. Easy to narrow if the tester prefers.
3. `serialize_us` covers writing the report up to the `profile` field (it cannot time its own text). `tokenize_us` includes dictionary lookup and the scope check. The four phases do not sum to the call (open arena, result arrays, final copy are outside).
4. `request.top_k` and `candidate_k` are the validated values with defaults filled (100); `candidate_k` is not clamped to the chunk count. `path_prefix` is `null` when absent. The term in a warning is the analysed term (lowercased; NFC and simple-case-folded under `analyzer-v2`).
5. `warnings` and `request` are always present in `ss_query` output (`warnings` may be `[]`). The JSON-RPC result has neither, by choice, to keep `serve` byte-identical (checked: `serve` and `searchd query --json` md5 equal between the `c055c80` and new binaries on one request).
6. The request and the empty-warnings case are written with one `print` call each instead of field-by-field `Stringify` calls (measured: the field-by-field version cost about +2 % on the one-word query).
