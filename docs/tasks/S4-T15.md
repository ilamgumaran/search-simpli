# S4-T15 · The `both` query keeps a bounded top-`candidate_k` instead of sorting every scored file, and its two levels are explained

**State:** ready (starts from `main` after the S4-T14 merge, `41b184c`) · **Date:** 2026-11-06 · **Depends on:** S4-T2 (the filename channel and the `both` field, PR #21), S4-T12 and S4-T14 (the layout row and the verifier's two-level observation) · **Size:** S

**Owner:** the Xcode Mac orchestrator · **Orchestrator:** Claude Fable 5.1 · **Builder:** Claude Opus 5.5 (local) · **Verifier:** Claude Opus 5.5 (local, a different agent)

**Why.** The app asks every question with `search_field: both` (its merged query, M16-T21), and on the 10k timing corpus that warm query costs 2.86 or 3.25 ms (`ReleaseSmall`, `scripts/source_read_parity.py time --filename`, p50 of 30) where the content query alone costs 0.40 ms and the filename query 0.76 ms. **Where the rest goes, by reading the code:** `filename_field.queryDecoded` scores the body channel over every chunk the query's postings touch (two common words touch most of the corpus), groups the chunks to one candidate per file through `slot_of_file`, and then **sorts the whole candidate list** (`sortCandidates`, `std.mem.sort` over about every file) before taking the first `candidate_k` (default 100); the filename channel sorts its whole list the same way. The content query does not: `hybrid.searchSparse` keeps a bounded top `candidate_k` (`TopK.offer`) with the same tiebreaks and produces exactly the dense path's output, which is the pattern this task applies to the two channels of `both`. **The two levels:** S4-T10 measured the `both` query 0.35–0.42 ms slower with 48 B of padding in `Loads`; S4-T12 found four libraries with byte-identical reader source at 2.83–3.25 ms and filed the row "the warm `both` query is layout-sensitive"; S4-T14's verifier found that **one binary gives either level from one process to the next** (*before* 3.25 in one run and 2.86–2.91 in another; *before2* both levels inside one run), so the level follows the process's placement of something, not the build. A query whose cost is dominated by a full sort of a 10k-entry array and a scatter over two 10k-entry score arrays is a likely place for a placement effect (a page or cache-line boundary across a hot array). The row says this question goes before the next task whose bar includes the `both` query; this task answers it and, where the engine can, removes it.

### Ruling 2: the bounded selection

- `hybrid.TopK` became `hybrid.BoundedTop(T, Context, before)`, which is the same heap and the same `pdq` sort of the kept items. `TopK` is `BoundedTop(Candidate, void, candidateLess)`, and `searchSparse` is unchanged; hybrid's sparse-against-dense test passes.
- `filename_field.queryDecoded` is split into three private functions: `scoreQuery` (steps 1–5 unchanged), `rankChannels` and `fuse`.
  - `rankChannels` offers each positive filename score to a top of `min(candidate_k, touched)`.
  - For `both`, `rankChannels` keeps each file's best body chunk in `slot_of_file` (score, then the lower chunk id, the grouping rule unchanged). It then offers each file's kept chunk to a top of `min(candidate_k, files)`.
  - Both tops use `lessCandidate` itself as `before`.
  - `fuse` is `mergeHit`, RRF k = 60, `hitLess` and the `top_k` cut, all untouched. `sortCandidates` is gone.
- **Why it is exact.** Scores are finite and positive: BM25 with tf > 0, idf > 0 and a length factor ≥ 0.25. Within a channel paths are distinct: the catalog is strictly ascending and there is one candidate per catalog entry. So `lessCandidate` is a strict total order over each channel's candidates, and the stable full sort and heap-plus-`pdq` give the same unique prefix.
- **2(a).** `test "S4-T15 ruling 2(a)…"` in `filename_field.zig` keeps the old full-sort selection in test code (`referenceLess`, `referenceFull`).
  - It runs 30 fixed seeds. Sizes are 1, 2 and 3,000 files, then log-uniform; files have 0–6 chunks, and a third of texts are copied from an earlier chunk, so scores tie.
  - Paths come from 4 roots × 3 subfolders × 8 stems with suffixes. A label on one root, root masks, and prefixes (`school/`, `home/trips/`, `sc`, `zz/`).
  - It runs 16 requests per corpus, `top_k` 1–100 (half of them 1–10). The depths are `top_k`, `top_k`+1, 20, 100, n/2, n−1, n, n+1, 10,000 and `top_k`+rand(n).
  - It compares both channels element for element (path, `body_index`, `catalog_index`, the score's bits), then the hits of `fuse` over the reference.
  - The result is 30 corpora, 64,082 candidates compared, 126 lists cut (104 inside equal scores, 22 between different scores). It passes in Debug and `ReleaseSmall`.
