# S1-T22 · The iOS framework's segments are 16 KiB aligned at the source, so the app stops padding them

**State:** ready · **Date:** 2026-10-22 · **Depends on:** verified S1-T21 (`7c40937`) · **Size:** S–M

**Owner:** the Xcode Mac orchestrator (`vizhi-family-helper-pro`) · **Orchestrator:** Claude Fable 5.1 · **Builder:** Claude Opus 5.5 (local) · **Verifier:** Claude Opus 5.5 (local, a different agent). The cloud session is not used for this task.

**Why.** The app task M8-T5 (simpli-helper, 19 Oct 2026) found that the `aarch64-ios` dylib Zig links has segment sizes that are not multiples of the 16 KiB page (`__TEXT` vmsize/filesize `0x511f0`, `__DATA_CONST` `0x8`, `__DATA` likewise), and iOS code signing refuses such a binary on the phone (`dlopen` → "code signature invalid"; `codesign --verify --strict` on the Mac still says valid). The app works around it in `tools/ios/bundle_native_libs.sh`: a Python step rounds each segment's vmsize and filesize up to 16 KiB after copying the framework. A consumer should not have to repair the library it is given: the framework this package ships must be right as built, and `tool/check_native.sh` must say so.

## Rulings
1. **The shipped iOS binary is page-aligned as built.** `native/ios-arm64/search_simpli.framework/search_simpli` has every segment's `fileoff`, `vmsize` and `filesize` a multiple of 16 KiB (`__PAGEZERO` excepted; `__LINKEDIT`'s vmsize per the platform's rule — state it from `otool -l` of an Apple-linked dylib for comparison), the install name unchanged (`@rpath/search_simpli.framework/search_simpli`), `LC_BUILD_VERSION` platform iOS, minos 17.0, arm64 only. The builder picks the way, in this order of preference, and records why the earlier ones were not taken: (a) a `zig build` option that makes the self-hosted Mach-O linker emit page-rounded segments (search `std.Build.Step.Compile` and the `-z`/`-segalign`-like flags of Zig 0.16; measure); (b) link the dylib with Apple's linker from the iPhoneOS SDK over the Zig-built static library (`xcrun -sdk iphoneos clang -target arm64-apple-ios17.0 -dynamiclib libsearch_simpli.a -install_name … -o search_simpli`, in `tool/build_native.sh`, with the C ABI's exported symbols checked against the macOS dylib's list — same `nm -gU` set); (c) the rounding moved from the app into `tool/build_native.sh` as a post-link step (the same byte logic the app uses today, cited), so the shipped file is already padded. Whichever way: the binary's size, sha256 and `otool -l` segment table in the Report.
2. **`tool/check_native.sh` asserts the alignment** for the iOS framework (every segment's three numbers; a plain failure line naming the segment), and the Dart package's existing native tests still pass. The check is run on the shipped file and pasted.
3. **The Dart loader is unchanged;** the package version or the recorded native digest (`tool/source_digest.py` or whatever S1-T21 records) moves as the project's rule says, so the app's re-pin changes `searchSimpliCoreIdentity` exactly once (name the field the app reads).
4. **The macOS and Android libraries are rebuilt only if the chosen way touches their link** (way (a) might); otherwise byte-identical, proved by sha256 before and after.
5. **Private Apple symbols** (`___ulock_wait2`, `___ulock_wake`, `___getdirentries64`, `_execve`, from S1-T21's finding): unchanged by this task; one sentence in the Report whether way (b), if taken, changes the list (`nm -u`).
6. **Docs:** README's iOS paragraph (one sentence: the framework is page-aligned as built since S1-T22; the app's rounding step is retired by its own task), `PROJECT-STATE.md` S1-T22 section with the exact commands, `docs/journey/` next-task pointer. The app-side follow-up is named for the orchestrator: re-pin to this task's merge sha, delete the rounding step in `tools/ios/bundle_native_libs.sh` (the alignment test in `ios_bundle_test.dart` stays as the guard), republish once.
