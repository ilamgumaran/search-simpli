# S4-T8 · NFR-13 headroom past 10k files: measure 15k and 20k, name what grows

**State:** ready · **Date:** 2026-11-05 · **Depends on:** S4-T4 (merged at `2509003`), S4-T6 (merged at `bb1d602`) · **Size:** S for phase A (measurement); phase B, if any, is ruled separately

**Owner:** the Xcode Mac orchestrator · **Orchestrator:** Claude Fable 5.1 · **Builder:** Claude Opus 5.5 (local) · **Verifier:** the orchestrator for phase A (re-runs the scale tests once and compares the peaks; a measurement task adds no behaviour); an Opus 5.5 verifier if phase B is ruled

**Why.** The "NFR-13 headroom past 10k files" row in `docs/journey/03-next.md`. NFR-13 (CAP-19) caps every caller-owned workspace at 64 MiB (67,108,864 B); `zig/src/nfr13_arena_test.zig` proves it over the family folder and over a generated 10,000-file corpus with a capped allocator that records peak live bytes. The recorded 10k peaks (S4-T4 Verdict, byte for byte S4-T2's): open 45,222,180 B; `find` 51,777,594; `list_files` 52,264,290; with filename sections: open 50,128,018, `find` 56,683,432, `list_files` 57,170,128 (85.2 % of the cap), filename query 51,317,656, `both` 51,560,116. The open alone is three quarters of the cap at 10k, so a phone folder somewhat past 10k files would breach it, and nothing today says at what count or which table grows. This task measures 15k and 20k, attributes the open's resident bytes to its tables, and reports the count at which each operation would reach the cap. It changes no behaviour and no format; whether and how to bound (page `list_files`, trim the open's resident tables, lazy-load a table) is phase B, ruled on the Report.

## Rulings
1. **The corpus generator takes the file count.** `nfr13_arena_test.zig`'s `generateCorpus` (and `word`'s quota loop) take `file_count` as a parameter; the three existing tests pass 10,000 and keep their names and their printed peaks **byte for byte** (the Report shows the 10k numbers from this branch beside the S4-T4 Verdict's: all equal). The folder layout stays 100 files a folder (`group-NN/doc-NNNNN.md`), so 15k is 150 folders and 20k is 200.
2. **Two scale tests, gated.** New tests "NFR-13 scale: 15,000 files" and "NFR-13 scale: 20,000 files", each building the corpus with the filename channel on (the larger configuration) and running `measure` for the open, `find` ("the"), `search_knowledge` ("the" + a rare word), `list_files`, a filename query and a `both` query, **under a measurement cap of 256 MiB**, printing every peak with the label and the file count, and asserting only that every peak is above zero and that the open's peak grew with the count. They run only when the environment variable `SEARCH_SIMPLI_NFR13_SCALE=1` is set (`std.process` at test start; otherwise `return error.SkipZigTest` with a printed line naming the variable), so `zig build test` and CI are unchanged in time and in count except for the two skips. Each scale test must finish in under 10 minutes in Debug on the Mac; if 20k does not, say so and report what did finish.
3. **The open's resident bytes, by table.** With the 20k index open, attribute the open's peak to its parts: measure, with the same `Capped` allocator, the bytes held after each loader the open runs (the manifest and sections directory, the documents/paths table, the statistics, the lexical dictionary and any table the open decodes eagerly, as `snapshot_open.zig` and `engine.zig` name them), at 10k and at 20k. One table with its bytes per 1,000 files; no guessing: a number per table, from a run. If a table is loaded lazily today and so does not count at open, say which.
4. **The Report answers four questions with numbers**, each from this branch's runs: (a) peak live bytes per operation at 10k, 15k and 20k, in a table, with the growth per 1,000 files between 10k and 20k; (b) the file count at which each operation would reach 64 MiB if the growth stayed linear (state the formula); (c) which table dominates the open at 20k and its share; (d) the generated corpus's size on disk and the index's size at 15k and 20k, and the Debug wall time of the two scale tests. Also, if it fits in the 10-minute rule: `scripts/s4t4_budgets.py`'s one-changed-file p50 at 15k with `ReleaseSmall` and the filename channel on (NFR-12's bar is 200 ms at 10k; the row is informational here), otherwise "not measured".
5. **No behaviour or format change.** The library, `searchd`, the contracts, the Dart binding, the natives and `native/SOURCE-SHA256` are untouched (the test file is not a digest input: state the digest is unchanged). `docs/journey/03-next.md`: the row gains the measured counts and the phase-B question for the orchestrator (do not strike it). `docs/requirements/cap-19-folder-knowledge.md`'s NFR-13 evidence line gains one sentence with the 20k peak and the projected count.
6. **Diff scope.** `zig/src/nfr13_arena_test.zig`, `docs/journey/03-next.md`, `docs/requirements/cap-19-folder-knowledge.md`, this file. Anything else is a deviation to name.
