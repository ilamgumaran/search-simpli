# S4-T17 · `find` ranks its hits by sorting an index list and checks scope by pointer, so its speed no longer depends on where the compiler puts a byte loop

**State:** ready (starts from `main` after the S4-T16 merge, `c53c953`) · **Date:** 2026-11-06 · **Depends on:** S4-T16 (the finding: its Report's "`find`: the loop found"; its scratch variants), S4-T15 (the bounded selection and the two-level reading) · **Size:** S

**Owner:** the Xcode Mac orchestrator · **Orchestrator:** Claude Fable 5.1 · **Builder:** Claude Opus 5.5 (local) · **Verifier:** Claude Opus 5.5 (local, a different agent)

**Why.** `find` (`the`, words mode, 20 a page, the 10k timing corpus, `ReleaseSmall`) takes 5.84 ms in the `aa765d7` library and 7.79 ms in S4-T16's, with no line of `find` changed. S4-T16's builder sampled both: `find.zig:241` sorts every kept hit, `std.sort.pdq(Candidate, kept.items, engine.documents, rankedBefore)`, and `Candidate` is 64 bytes, so the sort's swap moves each record **one byte at a time**; in one layout the byte step is five inline instructions (1.70 ms of the call), in the other the `ReleaseSmall` machine outliner makes it a call per byte (3.78 ms). Two more costs sit beside it in both layouts: `visible()` copies the whole `Engine` and `Request` structs through `memcpy` for every posting it checks (`documentInScope` takes them by value; 1.87 ms), and the comparator's byte compare (1.20 ms, the ranking itself). The order is total (score, then root, then path, then start line, then record number), so any correct sort gives the same list. S4-T16's scratch (`S4-T16-scratch/fix-before`, `fix-after`, `fix2-after`; `results/reads-fix*.json`): sorting a `u32` index list through `rankedBefore` and copying each record once gives **5.22–5.23 ms in both layouts**; adding `documentInScope(*const Engine, *const Request)` gives **3.45–3.47 ms**; 84 pages over six queries (words, prefix, phrase, paged by cursor) hash the same (`dadf5f4f…`) in all six libraries. The app's merged question runs `find` for every file-name and content look-up; the phones get this at their next pin.

## Rulings
1. **The index sort.** `find` sorts a `[]u32` (or `usize`) of positions into `kept` under `rankedBefore` applied through the indices, then builds the ranked list by one copy per record (or reads the page and `fileCounts` through the indices without a second list, if that is simpler and the output is the same). The comparator is unchanged; `pdq` stays; nothing about which hits are kept, deduplicated, paged or counted changes. **A bounded top-k is not used:** `fileCounts` lists files in the order of their first appearance in the full ranking, so the full order is needed (S4-T16's finding; say so in a comment).
2. **Scope by pointer.** `documentInScope` (and `visible()` if it is the caller) take `*const Engine` and `*const Request`; no other signature changes. Any other by-value pass of `Engine` or `Request` on `find`'s per-posting or per-candidate path found while reading is named in the plan (fixed only if the orchestrator rules it in).
3. **Tests.** (a) A unit test in `find.zig` over random candidate lists (seeded; scores with ties, equal scores across roots, paths sharing prefixes, equal paths with different start lines and record numbers): the index-sorted ranking equals a reference sort of the records themselves under the same comparator, element for element. (b) The existing `find` tests pass unchanged. (c) A test that `fileCounts` over the index-ranked list equals today's over the record-ranked list (may be part of (a)). (d) Plants: the comparator applied to the wrong element (index as record number); the copy loop dropping the last record; `documentInScope` by value restored (timing only, not a test).

### The code read (`git diff c53c953 7bb1e19 -- zig/ scripts/`)

- **`rankKept`.** It counts the kept candidates, writes their positions into an exactly sized `[]u32`, sorts it with
  `std.sort.pdq(u32, …)` through `Ranking.lessThan`, which applies the unchanged `rankedBefore` to the two candidates the
  positions name, then copies each candidate once into an exactly sized list in rank order; `find` reads that list for the
  page, `attachMatches`, `makeHit`, `fileCounts`, `total_hits` and the cursor exactly as it read `kept.items`, and
  `deduplicated` is still `candidates.len - total`. **The order is strict and total:** every candidate comes from one
  record (`conjunctive` appends at most one per document, from the driver's ascending postings or the union array;
  `filterPhrase` and `deduplicate` only drop or mark), so two different candidates differ in `document_index`, the last
  key, and `rankedBefore` (score descending, `root_id`, path, start line, record number) never calls two distinct
  candidates equal; any correct sort, stable or not, gives the one sequence. A score of `-0.0` against `0.0` compares
  equal under `!=` and falls to the next key in both forms. The positions fit `u32` as `document_index` already does. The
  doc comment says why the full order is kept (`files` lists every file in the order of its first appearance in the whole
  ranking) and why the sort moved off the 64 B records.
- **The two pointer signatures.** `documentInScope(*const Engine, *const Request, usize)` and `termInScope` likewise;
  their callers are `Context.visible` and `Context.hasVisiblePosting` (`&context.engine`, `&context.request`: pointers
  into the context's own copy, which lives for the call), `termInScope`'s own loop, and `apply_test.zig`'s one call site
