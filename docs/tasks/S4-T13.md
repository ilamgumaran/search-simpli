# S4-T13 · The writer's open of the previous generation checks what the checksums do not, and the filename channel carries its lexical section when no path changed

**State:** ready (starts from `main` after the S4-T12 merge, `0f07746`) · **Date:** 2026-11-06 · **Depends on:** S4-T11 (the carried merge), S4-T12 (the end-of-walk refusals hold in every build; one validation at encode) · **Size:** M

**Owner:** the Xcode Mac orchestrator · **Orchestrator:** Claude Fable 5.1 · **Builder:** Claude Opus 5.5 (local) · **Verifier:** Claude Opus 5.5 (local, a different agent)

**Why.** After S4-T11 and S4-T12 one changed file in the 10k index costs about 75 ms with the filename channel off and about 92 ms with it on (`ReleaseSmall`, p50; S4-T12's verifier). The stage profile now reads, filename off: **`open_previous` 24.3–26.6 ms**, the largest stage; `build_documents` 10.7; `encode_sections` 16.0 (the lexical 9.1, the documents and the source copy the rest); `publish` 7.5; `load_previous` 5.8; `build_lexical` 4.9; `state_encode` 2.5. With the channel on, **`filename_build` 9.2–9.9 ms and `filename_validate` 3.8 ms** plus a larger manifest and publish make the 16 ms difference. Two things in those stages are work the checksums already do, and one is a rebuild of what did not change. (1) `apply.zig`'s `openPrevious` reads the manifest, the documents, lexical and source sections and the state section, checks every section's size and stored checksum against the manifest, and then decodes: the lexical section **with position validation** (`lexical_segment.decode`'s default walk of sections 4 and 5, about 4.9 ms at 10k by S4-T12's profile of the same pass) and the source section through `openIndexed`, which **validates every file's line map against its bytes** (S4-T10's reader does the same at first use; S4-T11 carries those maps byte for byte). Both walks guard against a section whose bytes are damaged, which the XXH3-64 checksum the writer has just verified already refuses; what they add is a guard against a section that is internally inconsistent **with a valid checksum**, which only a wrong writer can produce. For the lexical section S4-T11's merge now refuses a misaligned section 4 or 5 in every build (S4-T12), and the merged index is validated whole before it is encoded (`validateIndex`, including every ordinal and offset), so a carried inconsistency cannot reach a file. For the source section the reader validates each file's line map at first use and refuses that file with `CAPACITY` naming the check, so a carried inconsistency cannot reach an answer. (2) `filename_field.build` tokenizes every stem and builds and encodes the catalog and the filename lexical index for the whole folder at every generation, and `validateBuilt` decodes both sections again; for one changed file the sorted path list is unchanged, so **the filename lexical section is byte-identical to the previous generation's**, and only the catalog's anchors (the changed file's first chunk) move. This task makes the writer's open check only what the checksums do not, and lets the filename channel carry its lexical section when no path was added, removed or renamed. **Format, readers, contracts (2.2.0), analyzer and every section's bytes are unchanged**; nothing is rebuilt on any phone.

## Rulings
1. **Profile first, in the Report, before any change.** `main` at `0f07746` on the 10k timing corpus (`scripts/gen_timing_corpus.py <dir> 10000`, `corpus_matches_recorded: true`), `ReleaseSmall`, one changed file as `scripts/s4t4_budgets.py profile` does, filename off and on, ten runs, p50 and worst, load stated: `open_previous` split into the reads (manifest, documents, lexical, source, state), the two stored-checksum computations, `segment.decode`, `lexical_segment.decode` with and without position validation, `source.openIndexed` split into its checksum, its line-map validation and its index; and `filename_build` split into grouping, tokenizing, the lexical build, the two encodes, with `filename_validate` beside it. Sub-timers under `SEARCH_SIMPLI_APPLY_STAGES` through `Stages.sub`/`inner` as S4-T11 and S4-T12 did, kept if they fit `max` 48 (state the count); otherwise a scratch measurement, stated as such.
2. **The writer's open validates positions only where the checksum cannot.** `openPrevious` decodes the lexical section with `validate_positions = false` (the reader's deferred setting since S4-T1), **after** the stored checksum has matched the manifest's (it already does, before the decode); the position walk the writer still needs is the one it already pays: `mergeCarried`'s `skipVarintsChecked` and end-of-walk refusals (S4-T12), and `validateIndex` over the merged index before it is encoded. **Tests:** (a) a previous lexical section with one byte flipped in section 4 is refused at open by `LexicalSectionChecksumMismatch` (today's behaviour, kept); (b) a previous lexical section with one ordinal gap set to zero (a repeated ordinal) and the stored XXH3 checksum **re-sealed** is refused before anything is published, with the error named (today `InvalidPositions` at open; after this task `InvalidPositions` from the final `validateIndex`, or `InvalidLexicalSection` from the merge: say which, and that nothing was written); (c) the same with a byte appended to section 4 and the checksum re-sealed (refused by the merge's end-of-walk check, S4-T12); (d) the generation written from an untouched previous section is byte-identical to today's. The reader's `ss_open` is untouched.
3. **The writer's open of the source section validates line maps only where the checksum cannot.** `openPrevious` opens the previous source section with its checksum verified against the manifest (today's check, kept) and **without** the per-file line-map walk (`openIndexed`'s `validateLineMap` over every file, or whatever its successor is named), keeping the records table and the text for carrying. A fresh or changed file is still scanned and hashed when encoded (S4-T11 ruling 3). **Tests:** (a) a previous source section with one flipped byte is refused at open by `SourceSectionChecksumMismatch` (kept); (b) a previous source section whose line map was corrupted and whose checksum was re-sealed: the writer carries the record (state this plainly in the Report and in `docs/source-section-v1.md`'s "Reading" paragraph: the writer's guard is the checksum; a checksum-valid inconsistency is a forged section, which the reader refuses per file at first use with `CAPACITY` naming the check, exactly as it does for a section it opened itself: the test shows that `read_span` on the carried file answers that `CAPACITY` and every other file answers as before); (c) the generation written from an untouched previous section is byte-identical to today's. If the builder finds the line-map walk is **not** where `openIndexed`'s time goes (ruling 1 decides), this ruling is "no change, the numbers say why".
4. **The filename channel carries its lexical section when no path changed.** In `buildGeneration`, when the filename channel is on and the previous generation has filename sections, and the sorted list of record paths with their labels is identical to the previous catalog's (the builder states the exact condition; a rename, add or remove fails it), the writer **copies the previous generation's filename lexical section bytes** (read once, its stored checksum verified against the previous manifest's) instead of tokenizing and building, and rebuilds only the catalog (the grouping that finds each file's anchor chunk is still done, since anchors move with a changed file's chunks); `validateBuilt` then decodes the catalog and checks it against the grouping, and checks the carried lexical section by its checksum and its header counts against the catalog (not a second decode). When the condition fails, today's full build runs. **The bar is bytes:** `filenames-N.hybseg` and `filename-lexical-N.hyblex` byte-identical to a full build for the one-changed-file case, the changed-chunk-count case, the add, remove and rename cases (which take the full path) and the empty generation; S4-T4's reversed-input test and `filename_field_test.zig`'s cases pass unchanged; the 10k compare of `scripts/s4t11_budgets.py compare` extends to the two filename sections if it does not cover them (state).
