# S4-T13 · The writer's open of the previous generation checks what the checksums do not, and the filename channel carries its lexical section when no path changed

**State:** ready (starts from `main` after the S4-T12 merge, `0f07746`) · **Date:** 2026-11-06 · **Depends on:** S4-T11 (the carried merge), S4-T12 (the end-of-walk refusals hold in every build; one validation at encode) · **Size:** M

**Owner:** the Xcode Mac orchestrator · **Orchestrator:** Claude Fable 5.1 · **Builder:** Claude Opus 5.5 (local) · **Verifier:** Claude Opus 5.5 (local, a different agent)

**Why.** After S4-T11 and S4-T12 one changed file in the 10k index costs about 75 ms with the filename channel off and about 92 ms with it on (`ReleaseSmall`, p50; S4-T12's verifier). The stage profile now reads, filename off: **`open_previous` 24.3–26.6 ms**, the largest stage; `build_documents` 10.7; `encode_sections` 16.0 (the lexical 9.1, the documents and the source copy the rest); `publish` 7.5; `load_previous` 5.8; `build_lexical` 4.9; `state_encode` 2.5. With the channel on, **`filename_build` 9.2–9.9 ms and `filename_validate` 3.8 ms** plus a larger manifest and publish make the 16 ms difference. Two things in those stages are work the checksums already do, and one is a rebuild of what did not change. (1) `apply.zig`'s `openPrevious` reads the manifest, the documents, lexical and source sections and the state section, checks every section's size and stored checksum against the manifest, and then decodes: the lexical section **with position validation** (`lexical_segment.decode`'s default walk of sections 4 and 5, about 4.9 ms at 10k by S4-T12's profile of the same pass) and the source section through `openIndexed`, which **validates every file's line map against its bytes** (S4-T10's reader does the same at first use; S4-T11 carries those maps byte for byte). Both walks guard against a section whose bytes are damaged, which the XXH3-64 checksum the writer has just verified already refuses; what they add is a guard against a section that is internally inconsistent **with a valid checksum**, which only a wrong writer can produce. For the lexical section S4-T11's merge now refuses a misaligned section 4 or 5 in every build (S4-T12), and the merged index is validated whole before it is encoded (`validateIndex`, including every ordinal and offset), so a carried inconsistency cannot reach a file. For the source section the reader validates each file's line map at first use and refuses that file with `CAPACITY` naming the check, so a carried inconsistency cannot reach an answer. (2) `filename_field.build` tokenizes every stem and builds and encodes the catalog and the filename lexical index for the whole folder at every generation, and `validateBuilt` decodes both sections again; for one changed file the sorted path list is unchanged, so **the filename lexical section is byte-identical to the previous generation's**, and only the catalog's anchors (the changed file's first chunk) move. This task makes the writer's open check only what the checksums do not, and lets the filename channel carry its lexical section when no path was added, removed or renamed. **Format, readers, contracts (2.2.0), analyzer and every section's bytes are unchanged**; nothing is rebuilt on any phone.

### Ruling 4: the filename lexical section carried when no path changed (`4dc1a82`, `d7e4bc6`)

**The exact condition.** `filename_field.group` gives this generation's catalog: one record
per path in path order, with its anchor chunk's packed `required_labels`. `samePaths` walks
the previous generation's body documents, already decoded by the open. Each catalog entry
must equal the next previous document's path and labels. That path's chunks are then
skipped, and at the end every previous document must have been consumed. So the same
paths, in the same order, with the same labels, and every file's chunks adjacent. A rename,
add, remove or label change fails it, and so do previous documents not in path order.

**The carry.** If the condition holds and the previous manifest has filename sections, the
previous `filename-lexical-N.hyblex` is read once. `carryLexical` then checks, in order:

1. the policy id;
2. the size against the manifest;
3. `inspect` (computed checksum against the header's);
4. the header's checksum against the manifest's;
5. `HYBLEX01` with FNV-1a;
6. the document count against the new catalog's length and the manifest's file count;
7. the term and posting counts against the manifest.

Any failure, or a read error other than out-of-memory, takes today's full build
(`buildFromCatalog`). `buildCarried` encodes only the catalog. `validateBuilt` on the
carried path (`validateCarried`) does three things:

- it decodes the new catalog and checks it against the grouping, field by field with the
  reader's per-entry rules;
- it checks that the carried header's checksum and the stored checksum both equal the
  manifest's;
- it checks the header's counts against the catalog and the manifest.

There is no second decode.

**Grouping (`d7e4bc6`).** `group` now counts the files first, allocates the catalog once,
and points each record's text at the path's stem (a slice, not a copy). The carried path's
grouping went from 2.756 to 1.525 ms. The full path uses the same function.

### The correctness read (`git diff 0f07746 -- zig/src/`)

- **`openPrevious`.** Lexical: the stored value against the manifest's
  (`lexicalStoredChecksum`, unchanged), then `lexical_segment.inspect` (the computed
  checksum against the stored one), then `decodeWith(…, .{ .validate_positions = false,
  .inspected = header })`, whose `options.inspected orelse try inspect(encoded)` skips the
  second checksum (read). The counts against the manifest follow, as before. Documents:
  `segment.inspect` then `decodeInspected`, which is what `segment.decode` is. Source:
  `inspect` once, the stored value against the manifest's (`SourceSectionChecksumMismatch`),
  the kind rule, then `openIndexedInspected`. The positions the writer still walks:
  `mergeCarried`'s checked varint walk with its end-of-walk refusals (S4-T12), and the
  final `validateIndex` in `encodeAllocMarked` (plant 1 shows 2(b) depends on it).
  `ss_open`, `snapshot_open.zig`, `scope.zig`, `engine.zig`, `lexical_segment.zig`,
  `segment.zig`, `zig/include`, `contracts`, `bindings/dart/search_simpli/lib`, `scripts`
  and `tests` are not in `git diff --stat 0f07746`.
- **`openIndexedInspected` equals `openIndexed`.** It is `openIndexed` with the
  `inspect` call replaced by the header passed in, and `openWith`'s `inspected orelse try
  inspect(encoded)` takes the same header; `Index.init`, the table walk, every
  `validateLineMap`, and the three fields set afterwards are the same lines. `open` and
  `openIndexed` pass null, so the readers run exactly as before. `Section.checksum` is
  `header.checksum` in both. The new `source.zig` test compares the offsets, checkpoints
  and checksum and shows a re-sealed bad line map refused by both.
- **`samePaths`.** It walks the new catalog (sorted by path, one entry per path from
  `group`) against the previous body documents in their stored order: each entry must
  equal the next previous document's path and packed labels; that path's run of documents
  is skipped; at the end every previous document must be consumed. So: the same paths, in
  the same order, the previous documents in path order with each file's chunks adjacent
  (`[a, b, a]` leaves one unconsumed, false; `[b, a]` fails at the first entry). The empty
  generation (both empty) is true, and the walk's empty-to-empty step carries a
  zero-document section byte-identical to a full build. The labels rule compares the
  previous file's first chunk with the new anchor; `group` already refuses a file whose
  chunks disagree on labels (`InconsistentLabels`), and labels do not enter the filename
  lexical section (deviation 3), so the rule can only send a case to the full build. The
  condition is sufficient for byte identity: `lexical_build.build` reads only the
  documents' count and the token lists, and the tokens come from the stems of the paths in
  catalog order with the analyzer, which `applyParsed` refuses to change between
  generations (`AnalyzerMismatch`, read). A file that loses its last chunk leaves the
  catalog and fails the condition.
- **`carryLexical`'s seven checks.** In order: the policy id against the filename policy;
  the size against the manifest's `lexical_bytes`; `inspect` (the computed checksum
  against the header's, any decode refusal → null); the header's checksum against the
  manifest's `lexical_checksum`; no positions and FNV-1a (`HYBLEX01` as the encoder writes
  it for the filename index); the header's document count against the new catalog's
  length, and the manifest's `file_count` against it; the header's term and posting counts
  against the manifest's. Each failure returns null, which takes the full build;
  `readWhole`'s errors other than out-of-memory do too. `validateCarried` re-checks the
  header's and the bytes' stored checksum against the manifest's, and the counts against
  the decoded catalog, and decodes the new catalog and compares it field by field with the
  grouping (plant 3 shows it as the second guard).
- **The grouping change and the stem slice.** `group` counts the paths, allocates the
  catalog once (`initCapacity` then `appendAssumeCapacity`; the count pass uses the same
  path-equality test as the grouping loop, so the capacity is exact), and sets each entry's
  `text` to `stem(path)`, a slice of the same path bytes its `path` field already pointed
  into before this task (only the text was copied). So the catalog lives no longer than
  the paths it already depended on. In `buildFilenames` those are this generation's
  documents' paths (fresh records' or the previous section's decoded bytes, both from the
  call's arena, `applyChanges`' documented allocator), and the catalog is encoded and
  checked (`validateBuilt`) and the bytes published within the same `applyParsed` call; the
  other callers of `filename_field.build` (the full index and `import-json`) encode within
  the call as before. When `group` sorts a copy (unsorted input), the copy holds the same
  path slices.
- **`buildFilenames`** carries only when `prev` (the previous engine, null for
  `options.fresh`) gives `samePaths` true and the previous manifest has filename sections;
  the bytes come from the previous generation's `lexical_file` in the same directory,
  under the writer lease, before any file of the new generation is written.
- **The `Stages` slot count.** `max` is 48 and `mark`, `sub` and `inner` stop at it. My
  run of the worst path (`searchd index --update` with `SEARCH_SIMPLI_APPLY_STAGES=1` after

  edit on the same directory (the carried path) printed 46. The other stage names
  (`build_lexical.occurrences`, `.layout`, `.encode`) belong to the fresh build, which has
  no `open_previous` sub-stages, so no path prints more.
