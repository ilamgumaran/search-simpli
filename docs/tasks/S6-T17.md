# S6-T17: a full rebuild does not fail when another writer publishes while it reads `MANIFEST`

**State:** filed by the orchestrator, 20 Nov 2026, from `main` at `4c84ee8` · **Depends on:** [S6-T13](S6-T13.md) (its fix for an open; this is the follow-up it left open) · **Plan:** [objective plan](../plans/2026-11-16-objective-plan.md), section G (correctness follow-ups)

## Why

[S6-T13](S6-T13.md) made an open read `MANIFEST` through one handle, so a
publish between the `stat` and the read cannot make the open fail. Its Report
and Verdict (finding 3) list the same pattern left in the writer: a full
rebuild (`ss_index_folder` without `update`; `searchd index` without `--update`
or `--generation`) calls `generation_alloc.nextFreeGeneration` **before** it
takes `WRITER.LOCK`. That reads `MANIFEST` in `generation_alloc.currentGeneration`
by one `stat` and then a read by name. If a second writer publishes in between,
this writer can fail with `Truncated` where it should go on to publish or to
`WriterBusy`. `incremental_state.readStateFile` runs in the same place; its
caller turns every error into `null`, so a race there can lose the
`INDEX-STATE.json` trace of the highest generation for that one call.

This was read from the code, not reproduced.

## What

1. **Reproduce first.** A test that fails on `main`: a `MANIFEST` replaced (by
   rename, as a publish does) with a longer and with a shorter one between the
   `stat` and the read in `currentGeneration`. Use the way S6-T13's tests did it
   (read its task file and tests first; reuse its seam if one fits). If it cannot
   be reproduced, stop and report: the task is then a document correction only.
2. **Fix `currentGeneration`** so the size and the bytes come from the same
   open file, as S6-T13 did for the open. Reuse the core's existing helper if
   one fits; do not add a second copy of the pattern.
3. **`readStateFile` before the lease.** Reproduce or rule out the lost trace
   (replace `INDEX-STATE.json` between its `stat` and read, and see whether
   `nextFreeGeneration` returns a number at or below one already used). Fix it
   the same way if it is real. State which it was.
4. **Report what remains**: after the fix, every `stat`-then-read-by-name site
   left in `zig/src` outside tests and benchmarks, each with why it is safe
   (under the lock, or the user's own file) or filed as a follow-up.

## Rulings

1. **Answers and formats unchanged.** No contract, C header, format or error
   name changes. The generation number a full rebuild chooses is the same as
   `main`'s in every case without a race.
2. **A race ends in one of two ways:** the writer goes on with a number above
   every generation on disk, or it returns `WriterBusy`. Never `Truncated`, and
   never a number already used.
3. **Natives.** Function bodies change, so the natives are rebuilt and
   restamped in the same commit, with sizes reported against `main`'s (macOS
   1,006,456 B, Android 966,800 B, iOS 971,424 B, `searchd` ReleaseSmall
   1,151,208 B). The changed code is on the writer's path only; say whether any
   open, search or find path's code changed. If none did, timing by the rule of
   2026-11-17 is not owed; if one did, it is, before a Verdict.
4. **`core.api`.** No new name in `core.api`; both guards of S6-T15 and the
   S6-T16 rule pass.
5. **Stop before:** changing when the lock is taken (moving `nextFreeGeneration`
   under the lease is a design change; describe it as an option if the fix above
   is not enough, do not make it); a contract, header, format or answer change.

### The fix (`5bfd3e0`)

`generation_alloc.currentGeneration` calls `snapshot_open.readManifest` (one open of `MANIFEST`, a `stat` of that
handle, an allocation of that size, the read through the same handle). It maps `FileNotFound` to 0, as before, and
frees the buffer after `manifest.decode` (the old code left it to the caller's arena; only the generation number is
returned, so nothing points into it). A publish renames a new `MANIFEST` in, so the handle keeps the old file and
the read is whole. The directory listing that follows in `highestGenerationOnDisk` then finds the new generation's
sections. So the race ends with a number above every generation on disk (ruling 2's first way). The second way,
`WriterBusy`, is the lease's existing behaviour; it is not reached in these tests, since the step finishes and
releases the lock before the rebuild takes it.

- Same open flags as before (`.{}`); same errors for a damaged or absent `MANIFEST`. The error set can only shrink: a
  second open by name, which could fail, is gone.
- `currentGeneration`'s other caller, `apply.applyParsed` (line 767), holds `WRITER.LOCK`; it reads the same bytes as
  before.
- No contract, C header, format, error name or answer changes. No name added to `core.api`; `check_layers.py` (both
  S6-T15 guards and the S6-T16 rule) passes.
- When the lock is taken is unchanged (ruling 5).

**What the fix does not cover (read from the code, not tested; for the maintainer).** `nextFreeGeneration` still runs
before the lease. If a second writer publishes the very number this rebuild has just chosen, between the choice and
`tryAcquireWriter` (`apply.zig` line 764), the rebuild takes the lease afterwards and its publish meets that number's
existing section files. The publish refuses them with `PathAlreadyExists` and publishes nothing, as
`docs/generation-lifecycle.md` says of a caller's own number. That is neither of ruling 2's two ways, but no number
is used twice. Closing it means choosing the number under the lease, which `apply.zig` line 1224 already does for
`--update` and `apply_changes`: the design change ruling 5 says to describe, not make.

### Item 3: `incremental_state.readStateFile`

It opens `INDEX-STATE.json`, `stat`s the handle, closes it and reads by name. Its caller in `nextFreeGeneration` is
`recordedGeneration`, which runs before the lease in a full rebuild. Test 3 shows both halves of the reading:

- **The trace is lost for that read:** a publish that replaces the pointer with a longer one between the two gives a
  cut JSON, `recordedGeneration` turns the parse error into `null`, and `INDEX-STATE.json` does not count.
- **No number is lost:** `nextFreeGeneration` returns 11 with generations 9 and 10 on disk, on `main`'s code and on
  the head. A publish writes `INDEX-STATE.json` only after it has linked its sections and renamed its `MANIFEST`
  (`apply.zig`: `publishLeasedKeepingWithExtras`, then `savePointer`), and the directory is listed after the pointer's
  read, so the new generation's `documents-N`, `lexical-N` and `state-N` count. A new pointer shorter than the
  `stat` said is read whole, since the read by name stops at the end of the file.

So it is not fixed. A fix "the same way" would need a whole-file read of a named file through one handle.
`readManifest` reads only `MANIFEST`. Generalizing it changes a function on the open path, which makes timing owed;
a copy of its body beside it is the second copy item 2 rules out. **A decision for the maintainer** if the trace
should not be lost even for one read.

6. **Item 3's reasoning holds.** A publish links its sections (`publishWithExtrasRecorded`), renames `MANIFEST`, and
   only then writes `INDEX-STATE.json` (`savePointer`, an atomic rename; `apply.zig` 1233, then 1239). It never writes
   in place. `highestGenerationOnDisk` reads `MANIFEST`, then the pointer, then lists the directory. So any publish
   whose new pointer a cut read loses has its sections on disk before the listing starts.

   I tried to break it in three ways:
   - A cut prefix of a longer JSON pointer lacks its closing brace, so it parses to `null`, never to a smaller number.
     If only a trailing byte is cut, it parses to the new number.
   - A shorter or equal-length new pointer is read whole.
