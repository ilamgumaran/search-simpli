### Non-blocking findings
1. **The parser inherits `std.fmt.parseInt`'s leniency.** `+5` is read as 5, `-0` as 0, and `1_000` as 1000, all exit 0. Each is a non-negative whole number, so this is within the criterion, but the underscore form is undocumented. A digits-only check before `parseInt` would make the accepted syntax exactly what `--help` implies.
2. **Edge cases of the message.** An empty value prints `--max-total-bytes:  (expected …` (the value is there but invisible; quoting it would help). A value too long for `main.zig`'s 512-byte buffer (I used 600 digits) takes the `WriteFailed` fallback and prints `searchd: invalid value for --max-file-bytes` without the value. Both are still one line, no trace, exit 1.
3. **The Report's "every other bad argument exits 1" is incomplete.** `searchd frobnicate` (unknown command) and a bare `searchd` print the usage text and exit **0**, on `origin/main` and on the merge alike. Pre-existing and outside this task. So are the traces after `unknown index flag`, after a flag with no value (`error: MissingMaxFileBytes`), after `index` without a folder and after `query` without a directory. A follow-up could route all of these through the same one-line, exit-1 path.
4. **The new Python test hard-codes `9.9.9\n`.** If `contracts/CONTRACTS_VERSION` ever reads exactly `9.9.9\n`, `test_changing_contracts_version_changes_the_digest` fails for no reason. My plant used that value, which is why I saw `failures=2` where the Report shows `failures=1`. Appending a byte to the current content would remove the coincidence.
5. `main.zig`'s `parseByteCountOrExit` (stderr and `std.process.exit(1)`) has no Zig test, as the Report says. I covered it by running the binary.
