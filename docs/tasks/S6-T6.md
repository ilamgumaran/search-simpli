## Source

The objective asks for semantic matches where possible. The engine stores and scores vectors and fuses by rank, but only for snapshots imported from the Python reference; a folder indexed by `searchd` or through `apply` is lexical only. The plan's item E: the host supplies a vector per chunk and a query vector, each bound to a model identity the engine checks; the engine runs no model. Capability document first. This task writes that document so it can be reviewed before any code.

## Rulings

1. **Inventory, from the code, with file and function names.** What the engine does with vectors today: the import path, the vector section format, how a query vector arrives on each surface, what identity is checked and where, how hybrid fusion picks candidates, what `apply` and the folder indexer write (and that they write no vectors), what the manifest flags say, the embedding-boundary and invariant rules that apply (quote them by INV number), and what S2-T13 enforces on values.
2. **The hard question, answered with options: how a host learns the chunks.** The engine chunks; the host embeds. Set out at least these, with what each costs in calls, memory, bytes written and failure cases: (a) two-phase: `apply` publishes lexical, the host lists chunks without vectors and supplies them in a second publish; (b) a callback or pull interface during `apply`; (c) the host chunks with a published chunker identity and sends vectors keyed by chunk identity with the change. For each: what happens on a one-file update, on a chunker or model change, when some chunks have no vector (partial coverage: what a hybrid query does, what it reports), and how a crash between phases leaves the index. Recommend one.
3. **Model identity.** What is bound (model id, dimension, normalisation, a version), where it is stored, what the engine refuses (a query vector of another identity; mixed identities in one generation), and how a model change is carried out without a window of wrong answers.
4. **Format and size.** Whether the existing vector section serves or needs a version; bytes per chunk at 384 and 768 dimensions for float32 and for int8 quantisation on the three 10k corpora's chunk counts (computed from recorded chunk counts, labelled as computed); how this sits with the D2 size work ([index-size](../index-size.md)).
5. **Surfaces.** What each interface would gain, stated as proposals: `apply` (JSON-RPC and C ABI), the query vector on `ss_query`, RPC and MCP, the CLI (a file of vectors, or nothing), Dart. Which are additive, which need a contracts minor version, and whether the direct `search` command stays lexical only.
6. **What is measured before it is called done.** A judged set with a semantic slice (what J2 has and lacks), the expected read and write cost, memory, and the bars a later build task would carry. The dependency-free native provider (the PPMI baseline) stays out of scope and is named as a later question.
7. **Open questions for the maintainer**, listed plainly, each with the orchestrator's recommendation.
8. **The document.** `docs/requirements/cap-NN-host-supplied-vectors.md` from the template, next free number, status **Proposed** (not approved: this one changes the wire and the C ABI, and the maintainer has not read it), registered so `check_requirements` passes; a 03-next row; one line in the plan's item E pointing at it. Every statement about today's code is checked against the code and cites it. No home paths; invented names only.
