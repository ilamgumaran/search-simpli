# S2-T5 · Durable publish on a phone: sync the directory, prune old generations

**State:** verified (2026-10-08, second round) · **Series:** S2 (research doc, learning 10) · **Depends on:** S1-T8 · **Size:** S · **Builder:** Sonnet 5 · **Tester:** Opus

We fsync each file but never the directory (`zig/src/publication.zig:113-121`):
after a power loss the `MANIFEST` rename may persist without the section
renames before it, and `ss_open` then fails closed until the next publish. We
also never delete superseded generations (`docs/incremental-indexing.md:151-153`);
the app republishes the whole index on every import, so its storage grows by
one full snapshot per import (about 16 MB per generation at 10,000 chunks).

## Acceptance criteria
1. The directory is fsynced after the section renames and again after the
   `MANIFEST` rename, in that order, on every publish path (folder index,
   import-json, incremental update). Windows/other platforms: say what the
   code does where a directory cannot be synced.
2. An opt-in option `"keep_generations": N` (N ≥ 1) on `ss_index_folder` and
   `ss_import_json` (and the CLI): after a successful publish, generation files
   older than the newest N are deleted, never the current one and never the
   control files; default unchanged (nothing deleted). Documented in the header
   and in `docs/generation-lifecycle.md` / `docs/publication-recovery.md`.
3. **Bar (a):** a test with a recording directory shim (or a bounded `dtruss`
   trace on macOS) shows the two directory syncs after the renames, in order.
4. **Bar (b):** publishing 20 generations of the 1k corpus with
   `keep_generations: 2` leaves exactly 2 generations' files plus the control
   files, and `lifecycle.scan` reports no orphans; with the option absent all
   20 remain.
5. **Bar (c):** index time changes by ≤ 5 % (best of five, 10k corpus).
6. **Bar (d):** the `SIGKILL` recovery run from S1-T3 is repeated and still
   recovers (say the command).
7. **Plants:** the sync test fails with the directory sync removed; the
   pruning test fails with the deletion removed.
8. All five suites green after the Report; libraries rebuilt last.

## Verdict (tester fills in)

**Rejected** (Opus tester, 2026-10-08). The directory syncs are there, in the right order, on every publish path, and pruning, the option and the docs largely check out. It is rejected for one defect in the new error path. If the **second** directory sync (after the `MANIFEST` rename) fails, `publish` returns the error and its `errdefer`s delete the two section files that the already-renamed `MANIFEST` names. The snapshot is then unreadable, which is the "`ss_open` fails closed until the next publish" state this task exists to remove, and it is reached deterministically on any `EIO`, not only after a power cut. The next `--update` makes it worse: it publishes an **empty** generation and exits 0 (below). Nothing was merged; `main` is unchanged at `67c2fb9`.

Setup: a detached worktree from `origin/main` (`67c2fb9`) with `origin/task/S2-T5` (`7275f95`) merged `--no-ff --no-commit` and no conflicts; `git merge-base origin/main origin/task/S2-T5` = `67c2fb9`. Pinned Zig 0.16.0 on PATH, NDK 28.2.13676358, `SEARCH_SIMPLI_LIBRARY_PATH` unset. `searchd` built ReleaseFast and ReleaseSmall from both trees into a scratch prefix (`<tmp>`). A `DYLD_INSERT_LIBRARIES` interposer (scratch, not committed) records the process's real `fsync` calls (file or directory, by `fstat`), `linkat`, `renameat` and `unlinkat`, and can make the N-th directory `fsync` fail with `EIO`.

### The blocking defect

The real calls, from my interposer, injecting `EIO` into a `searchd index small --out f --keep-generations 1` that publishes generation 3 over generations 1 and 2:

```
dir sync #1 fails:  ... linkat -> documents-3.hybseg, linkat -> lexical-3.hyblex, dir_sync #1 INJECTED FAILURE,
                    unlinkat lexical-3.hyblex, unlinkat documents-3.hybseg; error: InputOutput, exit 1
                    MANIFEST md5 unchanged (3008700758...), query "hybrid" still answers from generation 2   <- correct
dir sync #2 fails:  ... dir_sync r=0, renameat -> MANIFEST r=0, dir_sync #2 INJECTED FAILURE,
                    unlinkat lexical-3.hyblex, unlinkat documents-3.hybseg; error: InputOutput, exit 1
                    MANIFEST md5 changed (1ce1a9b5...) and names generation 3; ls: documents-1/2, lexical-1/2 only
                    searchd query -> error: FileNotFound                                                       <- broken
then --update:      {"generation":4,...,"changed":0,"unchanged":3,...,"documents":0,"terms":0,"postings":0}, exit 0
```

The cause is in `publishRecorded`: the two `errdefer dir.deleteFile(...)` are still armed when the final `try syncDirectory(...)` runs, after `MANIFEST` already names those files. `docs/publication-recovery.md` documents this as intended ("the usual error cleanup removes the section files this call created"). The empty generation 4 comes from older code that this path now reaches: `indexFolderIncremental` treats `FileNotFound` from `snapshot_open.open` as "no previous index" (`indexer.zig`, `previous_engine ... error.FileNotFound => null`). `INDEX-STATE.json` still marks every file unchanged, so no file is re-read and the update publishes zero documents. With `keep_generations` set, that empty publish then prunes the last good generation.

**Rework (exact):**
1. In `publication.publishRecorded`, disarm the section-file cleanup once the `MANIFEST` rename has succeeded, for example with a `manifest_visible` flag checked by the two `errdefer`s. A failed sync after that point must not delete anything `MANIFEST` names. Either return the error (the generation is visible but not known to be durable) or report it some other way, and say which in `docs/publication-recovery.md`. Fix that doc's "usual error cleanup" sentence to match.
2. Add a test that makes the second directory sync fail, for example a test-only fault hook beside the `Recorder`. It must assert that after the error `MANIFEST` and both sections it names are present and `loadCurrent` succeeds. Add a test that the first sync failing leaves `MANIFEST` byte-identical; the code already does this, but no test covers it.
3. Recommended in the same round, because this path now makes it reachable: `indexFolderIncremental` should not treat "`MANIFEST` exists but a section it names is missing" as "no previous index" while `INDEX-STATE.json` says files are unchanged. Fail, or drop the state and re-read every file. Otherwise one lost section turns the next `--update` into a silent empty publish.

Rebuild the libraries last, as before.
