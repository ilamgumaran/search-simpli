# S2-T5 · Durable publish on a phone: sync the directory, prune old generations

**State:** built · **Series:** S2 (research doc, learning 10) · **Depends on:** S1-T8 · **Size:** S · **Builder:** Sonnet 5 · **Tester:** Opus

We fsync each file but never the directory (`zig/src/publication.zig:113-121`):
after a power loss the `MANIFEST` rename may persist without the section
renames before it, and `ss_open` then fails closed until the next publish. We
also never delete superseded generations (`docs/incremental-indexing.md:151-153`);
the app republishes the whole index on every import, so its storage grows by
one full snapshot per import (about 16 MB per generation at 10,000 chunks).

## Acceptance criteria
1. The directory is fsynced after the section renames and again after the
   `MANIFEST` rename, in that order, on every publish path (folder index,
   import-json, incremental update). Windows/other platforms: say what the
   code does where a directory cannot be synced.
2. An opt-in option `"keep_generations": N` (N ≥ 1) on `ss_index_folder` and
   `ss_import_json` (and the CLI): after a successful publish, generation files
   older than the newest N are deleted, never the current one and never the
   control files; default unchanged (nothing deleted). Documented in the header
   and in `docs/generation-lifecycle.md` / `docs/publication-recovery.md`.
3. **Bar (a):** a test with a recording directory shim (or a bounded `dtruss`
   trace on macOS) shows the two directory syncs after the renames, in order.
4. **Bar (b):** publishing 20 generations of the 1k corpus with
   `keep_generations: 2` leaves exactly 2 generations' files plus the control
   files, and `lifecycle.scan` reports no orphans; with the option absent all
   20 remain.
5. **Bar (c):** index time changes by ≤ 5 % (best of five, 10k corpus).
6. **Bar (d):** the `SIGKILL` recovery run from S1-T3 is repeated and still
   recovers (say the command).
7. **Plants:** the sync test fails with the directory sync removed; the
   pruning test fails with the deletion removed.
8. All five suites green after the Report; libraries rebuilt last.

## Rulings on the Report (orchestrator, 2026-10-08)

Written before verification so the tester judges against them, not against
the criteria alone.

1. **`lifecycle.scan` split: accepted.** "Orphan" conflated two things that
   need different handling: files an update is *expected* to leave behind
   (older generations, kept until pruned) and files nothing should have left
   (a generation at or past the current one, odd names, no manifest). The
   split names them; the total of unreferenced files is unchanged; the scan
   has no consumer outside `zig/src` (no ABI function, nothing in the Dart or
   Python layers reads it). Conditions for the tester: `generation-lifecycle.md`
   defines both terms; the two edited assertions and the gen-7 case show the
   new meaning; the S1-T3/S1-T4 task files keep their old counts (history).
2. **`keep_generations` as a payload field: accepted** as a publication option
   carried in the interchange document, because `ss_import_json` has no options
   argument and a new ABI function would ripple into the bindings and the app
   for one integer. Conditions: the schema says it is an option, not snapshot
   content, and that a consumer that is not a publisher ignores it; it is
   optional; after S2-T1 lands (`analyzer_id` enum, contract 1.1.0) the two
   schema edits compose and the schema test covers a payload carrying both.
3. **`INDEX-STATE.json` not directory-synced: accepted.** Losing its rename
   costs one re-index on the next update and nothing else. The tester checks
   that `publication-recovery.md` says so.
4. **Shim instead of `dtruss`: accepted.** The bar said shim or trace. No
   power cut was performed; the Verdict says so plainly.
5. **Bar (c) was measured on `ReleaseFast`.** The tester re-measures on the
   shipped `ReleaseSmall` library as well; both must be within 5 %.
6. **Order of landing.** S2-T1 merges first. The builder merges `origin/main`
   after that, resolves `importer.zig`, `abi.zig`, the header, the schema and
   the bindings by hand, rebuilds the libraries last and re-runs the suites;
   only then does verification start.
