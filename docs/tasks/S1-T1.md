**State:** verified (round A, Thursday 17 Sep) · **Depends on:** ADR 0002 · **Size:** L · **Builder:** Sonnet 5 · **Tester:** Opus 5

## Acceptance criteria
1. `line-window-v1` chunker ported to Zig; golden test: chunk ids, line ranges, and bytes identical to the Python reference on every fixture and on `simpli-helper/packages/vizhi_core/test/fixtures/` text files (copied into `fixtures/` here, invented content only).

4. One static binary per platform (`macos-aarch64`, `linux-x86_64`) from `zig build -Doptimize=ReleaseSafe`; sizes and a 1,000-file timing pasted.
5. README gets a "Standalone" section (install nothing: download the binary, index a folder, query); tests green.

### What was built

- `zig/src/chunker.zig`: `line-window-v1` ported from
  `search_platform.core._line_chunks`/`_chunk_id`, operating on Unicode
  codepoints (matching Python's `len(str)` exactly; stricter than the
  existing Dart port in `simpli-helper`, which approximates with UTF-16
  code units and documents that as an unobserved-in-fixtures gap). Also
  ports Python's full `str.splitlines()` line-boundary set and
  `str.isspace()`-based `.strip()`, both generated from Python 3.9

  `scripts/gen_unicode_tables.py` from Python 3.9's `unicodedata`, Unicode

### Design decisions worth the tester's attention

- **`postings.zig`/`analysis.zig` untouched.** Rather than making the
  existing, already-tested ASCII postings builder/scorer generic over an
  analyzer (higher blast radius against S1-T0's parallel work and every
  existing postings/engine/service test), `analyzer-v2` gets its own
  additive builder/scorer (`lexical_build.zig`) that produces and consumes
  the *same* `postings.Index`/`TermEntry`/`Posting` wire types, so both
  analyzers persist through the identical `lexical_segment`
  encode/decode/manifest/publication path unchanged.
- **Term matching for `analyzer-v2` is plain byte equality**, not a
  case-fold comparator: both dictionary construction and query tokenization
  go through the same `analyzer_v2.tokenize` (NFC + casefold at extraction
  time), so nothing is left for a comparator to fold.
- **`analyzer-v1`'s new native path lowercases ASCII tokens at index time**
  (`indexer.tokenizeV1`) rather than leaving that to comparison time the way
  `analysis.zig` does — chosen so both analyzers could share one
  index-building function (`lexical_build.build`) instead of two.
- **Case folding is *simple* (one codepoint → one codepoint), not Python's
  *full* case folding** (e.g. German ß → "ss" is out of scope). Invisible on
  every fixture this task ships (English + Tamil; Tamil has no letter
  case). Documented in `analyzer_v2.zig`.
- **NFC excludes Hangul.** Documented in `nfc.zig`; not exercised by any
  fixture here.
- **`analyzer-v2` tokenization intentionally matches
  `search_platform.core.tokenize`'s existing behavior** of splitting Tamil
  text at combining marks (dependent vowel signs, virama — Unicode
  categories Mn/Mc), because Python's own `[^\W_]+` regex already does this
  (`\w` under `re.UNICODE` is alpha-or-decimal-or-digit-or-numeric, not
  mark-inclusive; verified interactively: `'்'.isalnum()` is `False`
  for the Tamil virama). This is not full grapheme-cluster-aware Indic
  tokenization; it is documented parity with the reference the BM25
  conformance test measures against.
- **`searchd index` snapshots are lexical-only** (`embedding_model_id`
  `"none"`); no vector/hybrid path here — out of this task's scope by the
  task description itself ("native indexing: chunker, Unicode analyzer,
  standalone CLI").

Checked both plain `x86_64-linux` (glibc) and `x86_64-linux-musl` directly
(`shasum -a256` on both outputs): both are the **same size** (5,293,344

differing only in embedded target/ABI metadata, not executable code.
`x86_64-linux-musl` is recorded above as the conventional, unambiguous way
to ask Zig for a static Linux binary; either target triple works equally
for this task's purposes.

### Non-blocking findings

1. **`searchd index` cannot re-publish into an output directory that already
   holds that generation.** It fails with a bare `error: PathAlreadyExists`,
   exit 1, and no guidance. Running the README's own first command a second
   time fails; `--generation 2` works. The failure happens at the final
   `publishSerialized` step, *after* all the walking, chunking and tokenizing —
   which is why the Report's and README's "warm" runs 2 and 3 are in fact these
   failures, and why their 0.08 s figures nonetheless reproduce exactly on a
   genuine warm run into a fresh directory (tester-measured 0.16 / 0.08 /
   0.08 s). **The numbers are right; the two timing tables' claim that these
   were three successful index runs is not.** The Report and the README should
   say so, and S1-T3 (incremental folder indexing) is the natural place to make
   re-indexing work.

2. **Indexing cost is superlinear in vocabulary size, and the committed timing
   corpus hides it.** `lexical_build.build` scans the whole term list linearly
   for every document term (O(unique terms × total tokens)).
   `scripts/gen_timing_corpus.py` draws from a ~30-word vocabulary, so the
   1,000-file corpus has **57 terms** — which is why it indexes in 0.08 s.
   Tester-measured on the same 1,000 files / 3.9 MB with a realistic 20,000-word
   vocabulary: **9.69 s** (19,992 terms, 416,201 postings) — **36× slower**.
   Indexing this repository itself (202 files, 1,239 chunks, 13,297 terms):
   0.77 s. A hash map here before the CLI meets a real corpus.

3. **Case folding is simple, not full** (disclosed in the Report and in
   `analyzer_v2.zig`), with one consequence worth calling out beyond ß and the
   ligatures: **`İ` (U+0130) is not folded at all**, not even lowercased,
   because its casefold is two codepoints and the generator keeps only
   single-codepoint pairs. `İstanbul` and `istanbul` are different terms.

4. **`scripts/gen_bm25_golden.py` is not byte-reproducible.** Three
   consecutive runs produced three different files (md5s differ), varying in
   the last ULP of two `lexical_score` values, because the Python reference's
   BM25 accumulation order depends on dict/set iteration order. The committed
   fixture matches `PYTHONHASHSEED=0`. The Zig test's 1e-4 tolerance absorbs
   it, so nothing fails — but the script should pin the seed so "regenerate and
   diff" is a meaningful check. (`gen_chunk_golden.py` and
   `gen_unicode_tables.py` are byte-reproducible; verified.)

5. **The BM25 conformance test only asserts top-1**, not the full ranking. The
   Report says "identical top-1", so this is disclosed, not hidden; the tester
   verified the stronger property by hand (36/36 full rankings). Worth widening
   the committed test to the whole list.

6. **File ordering differs subtly from the Python reference.**
   `_iter_text_files` sorts `Path` objects component-wise; `indexer.zig` sorts
   relative-path bytes. These disagree when a file and a directory share a
   prefix (`a.md` vs `a/b.md`), which would permute `document_index` and so
   change tie-breaking. No fixture triggers it today.

7. **`fixtures/tamil/judgments.json` is itself indexed** by the Tamil run
   (disclosed) and ranks #2 on most judged queries, since it literally contains
   the query strings. The judged passage still wins all ten, but the corpus
   would be cleaner if the CLI were pointed at `fixtures/tamil/passages`.

8. **`zig build test` prints a spurious `failed command: … --listen=-` line**
   on every run, because the two conformance tests write their counts with
   `std.debug.print` through the build runner's listen protocol. Exit code is
   0 and the summary reads `77/77 tests passed` (disclosed by the builder), but
   it reads like a failure to anyone new.

9. **Linux binary cross-compiled but never executed** (disclosed) — this
   machine is macOS. `file` confirms it is statically linked; its behaviour is
   unproven.
