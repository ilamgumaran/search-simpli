# S1-T1 · Native indexing: chunker, Unicode analyzer, standalone CLI

**State:** built (round A, alongside S1-T0) · **Depends on:** ADR 0002 · **Size:** L · **Builder:** Sonnet 5 · **Tester:** Opus 5

## Acceptance criteria
1. `line-window-v1` chunker ported to Zig; golden test: chunk ids, line ranges, and bytes identical to the Python reference on every fixture and on `simpli-helper/packages/vizhi_core/test/fixtures/` text files (copied into `fixtures/` here, invented content only).
2. `analyzer-v2`: Unicode-aware tokenization (NFC, case folding, letters/digits by Unicode category, no ASCII-only paths), recorded as the analyzer id in segments; the ASCII analyzer stays available as `analyzer-v1`; a Tamil fixture folder (≥ 10 invented short passages) with judged queries proves Tamil works end to end; BM25 results identical between Python and Zig for both analyzers.
3. `searchd index <folder> --out <dir>` indexes UTF-8 text/markdown/source files natively (no Python), `searchd query <dir> "<text>" [--json]`, `searchd evidence`, `searchd serve <dir>` (existing JSON-RPC over stdio, plus `--http 127.0.0.1:<port>` local only); `--help` for a stranger.
4. One static binary per platform (`macos-aarch64`, `linux-x86_64`) from `zig build -Doptimize=ReleaseSafe`; sizes and a 1,000-file timing pasted.
5. README gets a "Standalone" section (install nothing: download the binary, index a folder, query); tests green.

### What was built

- `zig/src/chunker.zig`: `line-window-v1` ported from
  `search_platform.core._line_chunks`/`_chunk_id`, operating on Unicode
  codepoints (matching Python's `len(str)` exactly; stricter than the
  existing Dart port in `simpli-helper`, which approximates with UTF-16
  code units and documents that as an unobserved-in-fixtures gap). Also
  ports Python's full `str.splitlines()` line-boundary set and
  `str.isspace()`-based `.strip()`, both generated from Python 3.9
  interactively rather than guessed.
- Unicode data and NFC (`zig/src/unicode_tables.zig`, generated by
  `scripts/gen_unicode_tables.py` from Python 3.9's `unicodedata`, Unicode
  **13.0.0** — recorded in the generated file's header and as
  `unicode_tables.unicode_version`; documented because Zig 0.16.0's
  `std.unicode` carries no category/case-fold/normalization data of its own,
  verified directly against the pinned toolchain's `lib/std/unicode.zig`)
  and `zig/src/nfc.zig` (full UAX #15 decompose/canonical-order/compose,
  with Hangul syllables excluded from the generated tables since Hangul
  (de)composition is algorithmic, not table-driven, in the Unicode Standard
  — documented limitation, not exercised by any fixture here).
- `zig/src/analyzer_v2.zig`: `analyzer-v2` (NFC + Unicode letter/digit
  categories Lu/Ll/Lt/Lm/Lo/Nd/Nl/No + simple per-codepoint case folding).
  `zig/src/analysis.zig` (ASCII, `analyzer-v1`'s tokenizer) is untouched.
- `zig/src/lexical_build.zig`: an additive, analyzer-generic
  `postings.Index` builder from pre-tokenized documents. `postings.zig`
  itself is untouched (its hot, already-tested ASCII path stays exactly as
  it was), which keeps this task's changes additive rather than a risky
  generic rewrite of shared, already-tested code.
- `zig/src/indexer.zig`: native folder walk → chunk → tokenize → publish,
  no Python involved; extension allow-list and ignored-directory set mirror
  `search_platform.core.DEFAULT_EXTENSIONS`/`IGNORED_DIRECTORIES` exactly.
- `zig/src/engine.zig`: `Engine.queryTokenized` dispatches query
  tokenization by the snapshot's `analyzer_id` — the ASCII path for
  `analyzer-v1` and legacy `ascii-alnum-v1`/`ascii-v1` snapshots is
  `Engine.query`, unchanged; `analyzer-v2` snapshots get
  `analyzer_v2.tokenize` + `lexical_build.scoreQuery`. `Service.searchKnowledge`
  (`service.zig`) and RPC `search_knowledge` (`rpc.zig`) now call
  `queryTokenized` too (threaded an `allocator` parameter through both), so
  `searchd serve` — stdio and `--http` alike — is analyzer-aware, not only
  the new `query`/`evidence` CLI commands.
- `zig/src/cli.zig`, `zig/src/snapshot_open.zig`, `zig/src/main.zig`:

### Design decisions worth the tester's attention

- **`postings.zig`/`analysis.zig` untouched.** Rather than making the
  existing, already-tested ASCII postings builder/scorer generic over an
  analyzer (higher blast radius against S1-T0's parallel work and every
  existing postings/engine/service test), `analyzer-v2` gets its own
  additive builder/scorer (`lexical_build.zig`) that produces and consumes
  the *same* `postings.Index`/`TermEntry`/`Posting` wire types, so both
  analyzers persist through the identical `lexical_segment`
  encode/decode/manifest/publication path unchanged.
- **Term matching for `analyzer-v2` is plain byte equality**, not a
  case-fold comparator: both dictionary construction and query tokenization
  go through the same `analyzer_v2.tokenize` (NFC + casefold at extraction
  time), so nothing is left for a comparator to fold.
- **`analyzer-v1`'s new native path lowercases ASCII tokens at index time**
  (`indexer.tokenizeV1`) rather than leaving that to comparison time the way
  `analysis.zig` does — chosen so both analyzers could share one
  index-building function (`lexical_build.build`) instead of two.
- **Case folding is *simple* (one codepoint → one codepoint), not Python's
  *full* case folding** (e.g. German ß → "ss" is out of scope). Invisible on
  every fixture this task ships (English + Tamil; Tamil has no letter
  case). Documented in `analyzer_v2.zig`.
- **NFC excludes Hangul.** Documented in `nfc.zig`; not exercised by any
  fixture here.
- **`analyzer-v2` tokenization intentionally matches
  `search_platform.core.tokenize`'s existing behavior** of splitting Tamil
  text at combining marks (dependent vowel signs, virama — Unicode
  categories Mn/Mc), because Python's own `[^\W_]+` regex already does this
  (`\w` under `re.UNICODE` is alpha-or-decimal-or-digit-or-numeric, not
  mark-inclusive; verified interactively: `'்'.isalnum()` is `False`
  for the Tamil virama). This is not full grapheme-cluster-aware Indic
  tokenization; it is documented parity with the reference the BM25
  conformance test measures against.
- **`searchd index` snapshots are lexical-only** (`embedding_model_id`
  `"none"`); no vector/hybrid path here — out of this task's scope by the
  task description itself ("native indexing: chunker, Unicode analyzer,
  standalone CLI").

### Binary sizes (criterion 4)

Built with `zig build -Doptimize=ReleaseSafe -Dtarget=<triple> -p
dist/<platform>` from the pinned toolchain (no sysroot needed for either
target, per ADR 0002):

| Platform | Target triple | Size |
|---|---|---|
| macOS (Apple Silicon, this machine's native target) | `aarch64-macos` | 851,080 bytes (0.81 MiB; seen ±32 bytes between rebuilds, presumably build-metadata) |
| Linux x86_64 | `x86_64-linux-musl` | 5,293,344 bytes (5.05 MiB) |

Checked both plain `x86_64-linux` (glibc) and `x86_64-linux-musl` directly
(`shasum -a256` on both outputs): both are the **same size** (5,293,344
bytes) and `file` reports both "statically linked" with no dynamic
dependencies -- this binary calls no libc functions at all (nothing in
`zig/build.zig`/`main.zig` requests or uses one), so the static-vs-dynamic
outcome does not depend on glibc vs musl here. The two builds are **not**
byte-identical though (different SHA-256: `0743942a...` for plain
`x86_64-linux` vs `d435d2a9...` for `x86_64-linux-musl`), evidently
differing only in embedded target/ABI metadata, not executable code.
`x86_64-linux-musl` is recorded above as the conventional, unambiguous way
to ask Zig for a static Linux binary; either target triple works equally
for this task's purposes.

### Not done / scoped out (no silent narrowing)

- **Linux binary not run natively** (see above) — only cross-compiled and
  statically-linked-verified from macOS.
- **`searchd index` produces lexical-only snapshots** (no vectors); the
  task description scopes this task to chunker/analyzer/CLI, not
  vector/hybrid indexing.
- **Case folding is simple, not full** (documented above and in
  `analyzer_v2.zig`); **NFC excludes Hangul** (documented above and in
  `nfc.zig`). Neither is exercised by any fixture here.
- **`analyzer-v1`'s new native tokenizer lowercases ASCII only**; it does
  not attempt any Unicode awareness (by design — it is the ASCII analyzer).
- Bindings, incremental folder indexing, and the C ABI are separate tasks
  (S1-T0 and later in ADR 0002's plan) and are untouched here.
