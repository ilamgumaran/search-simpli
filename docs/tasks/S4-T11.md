# S4-T11 · One changed file: the lexical merge carries the previous postings instead of rebuilding them, and the source encode carries each unchanged file's record

**State:** ready (starts from `main` after the S4-T10 merge, `6c68370`) · **Date:** 2026-11-06 · **Depends on:** S4-T4 (the stage profile and `scripts/s4t4_budgets.py`), S4-T10 (the writer's source path) · **Size:** M

**Owner:** the Xcode Mac orchestrator · **Orchestrator:** Claude Fable 5.1 · **Builder:** Claude Opus 5.5 (local) · **Verifier:** Claude Opus 5.5 (local, a different agent)

**Why.** NFR-12 (`apply_changes` of one changed file in a 10k index ≤ 200 ms, `ReleaseSmall`) is met: S4-T4's profile on the 10k timing corpus measured 123.2 ms with the filename channel off and 141.6 ms on (p50 of five; S4-T10's verifier saw 123.4–124.5 off on `main` before its change). On a phone that cost is paid on the device at every save, so the "Ready to build now" row *Writer path after S4-T4: the lexical build and the section encode* in `docs/journey/03-next.md` names where the rest goes: of the 123 ms, **the lexical build is 33.5–34.3 ms** and **the encode of the documents, lexical and source sections 36.1–36.9 ms**, both a full rebuild for one changed file. Today `apply.zig`'s `buildPositionalMerged` avoids re-tokenizing a carried document, but it does so by **transposing the whole previous section 4** into one (term, ordinal) pair per token of the previous corpus (8 B each, scratch), appending every pair as an occurrence beside the fresh documents' tokens, ranking the dictionary, counting-sorting every occurrence term-major and **re-encoding every posting's ordinals as varints**: the work is proportional to the corpus, not to the change. `source.encode` **re-hashes every retained file with SHA-256 and re-scans its line starts** at every generation, although a carried file's bytes, digest, line map and encoding flag are exactly the previous section's record. The delta-sections row (S4-T1 candidate (b)) would change the format to reach the same end; this task reaches most of it **without touching the format**: the sections a generation writes stay **byte-identical to a fresh positional build**, which is already the invariant `apply_test.zig` asserts ("a generation carrying unchanged documents has the lexical section a fresh positional build gives"), so every reader, every contract (2.2.0), the analyzer and every result are unchanged, and nothing is rebuilt on any phone.

## Rulings
1. **Profile first, in the Report, before any change.** On S4-T1's 10k timing corpus (`scripts/gen_timing_corpus.py <dir> 10000`, `corpus_matches_recorded: true`), `ReleaseSmall`, filename off and on, one changed file (`group-00/doc-00000.md` plus one line, a fresh copy of the index per run, as `scripts/s4t4_budgets.py profile` does), five runs, p50 and worst, load stated: the S4-T4 stage table for `main` at `6c68370` from this branch's build of it, **with `build_lexical` split** into the transposition of the previous section 4, the occurrence and dictionary pass, the term-major layout, and the postings-plus-positions encode, **and `encode_sections` split** into the documents section, the lexical section and the source section (the source split again into line maps, SHA-256 and the copy). The sub-stages go under the existing `SEARCH_SIMPLI_APPLY_STAGES` variable (`Stages`, `apply.zig`) and stay if `scripts/s4t4_budgets.py profile` prints them without harm (extend it if a new name breaks it); the Report's table has before and after per sub-stage.
2. **The lexical merge carries.** `buildPositionalMerged` no longer transposes the previous section 4 or re-sorts the previous corpus's occurrences. For a generation with carried documents it builds, from the previous `postings.Index` the writer already holds (decoded at the open of the previous generation) and the fresh documents' positioned tokens: (a) the document map, previous index → new index or removed, from `sources`; (b) the dictionary: every previous term that keeps at least one carried posting, merged by bytes with the fresh documents' terms, in the order `lexical_build.buildPositional` lays out; (c) per term, the carried postings with their document index remapped and their `term_frequency` unchanged, **their section-4 bytes copied verbatim** (a posting's ordinals are relative to its own document, independent of the document index), merged in new-document order with the fresh documents' postings built as today; (d) section 5: a carried document's offset table copied as today, fresh documents encoded as today; (e) `document_lengths` and `average_document_length` computed by the same expression as `buildPositional` (the same `f32` from the same integers). A previous generation without positions (`HYBLEX01`, `previous_positional` false) keeps today's fresh path. **The bar is bytes:** the existing `apply_test.zig` parity test keeps passing and gains cases, each comparing the written `lexical-N.hyblex` with a fresh `buildPositional` over the same documents' tokens: a changed file whose chunk count grows, one whose count shrinks, a deleted file, a rename (`moved_from`) to a path that sorts elsewhere, a term that disappears from the corpus, a new term sorting before every previous term and one sorting after every previous term, several changed files in one batch, the last file deleted (the empty generation), and a `HYBLEX01` previous generation (the fresh path). A seeded randomized test over the five-step fixture (`incremental_indexing_test.zig` or beside it) applies N random mutations (add, edit, delete, rename, several per round) and compares bytes with a fresh build after each round; the seed and N are printed. On the 10k corpus `scripts/s4t4_budgets.py budgets` (or a `scripts/s4t11_budgets.py` reusing it) compares the `lexical-N.hyblex` and `documents-N.hybseg` the update wrote with those a fresh `searchd index` of the mutated corpus writes, as it does today for the filename sections; if the documents section legitimately differs between a fresh index and an update (name the field and the reason), compare the lexical section and say so.
3. **The source encode carries each unchanged file's record.** `source.encode` (or a sibling the writer calls) takes, for a carried file, the previous section's record (digest, line-map bytes, encoding flag; the writer has the entry through `prev_source.find`) and copies it instead of hashing and scanning the bytes again; the text is still copied into the new section (one whole section per generation; `HYBSRC01` unchanged). A fresh or changed file is hashed and scanned as today. **Byte-identical** to today's `source.encode` over the same inputs: a test with carried and fresh files mixed, BOM and CRLF files included (the fixtures the source tests already use), compares the two encodings; the 10k compare of ruling 2 adds `source-N.hybsrc`. The reader's per-call SHA-256 check (S4-T10) is untouched. State where the previous section's bytes were validated before the writer trusts a record from it (the section checksum at the writer's open, or at first use: name the function).
4. **The bar.** On the 10k corpus, `ReleaseSmall`, interleaved rounds with `main`'s (`6c68370`) library and `searchd` built in a scratch worktree as *before*, load stated and below 3.0, filename off and on, five runs each, p50 and worst: (a) **`build_lexical` p50 ≤ 12 ms** (S4-T4: 33.5–34.3); (b) `encode_sections` p50 lower than before, the saving stated per sub-stage; (c) **one changed file p50 at least 20 ms below *before*'s in the same run, off and on**; (d) `ss_open` p50, the first query after a cold open, `find`, `search_knowledge`, a filename and a `both` query p50 within 0.3 ms of *before* (no reader changed: this is the layout check S4-T10 found necessary); (e) the full 10k build (`searchd index`, no update) within 3 % of *before* (the fresh path is untouched); (f) parity: `scripts/capture_query_outputs.py` and `scripts/source_read_parity.py` byte-identical before and after over the family folder and the 10k corpus (the sections are byte-identical, so this must hold; the counts stated). The writer's peak live bytes at 10k before and after, if a `Capped`-allocator run of `apply_changes` is cheap to add beside `nfr13_arena_test.zig`'s machinery, as information (the transposition's scratch, 8 B per previous token, is gone); otherwise say "not measured".
