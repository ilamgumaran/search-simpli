# S4-T11 · One changed file: the lexical merge carries the previous postings instead of rebuilding them, and the source encode carries each unchanged file's record

**State:** ready (starts from `main` after the S4-T10 merge, `6c68370`) · **Date:** 2026-11-06 · **Depends on:** S4-T4 (the stage profile and `scripts/s4t4_budgets.py`), S4-T10 (the writer's source path) · **Size:** M

**Why.** NFR-12 (`apply_changes` of one changed file in a 10k index ≤ 200 ms, `ReleaseSmall`) is met: S4-T4's profile on the 10k timing corpus measured 123.2 ms with the filename channel off and 141.6 ms on (p50 of five; S4-T10's verifier saw 123.4–124.5 off on `main` before its change). On a phone that cost is paid on the device at every save, so the "Ready to build now" row *Writer path after S4-T4: the lexical build and the section encode* in `docs/journey/03-next.md` names where the rest goes: of the 123 ms, **the lexical build is 33.5–34.3 ms** and **the encode of the documents, lexical and source sections 36.1–36.9 ms**, both a full rebuild for one changed file. Today `apply.zig`'s `buildPositionalMerged` avoids re-tokenizing a carried document, but it does so by **transposing the whole previous section 4** into one (term, ordinal) pair per token of the previous corpus (8 B each, scratch), appending every pair as an occurrence beside the fresh documents' tokens, ranking the dictionary, counting-sorting every occurrence term-major and **re-encoding every posting's ordinals as varints**: the work is proportional to the corpus, not to the change. `source.encode` **re-hashes every retained file with SHA-256 and re-scans its line starts** at every generation, although a carried file's bytes, digest, line map and encoding flag are exactly the previous section's record. The delta-sections row (S4-T1 candidate (b)) would change the format to reach the same end; this task reaches most of it **without touching the format**: the sections a generation writes stay **byte-identical to a fresh positional build**, which is already the invariant `apply_test.zig` asserts ("a generation carrying unchanged documents has the lexical section a fresh positional build gives"), so every reader, every contract (2.2.0), the analyzer and every result are unchanged, and nothing is rebuilt on any phone.

### Ruling 2: the lexical merge carries

`buildPositionalMerged(allocator, previous, sources, stages)` (`apply.zig`) no longer
transposes section 4 or re-sorts the previous corpus. With no carried source it calls
`buildPositionalFresh` (today's code with the transposition removed: every source
fresh, as for a full build and for a `HYBLEX01` previous generation); with any carried
source it calls `mergeCarried` over the previous `postings.Index` the writer decoded at
`openPrevious` (a carried source with no previous index is
`error.InvalidLexicalSection`):

- (a) **`build_lexical.map`**: `new_of_old` (previous index → new index or none; a
  previous document carried twice is an error), `new_of_fresh`, the fresh sources,
  `document_lengths` and the total. `average_document_length` is `buildPositional`'s
  expression, `@as(f32, total) / @as(f32, count)`, from the same integers.
- (b) **`build_lexical.fresh`**: `buildPositionalFresh` over the fresh documents only
  (in a scratch arena): their dictionary, postings, section 4 and section 5, built as
  today.
- (c) **`build_lexical.merge`**: one walk over the previous and the fresh dictionary by
  `std.mem.order` on the term bytes, the order `buildPositional` lays out. A fresh-only
  term: its postings with remapped indices, its section-4 run copied. A previous term:
  every posting whose document is kept, its `document` remapped, `term_frequency`
  unchanged, **its section-4 bytes copied verbatim**; a previous term with no kept
  posting is dropped. When every posting of a previous term is kept in increasing new
  order and no fresh posting joins it (almost every term of one changed file), its
  whole section-4 run is one copy; otherwise the kept postings are sorted by new index
  when a rename broke the order and merged with the fresh postings by document, each
  posting's bytes found by skipping its `term_frequency` varints. Consecutive copies
  that are adjacent in the source coalesce (`ByteSink`), so "copied as one byte run"
  holds for section 4 only, as ruled. At the end the walk must have consumed both
  section 4s exactly (Debug assert plus `error.InvalidLexicalSection`).
- (d) **`build_lexical.offsets`**: section 5 per new document: a carried document's
  table copied from the previous section (each table's start found by skipping its
  `2 × length` varints; the walk must end exactly at the section's end, Debug assert
  plus error), a fresh document's from (b).
- (e) The output slices are allocated at their upper bounds from the writer's arena and
  trimmed.

The varint skip (`source.varintsEnd`, merge note (b)) counts end bytes (< 0x80) sixteen
at a time with `@Vector` and `@popCount` and finishes byte by byte; it returns null, and
the writer `error.InvalidLexicalSection`, when the section ends before the count it
must yield. Varint bytes are copied, never decoded and re-encoded, so a carried
posting's bytes are the previous generation's bytes, which were a fresh build's bytes:

### Ruling 3: the source encode carries each unchanged file's record

`source.InputFile` gains `carried: ?Carried` (digest, line count, line-map bytes,
encoding byte, `bytes_from_section`); `source.carriedRecord(entry, from_section)` builds
it from a `prev_source.find` entry. `buildGeneration` sets it for a file the scan did
not re-read as fresh when the previous section has its record: if the scan read the
bytes, only when their length equals the record's and their SHA-256 hex (from the scan)
equals the record's digest; if it did not read them, the bytes are the section's own
copy. `source.encode` is now `encodeMarked(…, NoMarks{})`; `encodeMarked` takes the
carried digest, line map and encoding byte instead of hashing and scanning, copies the
text as before (one whole `HYBSRC01` section per generation, format unchanged), and
hashes and scans a fresh or changed file as today. The writer's call is
`encodeMarked(…, SourceMarks)` for the sub-stages.

Two choices the plan asked to have ruled (ruled at the plan):

- **UTF-8.** The UTF-8 check is skipped only when the bytes **are** the previous
  section's own copy (`bytes_from_section`), which `openWith` validated at the writer's
  open. A file carried by a length-and-hash match (bytes re-read from disk) is UTF-8
  checked as today; the source test checks that a re-read file with bad UTF-8 still
  answers `error.InvalidUtf8`.
- **The digest is trusted, not recomputed.** Where the previous section is validated
  before the writer trusts a record: `apply.openPrevious` → `source.openIndexed` →
  `openWith`, which runs `inspect` (the XXH3 section checksum against the header) and
  `validateLineMap` (each file's line map and encoding byte against its bytes); then
  `openPrevious` compares the section's checksum with the MANIFEST's `source_checksum`.
  The record's SHA-256 is covered by the section checksum, so a damaged digest fails the
  open (and the update falls back as today); it is not recomputed. That is sound
  because the digest was computed from the same bytes when the section was written, the
  bytes it describes are copied with it, and a later divergence between the two is still
  caught at every read by the reader's per-call SHA-256 check (S4-T10), which is
  untouched.

`buildGeneration` also gains a `carried_once` bit set over previous documents: if a
batch would carry the same previous document twice (two paths claiming one record),
the second is re-tokenized as fresh instead of failing the merge (deviation 6).

**Tests.** `source.zig`, "S4-T11 ruling 3: carried records encode byte for byte as the

### Findings of my own

1. **The merge's end-of-walk check is a Debug panic and, in `ReleaseSmall`, no check at
   all.** `mergeCarried` ends with `std.debug.assert(cursor == sections.positions.len and
   …); if (cursor != … ) return error.InvalidLexicalSection;` and `offsetTableStarts` with
   the same pattern. In Debug the assert panics ("reached unreachable code") before the
   return; in `ReleaseSmall` the assert is an `unreachable` the optimizer may assume, and
   it did: plant D2's `mergeCarried` returned an index with the left-over byte dropped.
   Nothing reaches it from a file: `lexical_segment.decode` refuses any section 4 with a
   byte left over (`InvalidPositions`, plant D) before the merge runs, and the writer's
   own `validateIndex` checks the merged index before it is encoded (plant 1). The
   update is safe in every build; the Report's and ruling D's "refused with
   `InvalidLexicalSection`" is true only of the `skipVarintsChecked` paths (a section that
   ends early), not of the end-of-walk checks. A later writer change could drop the two
   asserts so the returns stand; not a bar of this task, and I changed no code.
2. **`openWith` does not check UTF-8.** It checks the section checksum and every line map
   (`validateLineMap`: line starts and the BOM byte), not that the bytes are valid UTF-8.
   For bytes that are the previous section's own copy the UTF-8 verdict carried is the
   verdict of the encode that wrote that section, protected by its checksum, as ruling B
   accepted; the Report's "which `openWith` validated at the writer's open" should be read
   that way.
3. **The first `read_span` after a cold open is bimodal, near 8.3 or 9.8 ms, in both
   builds.** Over my 20 rounds (runs A to E; D and E, filename off, six rounds each, E with
   the after library run first in each round, loads 1.53–1.89) before's p50 per round has
   median 9.06 ms (8.27–9.79, 9 of 20 below 9 ms) and after's 9.77 (8.39–9.80, 3 of 20
   below 9 ms); both modes appear with both libraries and with either library first. It
   is not in ruling 4(d)'s list (no reader changed; S4-T10 measured 9.08–9.80 ms after its
   change, within its +5 ms bar), so it does not decide this Verdict; a change that touches
   the source reader should re-measure it with more rounds.
4. **Two stale sentences corrected in this commit (documentation only):**
   `docs/incremental-indexing.md` "What this is not" still said "The lexical index is
   rebuilt whole every generation"; `docs/lexical-segment-format-v2.md` "`--update`"
   still named `lexical_build.reconstructPositioned` (no writer calls it; only its own
   test). Both now say what S4-T11 carries.
5. **The randomized test is not over the five-step fixture**, as ruling 2 and the Report
   say: it starts from six random files of a 30-word vocabulary (Tamil, Hangul, accents
   and digits among them) and updates through `indexer.indexFolderIncremental` (the
   `searchd index --update` path; a rename is a write plus a delete). It is a broader test than the fixture would give;
   named here, not a failure.
