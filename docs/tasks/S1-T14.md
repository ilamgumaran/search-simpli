# S1-T14 · analyzer-v2 splits Tamil words at vowel signs

**State:** ready (2026-10-10) · **Series:** S1 · **Depends on:** S2-T1 (analyzer-v2 reaches `ss_import_json`) · **Size:** S · **Builder:** Sonnet 5.5 · **Tester:** Opus 5.5

**Found by simpli-helper's M12-T7 tester (10 Oct), with real input.** `analyzer-v2` tokenizes "letters and digits by Unicode category", so a Tamil word is cut at its vowel signs (category Mc/Mn): `கணினி` becomes `கண` and `ன`; an absent `யானைகள்` matched 8 of 12 passages on one-letter fragments. The Tamil fixture's judged queries are single distinctive words, so the bar in S1-T1 and S2-T1 could not see it. This is a correctness defect in Tamil search, and in every script that writes vowels as combining marks (Devanagari, Bengali, Thai, …).

## Rulings
- A token is a run of **letters, digits, and the marks attached to them** (Unicode categories L*, N*, **Mn, Mc**, plus ZWJ/ZWNJ U+200D/U+200C inside a run), so a Tamil word stays whole. Equivalent: split on Unicode word boundaries (UAX #29) rather than on category L/N alone; either implementation is acceptable if the tests below pass and ASCII behaviour is byte-identical.
- The analyzer id stays `analyzer-v2` **only if** every existing golden (chunk, BM25, conformance, the 36 and 814 ranked lists) is byte-identical for ASCII and the Latin-with-accents cases; the Tamil goldens are regenerated and the change is recorded. If any ASCII golden moves, stop: that is a decision (a new `analyzer-v3`) for the orchestrator.

## Acceptance criteria
1. Tokenization tests, Zig and Python reference alike: `கணினி` → one token; `யானைகள்` → one token; `நான் வீட்டிற்கு போகிறேன்` → three tokens; a Devanagari word with a vowel sign (`किताब`) → one token; `café` → one; `x-ray` → `x`, `ray` (unchanged); ASCII fixtures byte-identical.
2. **Bar, written first:** a new Tamil judged set of ≥10 queries where the query word is **absent** from the corpus must score 0 hits on the branch (today: fragments match); the existing Tamil set still scores success@1 1.00; paste both before and after.
3. Python reference and Zig agree on every fixture (the conformance harness); the Dart package's conformance test still 10/10 identical for Tamil.
4. `ss_import_json` and `searchd index` both carry the fix (one analyzer implementation); libraries rebuilt and `native/SOURCE-SHA256` re-stamped via `tool/build_native.sh` last; sizes and sha256 pasted; `CONTRACTS_VERSION` unchanged unless ruled otherwise.
5. All five suites green after the Report; tails pasted; paths redacted.

### Findings (none blocking)
1. **Zig's NFC is incomplete, and Python's new NFC step makes that visible.** `scripts/gen_unicode_tables.py` line 112 drops singleton canonical decompositions; its comment ("do not affect NFC recomposition") is wrong. `nfc.zig` also documents that it does not recompose Hangul. Before this task Python had no NFC, so the two agreed on those characters by accident.
   - **Effect now:** Zig and Python differ on 1,020 more codepoints, all singletons (1,002 CJK compatibility ideographs and 18 Greek/combining). They also differ on all 11,172 Hangul syllables written decomposed.
   - **In exchange:** 76 codepoints agree that did not, and decomposed non-Hangul text agrees on 1,933 of 2,061 characters instead of 1,199.
   - **Not affected:** no fixture, and nothing the app runs. The app uses only Zig.
   - **Needs its own task.** Either give Zig full NFC (singletons plus algorithmic Hangul), or make the Python reference match Zig. Full NFC in Zig changes Zig's terms for those characters, so the orchestrator should rule whether that change can stay `analyzer-v2`.
2. **A code comment claims too much.** `analyzer_v2.zig` says "ASCII and Latin text has no Mn/Mc after NFC … so its tokens are unchanged". That holds for ASCII and precomposable Latin, as verified above. It does not hold for Latin whose marks have no precomposed form: Yorùbá `ọ̀rọ̀`, Lithuanian `ą̃`, IPA, and strikethrough styling with U+0336. Those tokens change, as ruling 1 intends. No golden contains such text. I left the comment as it is: it is code.
3. **Variation selectors are Mn, so they now stay on a token.** The keycap `1️⃣` gives the token `1`+U+FE0F, so a query for `1` no longer finds it; `x`+U+FE0F+`y` becomes one token. A small follow-up could drop default-ignorable marks (U+FE00–FE0F, U+E0100–E01EF) in both implementations.
4. **Thai, Khmer and Chinese stay one run: acceptable for this task, but a separate task before any claim of support.** This task is the split-at-marks defect. Chinese was already one run before the change. Thai and Khmer go from fragments (which matched noise) to whole runs (which match only an identical run), so precision rises and recall falls: `ภาษาไทย` does not find `ฉันรักภาษาไทย`. Segmenting them needs a dictionary or n-grams and its own judged bar. Schedule it only if the family's text includes these scripts.
5. **Tamil now matches exact forms only.** `யானைகள்` does not find `யானை`, and `நூலகங்கள்` does not find `நூலகம்`. The bar requires this, but the app should know that a Tamil query must use the form that is in the text. Stemming or prefix matching would be a research task.
6. **`import_parity.py` still generates queries with the old `[^\W_]+` pattern.** 38 of its 48 Tamil door-parity queries are now fragments that match nothing: 10 ranked results compared, against 278 on main. The script should take its words from `core.tokenize`. That is a harness change; I did not make it, and my own both-door check covers the gap.
7. **The hand-over's counts are out of date.** The ABI harness is `16/16` since S2-T11, the same on main. The committed BM25 conformance compares 26 top-1 queries. "36/36" was S1-T1's tester's own full-ranking run, which I redid above with 48 queries.
8. **A snapshot published by the previous library becomes stale for marked scripts, and nothing detects it.** The id stays `analyzer-v2` (ruling 2), so a snapshot indexed with fragments is now queried with whole words. I indexed the Tamil fixture with main's `searchd` and queried it with the merge's: **success@1 0/10, 0 hits**; on main it was 1.00. ASCII and precomposed-Latin snapshots are byte-identical, so they are unaffected. **The app must republish every snapshot once after it re-pins.** Until it does, Tamil search returns nothing, which is worse than the noisy results before. If silent staleness is not acceptable, the orchestrator could record an analyzer revision in the `MANIFEST` so the library can tell a stale snapshot from a current one. That would be its own ruling and task.
