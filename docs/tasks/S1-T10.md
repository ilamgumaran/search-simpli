# S1-T10 · The Dart package finds its library inside a built macOS app bundle

**State:** verified (2026-10-08; ready 2026-10-08) · **Series:** S1 (the Xcode Mac's) · **Depends on:** S1-T8 · **Size:** S · **Builder:** Sonnet 5.5 · **Tester:** Opus 5.5
**Why now:** the family app's macOS runner (simpli-helper M7-T1) runs under the app sandbox, where `lib/src/library_loader.dart` finds nothing: the package-config lookup needs a `.dart_tool/` that a built app does not have, and the cwd and script-relative fallbacks point outside the bundle. M7-T1 works around it with a test-only copy into the app container; M7-T2 cannot ship until this task lands (simpli-helper ADR-011 decision 10).

## Acceptance criteria
1. **Bundled-app lookup, tried first on macOS.** Before the existing candidates, `openSearchSimpliLibrary()` tries, in this order: (a) `DynamicLibrary.open('libsearch_simpli.dylib')` by bare name, which resolves through the loader's search path and `@rpath` when the app bundles the library in `Contents/Frameworks` (the way `whisper_ffi.dart` in the app already does, `packages/vizhi_core/lib/src/speech/whisper_ffi.dart:131-158`); (b) `<executable dir>/../Frameworks/libsearch_simpli.dylib` from `Platform.resolvedExecutable`. Then the present candidates, unchanged in order. Linux gains the same two steps with `libsearch_simpli.so` and `<executable dir>/lib/`. Android and the `SEARCH_SIMPLI_LIBRARY_PATH` override are untouched, and the override still wins over everything.
2. **A failed candidate never masks a later one.** `DynamicLibrary.open` throws `ArgumentError` for a missing file; each candidate is tried in turn and the final `StateError` lists every path tried, including the two new ones, in the order tried. The existing message's advice stays.
3. **Proof in a real bundle, not a unit test only.** A throwaway macOS Flutter app (in a temp directory, `flutter create --platforms macos`, path dependency on this package, `libsearch_simpli.dylib` copied into `Contents/Frameworks` by a build step or by hand after `flutter build macos --debug`, and `SEARCH_SIMPLI_LIBRARY_PATH` **unset**) opens the demo snapshot and answers one query **from inside the built `.app`**, launched by double-click semantics (`open` or running the executable from `Contents/MacOS`, cwd set to `/`). Paste the command, the cwd, and the answer. Then the same with the app-sandbox entitlement on, so the sandbox cannot be the thing that breaks it. The probe is scripted in `bindings/dart/search_simpli/tool/bundle_probe.sh` so the tester can re-run it; the temp app is not committed.
4. **Unit tests** for the candidate order (a fake opener that records attempts): bundle first, then the package root, then the rest; the override short-circuits; the error lists every candidate. Plant: with the new steps removed, the order test fails; paste it.
5. **Docs.** The package README's "How the library is found" (or equivalent) section lists the order and says what an app must do: ship the `.dylib` in `Contents/Frameworks`, signed with the app. `docs/python-zig-bridge.md` or the binding doc, whichever describes the loader today, says the same in one paragraph.
6. **No change** to `zig/`, the header, `CONTRACTS_VERSION`, the shipped libraries or `native/SOURCE-SHA256` (this is Dart-only). State that the stamp is unchanged. All five suites green after the Report (`source ~/development/env.sh`; `flutter pub get` for the Dart package; `SEARCH_SIMPLI_LIBRARY_PATH` unset); tails pasted with home paths redacted.

### Findings (none blocking)
1. **Step (a) searches places before `Contents/Frameworks`.** dlopen of a bare name tries the cwd, then the Flutter engine's rpaths, including `/usr/local/lib/.`, before it reaches the bundle. A stray `libsearch_simpli.dylib` in `/usr/local/lib`, or in the cwd of an unsandboxed app, would load instead of the bundled copy. The `ss_version` check catches only a different contract version. The same holds for `dart test` in a checkout: such a file would now beat the package's own `native/` copy, the kind of shadowing the 30 Sep rule warns about. This Mac has none. Criterion 1 fixed the order, so this is not a build defect. Trying (b), an exact path, before (a) would make the bundle deterministic, and the probe shows (b) alone suffices. That is for the orchestrator to decide.
2. `bundle_probe.sh` always exits 0 (`|| true` after each run, no assertion on `PROBE_ANSWER`/`PROBE_FAIL`), so it reports but does not check. A regression shows only to a reader.
3. `show_sandbox` never prints the entitlement's value (the mismatch above). `grep -A2`, or `PlistBuddy` on `codesign … --xml`, would print it.
4. Clean-up: the script leaves its `mktemp` workdir ("delete when done"). The app leaves `ss_probe_*` snapshot copies in `$TMPDIR` and the container's `tmp/`. `~/Library/Containers/com.example.probeApp` persists between runs. I deleted the workdirs and those files after my runs and left the container.
5. Only `flutter build macos --debug` with ad-hoc signing was exercised. A Release build with hardened runtime, a Developer ID signature and notarization is the app's M7-T2 to prove in its own build.
6. `PROJECT-STATE.md`'s loader bullet still describes only the package-relative lookup. It is the orchestrator's file.
7. The README says the probe runs with "cwd `/`". With the sandbox on, the launch is from `/` but the process starts in its container, which is the proof. A clause would make that clear.
