**State:** filed by the orchestrator, 23 Nov 2026; Part 1 accepted 23 Nov; Part 2 built on `task/S6-T24`, timing orders committed, **stopped before timing** (no timed run), awaiting the maintainer's word on timing, then a Verdict · **Depends on:** [S6-T23](S6-T23.md) (the text rule; branch from `main` after it merges), [S6-T22](S6-T22.md) (the judged set) · **Plan:** [objective plan](../plans/2026-11-16-objective-plan.md) step H3; **specification:** [H3 in the implementation specification](../plans/2026-11-22-text-search-implementation-spec.md#h3-pattern-search-scan)

## Why

The maintainer's direction of 22 Nov 2026 makes simple token and pattern
matching ("like `sed`, `awk`") the base of text search. Today an exact string
cannot be searched: `142.50` becomes the tokens `142` and `50`, quotes are
ignored outside `find`, and there is no pattern code in `zig/src/`. On 23 Nov
the maintainer said to build this step, then pause.

## What

The specification's H3 section is the requirement: request and response fields,
order (path, then line), the pattern subset matched in linear time, the two
sources (an index's source section; a folder with nothing prepared), the code
table, the tests and acceptance. Read it whole. Where this file and the
specification differ, this file rules.

### 6. Notes, and what is not done

- **The warning's wording.** ADR 0006 §2 gave `pattern_matches_empty` the message "…so every line matches". That is
  not so for a pattern such as `^$`, which can match the empty string but matches only empty lines. The build says
  "the pattern can match the empty string, so a line can match without any match_offsets", which is what the
  result shows. Argued; the code `pattern_matches_empty` is the ADR's.
- **Marks.** Word code points include the marks Mn and Mc, not Me, as the analyser's table is generated
  (`scripts/gen_unicode_tables.py`). The user document says so.
- **`ẞ` and `ß`.** The fold is one code point to one. `ẞ`'s full fold is "ss", so it is left as it is: it matches
  neither `ß` nor `ss` under `insensitive`, and `smart` treats it as unchanged (insensitive). The engine and the
  reference agree (shown by `test_smart_case` and the agreement); the user document says so.
- **The reference's cursors** use SHA-256 prefixes where the engine uses XXH3, so a cursor goes back only to the
  implementation that made it (argued: `scan.py` `_request_hash`). **The reference checks its budget between lines
  only**, never inside one, so it cannot refuse a single long line as the engine does (argued: `scan.py` `_run`).
- **The `main` archive's two Python failures** come from the archive having no `.git`; both pass in the worktree
  (shown by the head's suite).
- **`--` between context groups.** The plain output prints `--` between every pair of hits that have context, even
  when their groups touch, where grep merges them; `--json` is not affected. Argued (a choice; `cli.runScan`).
- **The CLI's usage text** says `--case smart` ignores case "unless the pattern has an upper-case letter (one that
  case folding changes)".
- **Not done:** `ss_scan_folder` and a cancel (03-next rows, rulings O-5 and O-9); the timing runs (orders only);
  `scan` in the Python `tool_server.py`, which serves CAP-13's four methods; a Verdict.

## Verdict (verifier, 23 Nov 2026)

**FAIL.** Verified head: `137465c2b29067c47370864e86191bc9bdc26b1d` (the newest head of `origin/task/S6-T24` when
fetched, the same as the builder's report). `main` at `43a308d` was built beside it, from an archive with its own
caches. Probes and their outputs are in [`docs/evidence/s6-t24/verify/`](../evidence/s6-t24/verify/). Their outputs
are under `out/`, with the scratch path written as `<scratch>`. No timed run was taken. The probe times below are
single wall-clock runs on a machine that was not quiet, so read them as orders of magnitude, not as timings of the
build.

Most of the work holds up under attack. The answers match across every interface and the oracles. Paging,
cursors, the schemas, the byte identity of what existed, the natives and every check all pass. The FAIL is on
one point: the bounds the task claims for time and memory are not true. A 44-byte pattern holds the server for
27 s at `time_budget_ms` 1, and a nest one level deeper would hold it for hours. That breaks CAP-25's NFR-19 and
CFT-35 ("bounded by the budget") and `docs/scan.md`'s "a scan holds the server for at most its budget". This is
true on every surface, because they all share `scan.run`.

### Findings

1. **High: pattern compilation is bounded neither by the 8,192-step cap nor by the budget.** *Shown by a run*
   ([`probe_compile_hang.py`](../evidence/s6-t24/verify/probe_compile_hang.py), `out/compile_hang.txt`).
   - **Why it happens.** `(?:)(?:)` is a concatenation of two empty groups. `Parser.repeat` refuses a repeat
     only of an `.empty` node or an assertion, so `{255}` around this one is accepted. `Compiler.node` then
     expands the body `min` times, and each expansion emits nothing. Nested, the compiler walks the body
     255^depth times, the cap never fires, and the budget has not started yet: `Budget.start` comes after
     `pattern.compile` in `scan.run`.
   - **What the runs measured.**
     - `(?:(?:(?:(?:(?:)(?:)){255}){255}){255}){255}` (44 bytes) took 21.98 s with `--time-ms 1` on the command
       line (over a 2-line folder).
     - Over `searchd serve` it took 26.95 s, and a `status` call queued behind it answered only after the same
       26.95 s.
     - Depth 3 took 0.09 s.
   - **Argued from the code.**
     - Depth 5 (53 bytes) would take about 255 times longer, roughly 1.5 to 2 hours. There is no cancel.
     - `ss_scan`, MCP and Dart take the same path.
   - **What a caller sees:** no answer, and a server that answers nothing else for that time. The Python
     reference does not hang here, because it sizes the tree instead of expanding it.
   - **Possible fixes:** refuse a repeat whose body emits no instruction, or charge expansions rather than
     emitted instructions against the cap, and start the budget before compiling.
2. **Medium: the every-match loop costs up to 512 times the documented bound.** *Shown by a run*
   ([`probe_superlinear.py`](../evidence/s6-t24/verify/probe_superlinear.py), `out/superlinear.txt`).
   - **Why it happens.** `matchLine` restarts the VM after each match. Each restart runs until the
     higher-priority threads die. Matches are listed until one starts past the 512-byte `text`.
   - **What the runs measured** (one line of n `a`s):

     | Pattern | n | Time |
     | --- | --- | --- |
     | `a(.*b)?` | 2^14 | 0.12 s |
     | `a(.*b)?` | 2^16 | 0.49 s |
     | `a(.*b)?` | 2^18 | 1.99 s |
     | `a(.*b)?` | 2^20 | 7.89 s |
     | `a.*b` (one pass of the whole line) | 2^20 | 0.03 s |

   - **At the default budget** the 2^20 line is refused with `capacity` ("line 1 … outlasts
     time_budget_ms (2000)").
   - **Argued from the slope:** a line of about 4 MiB would outlast the 30 s maximum, so it can never be
     scanned with such a pattern.
   - **What is wrong in the claims.** The growth is still linear in n, but `docs/scan.md`'s "time proportional
     to the pattern's size times the line's length, whatever the pattern" and NFR-19 leave out this factor,
     which can reach about 512.
3. **Medium: the literal paths are not budgeted.** *Shown by a run* (same probe).
   - **Why it happens.** `scan.run` hands the whole rest of the file to `std.mem.findPos` or
     `std.ascii.findIgnoreCasePos`. Both are Boyer-Moore-Horspool with an O(n×m) worst case. The budget is
     asked only between candidate lines.
   - **What the runs measured** (a 10 MiB file of 4,095-`a` lines, `--time-ms 1`):

     | Needle | Path | Time | `stopped` |
     | --- | --- | --- | --- |
     | 1,023 `a`s + `b` | `ascii_ci` (the default `smart` case for a lowercase literal) | 3.90 s | `"none"` |
     | the same needle | the byte search | 0.17 s | |

     The `b` + `a`s needle and an `x` file stay at about 0.03 s.
   - **What this contradicts:** "`time_budget_ms` bounds one page" and "the clock is checked … every 256
     lines".
   - **Argued from the code:** the overrun is one file per page, because the budget is checked between files.
4. **Medium: memory grows with the number of lines, not with the file's size.** *Shown by a run*
   ([`probe_memory.py`](../evidence/s6-t24/verify/probe_memory.py), `out/memory.txt`).
   - **Why it happens.** `source.lineStarts` keeps one `u64` per line, held at once for the file being
     scanned.
   - **What the runs measured** (peak memory footprint, 10 MiB files):

     | File | Folder scan | Index scan |
     | --- | ---: | ---: |
     | lines of 67 bytes | 13,042,000 B | 31,277,416 B |
     | line breaks only | 203,211,256 B | 177,144,288 B |

   - **What this contradicts.** The Report's NFR-13-form result (a 64 MiB cap, peak 40,897,299 B) holds for its
     file shape only.
   - **What a caller sees:** on a phone (UC-007, `ss_scan`), a footprint near 200 MB, or an allocation failure.
5. **Low: the O-7 refusal can name the wrong cause.** *Shown by a run*
   ([`probe_paging.py`](../evidence/s6-t24/verify/probe_paging.py), `out/paging.txt`, last case).
   - **What the run showed.** An 8 MiB file whose first line is 5,000 `x`s was scanned for `x\d` at
     `--time-ms 1`. It was refused with "line 1 of r-legacy/a.txt outlasts time_budget_ms (1)".
   - **Why that is wrong.** The budget went on reading the file and finding its line starts. The VM's
     4,096-code-point check then fires inside the first line while `progress` is still false. The line itself
     is quick.
   - **What a caller sees:** the wrong reason, and no progress on that file at that budget.
6. **Low: the recorded divergence from the reference is a wider class than `docs/scan.md` says.** *Shown by a
   run* ([`probe_fuzz_agreement.py`](../evidence/s6-t24/verify/probe_fuzz_agreement.py), `out/fuzz1.txt`,
   `out/fuzz2.txt`).
   - **What the runs found.** Over 1,000 random nested patterns (seeds 20261123 and 7), hit lines were always
     identical to the reference and to Python's `re`. Two patterns had different offsets:
     - `[ckk].{2}((?:1|Bé){0,2}(?:\ds{1,3}){1,}|٣{0,2}|.*)+`: the engine gave `[21,26]` and the reference
       `[21,24]`;
     - a `(|…)+` case.
   - **What is wrong in the document.** The first holds a *nullable* alternative that is neither empty nor
     first. The document names only "an empty alternative first inside a repeat, `(|a)*`".
7. **Low: two documents are imprecise.**
   - **Line terminators.** `docs/scan.md` never lists which characters end a line: CR alone, VT, FF, NEL,
     U+2028, U+2029 and U+001C to U+001E. *Shown:* BSD grep disagrees on 5 lines of the fixtures, and a form
     feed in source code shifts line numbers against grep and editors
     ([`probe_grep_oracle.py`](../evidence/s6-t24/verify/probe_grep_oracle.py), `out/grep-oracle.txt`).
   - **Case folding.** `scan.request.schema.json` says `case` uses "Unicode simple case folding". But the fold
     leaves `ẞ` unchanged, and CaseFolding.txt gives `ẞ` the simple (status S) fold `ß`. The same holds for the
     Greek capitals with iota subscript. *Argued from the table.* `docs/scan.md` itself is accurate here.
8. **Low: a cursor carries no index identity.** *Shown* (`out/paging.txt`).
   - **What the run showed.** A cursor from index 1 at generation 1 was accepted by a different index at
     generation 1, and answered 2 hits from an arbitrary position.
   - **Also:** a `+` before a number in a cursor is accepted, though the schema's pattern refuses it.
   - **Not checked:** whether `find`'s cursor behaves the same.

All the other disagreements with grep and `re`, listed below, are documented in `docs/scan.md`, or follow from
its rules. Each was *shown*:

- `_` is not a word character;
- a BOM is not part of line 1;
- CRLF is one break;
- `\d` is Unicode Nd;
- the Kelvin sign, `ſ` and the sigmas fold;
- `ẞ` and `İ` are left unchanged;
- a combining mark after `cafe` blocks `whole_word`.

### Argued from reading

- **The literal fast path is exact.** In the analyser's fold table only `ſ`→`s` and `K`→`k` map a non-ASCII code
  point into ASCII. *Shown* from the table (1,386 pairs).
- **Every new API name is needed.** Each of the 15 new `api.pattern` and `api.scan` names is used by `ops/`. None
  is leakage.
- **Contracts 2.10.0 and Dart 0.12.0 are additive.** Two new schemas and `CONTRACTS_VERSION` change under
  `contracts/`, and nothing is removed in the Dart library. A 2.9.0 caller that never calls `scan` sees the
  identical answers shown above.
- **CAP-25 came first.** CAP-25 (`1941130`) precedes the extraction (`540bb09`) and the build (`137465c`). Part 1's
  prototype lies outside `zig/src/`.
- **The timing orders are well formed.**
  - The builds rotate left by (r−1) mod 5, so each is in each position once.
  - The corpora rotate by (r−1) mod 3.
  - There are two builds of `main` (`main`, `main2`).
  - The placement controls (+44,484 B and +44,644 B) bracket the head's +44,500 B; the dylib's `__text` delta is
    shown above.
  - The rule of 2026-11-17 is stated correctly.
  - They are in the format `run_timing.sh` parses.
  - No timed run had been taken.
