## Why

The maintainer's direction of 22 Nov 2026 makes simple token and pattern
matching ("like `sed`, `awk`") the base of text search. Today an exact string
cannot be searched: `142.50` becomes the tokens `142` and `50`, quotes are
ignored outside `find`, and there is no pattern code in `zig/src/`. On 23 Nov
the maintainer said to build this step, then pause.

## What

The specification's H3 section is the requirement: request and response fields,
order (path, then line), the pattern subset matched in linear time, the two
sources (an index's source section; a folder with nothing prepared), the code
table, the tests and acceptance. Read it whole. Where this file and the
specification differ, this file rules.

### 6. Notes, and what is not done

- **The warning's wording.** ADR 0006 §2 gave `pattern_matches_empty` the message "…so every line matches". That is
  not so for a pattern such as `^$`, which can match the empty string but matches only empty lines. The build says
  "the pattern can match the empty string, so a line can match without any match_offsets", which is what the
  result shows. Argued; the code `pattern_matches_empty` is the ADR's.
- **Marks.** Word code points include the marks Mn and Mc, not Me, as the analyser's table is generated
  (`scripts/gen_unicode_tables.py`). The user document says so.
- **`ẞ` and `ß`.** The fold is one code point to one. `ẞ`'s full fold is "ss", so it is left as it is: it matches
  neither `ß` nor `ss` under `insensitive`, and `smart` treats it as unchanged (insensitive). The engine and the
  reference agree (shown by `test_smart_case` and the agreement); the user document says so.
- **The reference's cursors** use SHA-256 prefixes where the engine uses XXH3, so a cursor goes back only to the
  implementation that made it (argued: `scan.py` `_request_hash`). **The reference checks its budget between lines
  only**, never inside one, so it cannot refuse a single long line as the engine does (argued: `scan.py` `_run`).
- **The `main` archive's two Python failures** come from the archive having no `.git`; both pass in the worktree
  (shown by the head's suite).
- **`--` between context groups.** The plain output prints `--` between every pair of hits that have context, even
  when their groups touch, where grep merges them; `--json` is not affected. Argued (a choice; `cli.runScan`).
- **The CLI's usage text** says `--case smart` ignores case "unless the pattern has an upper-case letter (one that
  case folding changes)".
- **Not done:** `ss_scan_folder` and a cancel (03-next rows, rulings O-5 and O-9); the timing runs (orders only);
  `scan` in the Python `tool_server.py`, which serves CAP-13's four methods; a Verdict.

## Verdict (verifier, 23 Nov 2026)

**FAIL.** Verified head: `137465c2b29067c47370864e86191bc9bdc26b1d` (the newest head of `origin/task/S6-T24` when
fetched, the same as the builder's report). `main` at `43a308d` was built beside it, from an archive with its own
caches. Probes and their outputs are in [`docs/evidence/s6-t24/verify/`](../evidence/s6-t24/verify/). Their outputs
are under `out/`, with the scratch path written as `<scratch>`. No timed run was taken. The probe times below are
single wall-clock runs on a machine that was not quiet, so read them as orders of magnitude, not as timings of the
build.

Most of the work holds up under attack. The answers match across every interface and the oracles. Paging,
cursors, the schemas, the byte identity of what existed, the natives and every check all pass. The FAIL is on
one point: the bounds the task claims for time and memory are not true. A 44-byte pattern holds the server for
27 s at `time_budget_ms` 1, and a nest one level deeper would hold it for hours. That breaks CAP-25's NFR-19 and
CFT-35 ("bounded by the budget") and `docs/scan.md`'s "a scan holds the server for at most its budget". This is
true on every surface, because they all share `scan.run`.

### Findings

1. **High: pattern compilation is bounded neither by the 8,192-step cap nor by the budget.** *Shown by a run*
   ([`probe_compile_hang.py`](../evidence/s6-t24/verify/probe_compile_hang.py), `out/compile_hang.txt`).
   - **Why it happens.** `(?:)(?:)` is a concatenation of two empty groups. `Parser.repeat` refuses a repeat
     only of an `.empty` node or an assertion, so `{255}` around this one is accepted. `Compiler.node` then
     expands the body `min` times, and each expansion emits nothing. Nested, the compiler walks the body
     255^depth times, the cap never fires, and the budget has not started yet: `Budget.start` comes after
     `pattern.compile` in `scan.run`.
   - **What the runs measured.**
     - `(?:(?:(?:(?:(?:)(?:)){255}){255}){255}){255}` (44 bytes) took 21.98 s with `--time-ms 1` on the command
       line (over a 2-line folder).
     - Over `searchd serve` it took 26.95 s, and a `status` call queued behind it answered only after the same
       26.95 s.

### Findings

1. **Medium: the scope filter runs before the budget can stop it, and its cost grows with the number of
   files.** *Shown by a run* ([`probe_bounds2.py`](../evidence/s6-t24/verify2/probe_bounds2.py), case B and G,
   `out/bounds2.txt`).
   - **Why it happens.** `scan.run` builds `kept` from every file of the source with `inScope` →
     `globMatches`, before the first file and with no charge to the budget. `globMatches` backtracks to the last
     `*`, so a name of n code points against a glob of g costs up to about n × g steps. Over an index there is no
     folder walk to count this under. Over a folder it is not part of the walk either: the walk of the same
     folder with no glob takes 61 ms in all.
   - **What the runs measured.** 20,000 files, each named 245 `a`s, 5 digits and `.txt` (255 bytes), with
     `--glob` set to `*`, 253 `a`s, then `b` (255 bytes), and `--time-ms 1`:

     | Source | No glob | `--glob '*.txt'` | The 255-byte glob |
     | --- | ---: | ---: | ---: |
     | index (CLI) | 33 ms | 70 ms | 3,314 ms, `stopped: "none"` |
     | folder (CLI) | 61 ms | 100 ms | 3,305 ms, `stopped: "none"` |
     | index over `serve` | | | 3,372 ms; an `index_status` call queued behind it answered at 3,373 ms |

     - Exact command (index):
       `searchd scan <index> tide --json --time-ms 1 --glob "*$(printf 'a%.0s' {1..253})b"`.
   - **Argued from the code.** The cost is linear in the number of files, so 200,000 such names would take about
     34 s. Even the ordinary `*.txt` over these long names spends about 37 ms outside the budget (70 against
     33 ms).
   - **What would fix it:** charge the filter's steps to the budget (a page that runs out while filtering stops
     with a cursor at file 0, or is refused under O-7), or filter lazily inside the file loop. Either way the
     time is then inside the stated bound.
2. **Medium: a unit of the meter is not bounded in time, so one meter interval can far exceed the Report's
   "under 10 ms".** *Shown by a run* (same probe, cases A, A2 and G).
   - **Why it happens.** The VM charges one unit per thread step and reads the clock once per 65,536 units. A
     step on a class instruction runs `Class.member`, a loop over every item of the class. A `\w`, `\W`, `\d` or
     `\s` item is a binary search of a Unicode table (`\w` searches two tables for a non-word code point), and a
     code point outside ASCII skips the class's ASCII table. A 1,024-byte pattern holds a class of 508 such items
     under `{255}`, so up to 254 threads are live at each position, each testing 508 items. The builder's meter
     test (`pattern.zig`, "the widest time between two reads of the clock") uses ASCII text and short classes,
     where one unit is cheap.
   - **What the runs measured** (2,000 lines of 254 code points; the bound is 1 + 50 ms, plus process start):

     | Pattern (1,024 bytes) | Text | `--time-ms 1` | `--time-ms 100` | `--time-ms 1000` |
     | --- | --- | ---: | ---: | ---: |
     | `[^\W×508]{255}` | `é` | 72 ms (folder), 73 ms (index), `stopped: "time"` | 138 ms | 1,037 ms |
     | `[^\w×508]{255}` | `→` | 131 ms ×3, refused (`capacity`) (folder); 133–134 ms (index) | 129–134 ms, refused | 1,008–1,042 ms |
     | `[^\s×508]{255}` | `→` | 136–137 ms, refused (folder); 141 ms ×3 (index) | 136–137 ms, refused | 1,059–1,068 ms |
     | `[^\W]{255}` (control) | `é` | 4 ms | 103 ms | 711 ms, done |

     - Over `serve`, `[^\w×508]{255}` at `time_budget_ms` 1 answered (refused) after 134 ms. An `index_status`
       call queued behind it waited the same 134 ms.
     - Exact command: `searchd scan --folder <folder> "[^$(printf '\\w%.0s' {1..508})]{255}" --regex --json
       --time-ms 1`.
   - **Two claims of the Report are not true for such a pattern:**
     - "one meter interval (under 10 ms in the test build; the widest measured, 1.2 ms)";
     - that "the first line of a page gets 10 ms": the first clock read inside that line comes after about
       130 ms.
   - **The bound still holds in form.** The overshoot is at most one interval, bounded by the class's 512 items,
     so about 140 ms on this machine, not unbounded. The stated constant of 50 ms is not met.
   - **What would fix it:** charge a class step by its items (or by the table searches it does), or cap the items
     of a class, so a unit's cost has a stated bound. Then measure the meter interval on the worst unit, not on
     ASCII.

## Rulings after Verdict 2 (orchestrator, 24 Nov 2026)

Recorded here as the orchestrator's rulings, each reversible by the maintainer or a reviewer. The eight earlier
findings are confirmed fixed; Verdict 2 is FAIL with two Medium and two Low findings.

1. **`name_glob` (Medium).** The glob filter's work is inside the budget: no pass over all names before the first
   file. Each name is filtered as the scan reaches it, charged to the meter, and `stopped: "time"` with a cursor
   resumes through it. One glob match is bounded: linear, or n×m with the name and glob lengths capped and stated.
   The verifier's case (20,000 files, 255-byte names, `*` + 253 `a` + `b`, `--time-ms 1`) stops within the stated
   bound over a folder, over an index and over `serve` with a call queued behind it. The folder walk stays outside
   the bound, and `docs/scan.md` says so plainly.
2. **Meter unit cost (Medium).** A unit of the meter has a bounded real cost: a class step is charged by the items
   it tests, or a class test is made constant-time (the builder's choice). The constant is then restated
   truthfully. The verifier's `[^\w×508]{255}` and `[^\s×508]{255}` cases at 1 ms and 1,000 ms, CLI and `serve`,
   hold the budget plus the stated constant. The time fuzz extends to full 1,024-byte patterns and class-heavy
   ones. If 50 ms cannot honestly be kept, the Report states the number that can be shown and why.
3. **Wall-clock thresholds in the default test run (Low).** NFR-19 stands: the default `zig build test` asserts
   on work counts or ratios, never on milliseconds. The meter-interval and first-line-grace tests count work; a
   wall-clock check lives only in a script outside the default run.
4. **The 16-match cut (Low).** (a) A hit gains one boolean, `matches_truncated`, true when the line's matches were
