# S1-T9 · Memory and disk under a long-running caller: measure first, fix what leaks

**State:** draft (owner reads before it runs) · **Depends on:** S1-T8 · **Size:** M · **Builder:** Opus (measurement design and leak fixes in Zig) · **Tester:** Opus

The app is a long-running caller: it keeps one handle open, queries on every turn, and re-indexes folders on demand. Leak-freedom has been a code-review claim since round C (S1-T4 finding 9, still open after S1-T5–T8), and the app found this week that it was not releasing two native handles (fixed app-side in M13-T22). This task measures the library itself.

## What exists (orchestrator, `main` `dbff430`)
- `zig/src/abi.zig` allocates every heap object through `std.heap.c_allocator` (`malloc`/`free`). Every returned string is freed by the caller with `ss_free`, and every handle with `ss_close`. `ss_last_error` is a thread-local 512-byte buffer, and `ss_version` is static.
- `ss_query` and `ss_index_folder` use a per-call `ArenaAllocator` over `c_allocator`, freed with `defer`.
- Each `ss_index_folder` run publishes a new generation. There is no generation garbage collection (PROJECT-STATE; `lifecycle.scan` reports unreferenced files but never deletes).

## The bars, written before the build (ROLES: "write the bar before the build"; a failed bar is recorded as failed, never redefined afterwards)
- **B1, leaks at exit:** macOS `leaks --atExit` on the soak harness after 1,000 full cycles reports **0 leaks** (0 bytes).
  *Caution, measured by the orchestrator on this Mac:* `leaks` scans the stack conservatively, so a stale copy of a pointer can hide a real leak. A test program that leaked one 64-byte block reported `0 leaks`, while one that leaked 1,000 blocks from a returned function reported `1000 leaks for 80000 total leaked bytes`. So B1 counts only together with criterion 2's planted leak, and B2–B4 (in-use growth) are the check that cannot be fooled this way.
- **B2, one long-lived handle:** with one handle open, malloc **in-use bytes** (`malloc_zone_statistics(NULL, …).size_in_use`, read in-process) after 50,000 `ss_query` + `ss_evidence` cycles exceeds the value after 10,000 by **≤ 64 KiB**. The 20,000 figure is reported too.
- **B3, open/close churn:** in-use bytes after 5,000 `ss_open`/`ss_close` cycles exceed the value after 1,000 by **≤ 64 KiB**.
- **B4, repeated re-indexing in one process:** with `ss_index_folder` and `update:true` over an unchanged 200-file folder, in-use bytes after 500 runs exceed the value after 100 by **≤ 64 KiB**.
- **D1, disk (reported, no bar):** the snapshot directory's byte size and file count after 1, 100 and 500 unchanged updates, and whether an unchanged update publishes a new generation at all. Growth is a known gap and its fix is a design question, so it is measured here and scheduled separately.

Each figure is the median of 3 runs, with all 3 shown. Never a single run; never a wall-clock time.

## Acceptance criteria
1. **Soak harness.** `zig/tests/abi_soak.c`, built and run by a new `zig build soak` step (not part of `zig build test`; bounded run time). It exercises every exported `ss_*` function, including failure paths (missing directory, malformed query JSON, malformed options, `ss_free(NULL)`, `ss_close(NULL)`). It frees every returned pointer and closes every handle. Cycle counts are arguments. It prints the in-use figures for B2–B4 and D1 as one parseable line each.
2. **B1–B4 measured and recorded** in the Report with the raw output of every run. If a bar fails, say so first, then go to criterion 3. **The harness must catch a planted leak:** remove one `free` from `ss_close` (and, separately, skip `ss_free` on one returned string in the harness) and show that B1 reports a non-zero leak and that B3 (or B2) exceeds its bar. Then restore it. A harness that cannot see a planted leak measures nothing.
3. **Every leak found is fixed**, in `zig/src`, with the failing bar re-measured green afterwards and **shown failing with the fix reverted**. If a fix needs a design change (generation garbage collection, an ABI change, a new allocator strategy), stop: report it with the evidence and do not build it.
4. **The Dart binding frees what it receives.** List every call site in `bindings/dart/search_simpli/lib/` that receives a native pointer or handle and show it is freed or closed on every path, exceptions included. Add a Dart test that runs 5,000, 10,000 and 20,000 query cycles on one handle and reports `ProcessInfo.currentRss` at each (best of 3), with a generous bound: growth from 5,000 to 20,000 ≤ 8 MiB. The VM's GC makes RSS noisy; the C-level bars are the precise ones.
5. Libraries and stamp: if `zig/src` changed, run `tool/build_native.sh` last and report whether the libraries changed byte for byte. No change to the header, `CONTRACTS_VERSION` or the ABI unless criterion 3 found it unavoidable, and then it is stopped and reported, not built.
6. All five suites green after the Report, run with `source ~/development/env.sh`. Tails pasted with home paths redacted.

## Not in scope
Linux measurement (no valgrind here; say so in "Not checked"). Generation garbage collection. The app's own handle use (that is simpli-helper's).
