# S4-T12 · The lexical section is validated once when it is written, and the merge's end-of-walk checks refuse in every build

**State:** ready (starts from `main` after the S4-T11 merge, `06f1783`) · **Date:** 2026-11-06 · **Depends on:** S4-T11 (the stage profile with `encode_sections.lexical_length`; the merge) · **Size:** S

**Owner:** the Xcode Mac orchestrator · **Orchestrator:** Claude Fable 5.1 · **Builder:** Claude Opus 5.5 (local) · **Verifier:** Claude Opus 5.5 (local, a different agent)

**Why.** Two findings of S4-T11, one from its builder and one from its verifier. (1) After S4-T11 the largest stage left in one changed file's encode is the lexical section: `encode_sections.lexical` 15.65 ms of `encode_sections`' 23.1 (10k timing corpus, `ReleaseSmall`, p50 of ten, filename off). The writer calls `lexical_segment.encodedLength`, which runs `validateIndex` (a hash set of every term for duplicates, although a positional dictionary is checked sorted a few lines later; every posting range; every posting; the posting order; every ordinal and offset of sections 4 and 5), then `encode`, which calls `encodedLength` and so `validateIndex` **again**: `encodedLength` alone measured 6.3 ms (`encode_sections.lexical_length`), so the second validation is most of the remainder. The same pair of calls writes the filename channel's lexical section (`filename_field.build`) and `import-json`'s (`importer.zig`). The row *The lexical encode validates the index twice* in `docs/journey/03-next.md` filed it. (2) `mergeCarried` and `offsetTableStarts` in `apply.zig` end with `std.debug.assert(cursor == …)` followed by `if (cursor != …) return error.InvalidLexicalSection`: in Debug the assert panics before the return, and in `ReleaseSmall` the assert is an `unreachable` the optimizer may assume true, and the verifier showed it did (its plant D2: `mergeCarried` returned an index with the left-over byte dropped). Nothing reaches those lines from a file today (`lexical_segment.decode` refuses a section 4 with a byte left over before the merge runs, and `validateIndex` checks the merged index before it is encoded), so the update is safe in every build; but the Report's "refused with `InvalidLexicalSection`" is true only of the early-end paths, and a later writer change could make the dead check matter. This task fixes both. **Format, readers, contracts (2.2.0), analyzer and every section's bytes are unchanged**: every section a generation writes stays byte-identical to today's, so nothing is rebuilt on any phone.

## Rulings
1. **Profile first, in the Report, before any change.** `main` at `06f1783` on the 10k timing corpus (`scripts/gen_timing_corpus.py <dir> 10000`, `corpus_matches_recorded: true`), `ReleaseSmall`, one changed file as `scripts/s4t4_budgets.py profile` does, filename off and on, ten runs, p50 and worst, load stated: `encode_sections.lexical` and `encode_sections.lexical_length`, and inside one `validateIndex` the cost of each pass (the hash set, the term ranges, the postings pass, `validatePostingOrder`, `validatePositions`) through temporary sub-timers that stay under `SEARCH_SIMPLI_APPLY_STAGES` only if they fit the existing `Stages` without harm (otherwise a scratch measurement, stated as such).
2. **Validate once.** Writing a lexical section runs `validateIndex` **once**: `encode` no longer re-validates what `encodedLength` validated (shape to the builder: an unchecked sizing shared by both, with `encode` validating once and sizing unchecked; or one public call that validates, sizes, allocates exactly and writes, which `apply.zig`, `filename_field.zig` and `importer.zig` use). **Every refusal is kept with its name**: the negative cases in `lexical_segment.zig`'s tests (`CountOverflow`, `InvalidAverageDocumentLength`, `InvalidTerm`, `DuplicateTerm`, `InvalidPostingRange`, `DocumentFrequencyMismatch`, `InvalidPosting`, `UnsortedTerms`, `InvalidPositions`, `BufferTooSmall`, and any other the tests name) pass unchanged through the public calls the writers use; a direct `encode` with an invalid index still refuses (the public contract does not weaken: say how).
3. **The duplicate check for a positional dictionary is the adjacency pass.** For an index with positions (`HYBLEX02`), whose dictionary `validateIndex` already requires sorted, the hash set is dropped: the adjacency pass distinguishes an equal neighbour (`DuplicateTerm`) from a descending one (`UnsortedTerms`), so the error names are unchanged and the decision does not trust the `sorted_terms` flag (a positional index claiming sorted but not sorted is still `UnsortedTerms`; one with an adjacent duplicate is still `DuplicateTerm`: two tests). For a `HYBLEX01` index (no positions, `import-json`) the hash set stays.
4. **The end-of-walk checks refuse in every build.** The two `std.debug.assert` lines before the `InvalidLexicalSection` returns in `mergeCarried` and `offsetTableStarts` are removed so the returns stand in Debug and `ReleaseSmall`; a test in `apply_test.zig` (or beside the merge) calls the walk directly with a previous section 4 carrying one extra byte and one carrying one byte too few and expects `error.InvalidLexicalSection` for both, run in Debug and `ReleaseSmall` (the verifier's plant D2 as a test). The Report names every other place in the writer path where an `assert` precedes a check of the same condition (`grep -n 'std.debug.assert' zig/src/apply.zig zig/src/source.zig zig/src/lexical_segment.zig`), and whether each is dead the same way; fixing them is in scope only if they guard a refusal.
5. **The bar.** On the 10k corpus, `ReleaseSmall`, interleaved rounds with the untouched `06f1783` built in a scratch worktree as *before*, load stated and below 3.0, filename off and on, five runs each, p50 and worst: (a) **`encode_sections.lexical` p50 ≤ 9 ms** (S4-T11: 15.65); (b) **one changed file p50 at least 5 ms below *before*'s in the same run, off and on**; (c) `ss_open`, the first query after a cold open, `find`, `search_knowledge`, a filename and a `both` query within 0.3 ms of *before* (no reader changed; `decode` and everything below it in `lexical_segment.zig` untouched by `git diff`); (d) the full 10k build (`searchd index`) within 3 % of *before*, and faster by about the saved validation if the saving shows (stated); (e) parity: `scripts/s4t11_budgets.py compare` (five sections identical), the randomized parity test with a seed of the builder's own, `scripts/capture_query_outputs.py` and `scripts/source_read_parity.py` byte-identical before and after (counts stated); the Python suite's `import-json` cases pass (241, no skips).
