# S4-T12 · The lexical section is validated once when it is written, and the merge's end-of-walk checks refuse in every build

**State:** ready (starts from `main` after the S4-T11 merge, `06f1783`) · **Date:** 2026-11-06 · **Depends on:** S4-T11 (the stage profile with `encode_sections.lexical_length`; the merge) · **Size:** S

**Owner:** the Xcode Mac orchestrator · **Orchestrator:** Claude Fable 5.1 · **Builder:** Claude Opus 5.5 (local) · **Verifier:** Claude Opus 5.5 (local, a different agent)

**Why.** Two findings of S4-T11, one from its builder and one from its verifier. (1) After S4-T11 the largest stage left in one changed file's encode is the lexical section: `encode_sections.lexical` 15.65 ms of `encode_sections`' 23.1 (10k timing corpus, `ReleaseSmall`, p50 of ten, filename off). The writer calls `lexical_segment.encodedLength`, which runs `validateIndex` (a hash set of every term for duplicates, although a positional dictionary is checked sorted a few lines later; every posting range; every posting; the posting order; every ordinal and offset of sections 4 and 5), then `encode`, which calls `encodedLength` and so `validateIndex` **again**: `encodedLength` alone measured 6.3 ms (`encode_sections.lexical_length`), so the second validation is most of the remainder. The same pair of calls writes the filename channel's lexical section (`filename_field.build`) and `import-json`'s (`importer.zig`). The row *The lexical encode validates the index twice* in `docs/journey/03-next.md` filed it. (2) `mergeCarried` and `offsetTableStarts` in `apply.zig` end with `std.debug.assert(cursor == …)` followed by `if (cursor != …) return error.InvalidLexicalSection`: in Debug the assert panics before the return, and in `ReleaseSmall` the assert is an `unreachable` the optimizer may assume true, and the verifier showed it did (its plant D2: `mergeCarried` returned an index with the left-over byte dropped). Nothing reaches those lines from a file today (`lexical_segment.decode` refuses a section 4 with a byte left over before the merge runs, and `validateIndex` checks the merged index before it is encoded), so the update is safe in every build; but the Report's "refused with `InvalidLexicalSection`" is true only of the early-end paths, and a later writer change could make the dead check matter. This task fixes both. **Format, readers, contracts (2.2.0), analyzer and every section's bytes are unchanged**: every section a generation writes stays byte-identical to today's, so nothing is rebuilt on any phone.

### Ruling 2: validate once

The ruling's second shape (ruled at the plan). `lexical_segment.zig`: two private halves,
`sizes(index)` (the byte counts and total, with checked arithmetic; no validation) and
`writeSized(index, sizes, output)` (today's writing body). The public calls:

- `encodedLength(index)` = `validateIndex`, `sizes`;
- `encode(index, output)` = `validateIndex`, `sizes`, `BufferTooSmall` if short,
  `writeSized`;
- `encodeAlloc(allocator, index)` (new) = `validateIndex`, `sizes`, an exact allocation,
  `writeSized`; the returned slice is the whole allocation. `encodeAllocMarked` is the same
  with the stage marks.

Each runs `validateIndex` **once**. **A direct `encode` of an invalid index still refuses:
`encode` calls `validateIndex` itself, before it sizes or writes anything.** It no longer
gets there through `encodedLength`, so it validates once instead of twice. Every
fixed-buffer caller (`main.zig`, `engine.zig`, `abi.zig`, `publication.zig`, the tests) is
unchanged and already validated once. The three writers call `encodeAlloc` in place of the
`encodedLength` + `encode` pair: `apply.zig` (`encodeAllocMarked`), `filename_field.build`,
`importer.zig` (its `defer free` now frees the returned slice). The error order is as
before: validation, then `SizeOverflow`, then `BufferTooSmall`.

In the stage profile, `encode_sections.lexical` is now the whole lexical write (one call),
with its passes as `encode_sections.lexical.<pass>`; `encode_sections.lexical_length` no
longer exists.

**Tests.** "S4-T12 ruling 2: every refusal keeps its name through encodedLength, encode and
encodeAlloc". Each case goes through `encodedLength`, `encode`, `encodeAlloc` and
`encodeAllocMarked`, with the testing allocator: nothing is allocated on a refusal.

- `CountOverflow`: 2^32 document lengths, as a slice over one `u32` that is never read
  (the length is refused first).
- `InvalidAverageDocumentLength`: NaN, −1, +∞.
- `InvalidTerm`: an empty term, v1 and v2.
- `DuplicateTerm`: v1 non-adjacent, v2 adjacent.
- `InvalidPostingRange`.
- `DocumentFrequencyMismatch`.
- `InvalidPosting`: a document out of range, a zero `term_frequency`, a term's postings out
  of document order.
- `UnsortedTerms`: descending terms, and sorted terms whose ranges cross.
- `InvalidPositions`: an ordinal past its document's length, and a byte left over in
  section 4.
- `BufferTooSmall`: through `encode`, one byte short.

Valid v1 and v2 indexes encode byte-identically through all three calls. The existing
negative tests are unchanged and pass. **Not testable, named as ruled:** `FieldTooLarge` is
declared but has no return site; `SizeOverflow` would need a slice longer than 2^61 that
validation walks before sizing; the hash set's `OutOfMemory` (page allocator) cannot be
forced.

### Ruling 3: the adjacency pass

For an index with positions, `validateIndex` runs one pass over neighbours, at the place
the hash set ran, so the error order is unchanged. It reads `index.positions`, never
`sorted_terms`. For each term it does today's `InvalidTerm` check, then `std.mem.order`
with the previous term:

- `.lt`: continue.
- `.eq`: `DuplicateTerm`.
- `.gt`: stop and **run the hash set from the start** (the fallback, ruled at the plan).

The later sorted check became `if (!sorted) return error.UnsortedTerms` at its old place,
after the posting checks, so the memcmp pass runs once (0.06 ms against the hash set's 0.8
plus the old 0.06). `HYBLEX01` keeps the hash set.

**The fallback costs nothing for every valid writer output:** a sorted dictionary, which is
what every writer builds, finishes the pass and never builds a hash set. Only an index that
is already refused takes the fallback. The one input whose name depends on it is an
unsorted positional dictionary that also holds a duplicate that is not next to its twin
(`beta`, `alpha`, `beta`): `DuplicateTerm` before S4-T12 and still `DuplicateTerm`, where
the pass alone would say `UnsortedTerms`.

**Tests.**

- "S4-T12 ruling 3: a positional index with an adjacent duplicate is DuplicateTerm, whatever
  sorted_terms says": `alpha, alpha, beta`, and the fallback case `beta, alpha, beta`, with
  `sorted_terms` true and false.
- "S4-T12 ruling 3: a positional index claiming sorted but descending is UnsortedTerms; a
  sorted one encodes": `beta, alpha` and `alpha, gamma, beta` with the flag true and false;
  `alpha, beta, gamma` encodes with either flag.
