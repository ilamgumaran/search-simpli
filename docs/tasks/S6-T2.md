### 1. Inventory (ruling 1), written before any code

Read from the source at `7cd2c16` and probed with a `ReleaseSmall` `searchd` built from it in a scratch copy with fresh caches (*main*, 1,095,880 B).

**How `index` builds a generation.** `cli.runIndex` opens `<folder>` (`openDir`, iterate) and creates `--out` (`createDirPathOpen`), takes the generation (`--generation`, else `generation_alloc.nextFreeGeneration`, which lists `--out`: 1 in an empty directory) and calls `indexer.indexFolder` → `walkAndApply`. The walk is `indexer.collectCandidatePaths`: every regular file under the folder whose path has no component starting with `.` or equal to one of `.git .search .zig-cache __pycache__ node_modules zig-out`, with one of the 19 `default_extensions` (case-insensitive), sorted bytewise. Each path becomes a `change` with `.walk` content in one root `r-legacy` (label `folder`, kind `local`, `retain_source` true), and `apply.applyBatch` → `applyParsed` runs with `analyzer` (default v2), the default chunker sizes (`max_chars` 1,600 / `overlap_lines` 3, `chunker.default_*`), `filename_index` (`--filename-index` → true), the two byte caps, `budget = .exhaust`, `detect_renames = false`, `complete_root = r-legacy`, `fresh = true` and the generation. `applyParsed` then: takes the writer lease (`lifecycle.tryAcquireWriter`: **creates `WRITER.LOCK`**); reads the current generation (`MANIFEST`, if any) and, with a `MANIFEST`, compares the file-name setting; skips the previous generation (`fresh`); stats and reads each candidate through the walk's directory (`readContent`), with the caps (`too_large`, `budget_exhausted`, `unreadable` for a failed read or invalid UTF-8); counts; then `buildGeneration`, which is **pure memory**: chunks (`chunker.chunkForPath`: `md-section-v1` for Markdown, `line-window-v1` otherwise), tokenizes, builds and encodes the documents, lexical, source, state, manifest and (with the channel) the two file-name sections, and checks the file-name sections (`validateBuilt`), returning every encoded byte in `Built`. Only after that does it touch the directory again: `lifecycle.publishLeasedKeepingWithExtras` (**writes** each section through a temporary file and rename, fsyncs the directory, then **writes `MANIFEST`**; prunes with `--keep-generations`) and `incremental_state.savePointer` (**writes `INDEX-STATE.json`**). Probed: `index fixtures/j2 --out idx --filename-index` writes 9 files (`documents-1.hybseg`, `lexical-1.hyblex`, `source-1.hybsrc`, `state-1.hybstate`, `filenames-1.hybseg`, `filename-lexical-1.hyblex`, `MANIFEST`, `INDEX-STATE.json`, `WRITER.LOCK`), generation 1, 95 files, 865 documents.

**How `query` and `evidence` open and answer.** `runQuery`/`runEvidence` open `<dir>` and:

- `--search-field content` (the default): `snapshot_open.open`, the eager one-shot open: `loadEngine` **reads** `MANIFEST` (stat, then read into a buffer), sizes one block from its counts (`OpenBlock.of`), **reads** the documents and lexical sections into the block and decodes them (`Engine.openWith`: checksums once, every check of `manifest.validateSnapshot`); the roots from the manifest's meta; with the channel, **reads** both file-name sections (`filename_field.load`: stat, read, check, decode); the position tables. Then `runSearch` (`title_field.derive` per call, `Engine.queryTokenized`, top-k) and the text, `--json` or evidence writer.
- `--search-field filename|both`: `snapshot_open.openScoped` (`openScopedWith`): the same `loadEngine` without position validation, then `scope.Loads` with the source section's file and the two file-name sections' files **opened, not read**, and `scope.Folder` built from the meta. The answer is `Engine.queryFields` (the file-name sections read and decoded at the first use, `Folder.filenameDecoded`; for `both` the title field, `Folder.titleField`) and `filename_response.writeEvidence` (text without `--json` for `query`; JSON for `query --json` and `evidence`).
- Neither path writes anything. Neither reads the source section's bytes (it is only opened by the scoped open); `generation` appears in the output only in the filename/both envelope (`index.generation`).

**Which steps touch the file system.** For a fresh walk: the folder (walk, stat, read: read-only); the index directory: create, list (`nextFreeGeneration`), `WRITER.LOCK`, `MANIFEST` read, section writes, renames, fsyncs, `MANIFEST`, `INDEX-STATE.json`; on the query side `MANIFEST` and section reads and file opens. Everything between the reads of the folder and the publish is in memory already.

**Whether the engine can be opened over sections held in memory today.** Not through a public function, but every decode step already works on byte slices: `Engine.openWith` takes a `publication.LoadedSnapshot` (manifest metadata plus the encoded manifest, documents and lexical sections) and output tables; `loadEngine` is "read the files into one block, then `openWith`". What is tied to files: `loadEngine`'s reads, `filename_field.load` (stat and positional reads of two files before the same checks and `decodeInspected`), and `scope.Loads` (the source section streamed from a file, the file-name sections read from two files at first use). On the build side, `applyParsed` takes a directory it needs only for the lease, the current-generation read, the generation number, the publish and the state pointer: with `fresh` and a stated generation, none of its other steps reads the directory (the previous generation is skipped and `prev_filename` is null).

**The smallest change that allows it**, all behaviour-neutral for existing callers (each existing call passes its directory and takes exactly today's statements):

1. `apply.zig`: `applyParsed` takes an optional directory and an optional place for the encoded sections. With no directory (allowed only with `fresh` and a stated generation) it takes no lease, reads no generation, and returns the `Built` sections instead of publishing them and writing the pointer. A public `apply.buildDetached` calls it.
2. `indexer.zig`: `walkAndApply`'s batch and options built by one helper, used by today's path and by a new `indexer.buildFolderDetached` (the same walk, root, options and caps, `fresh`, generation 1: what `index` into an empty `--out` uses).
3. `snapshot_open.zig`: `loadEngine` and `openScopedWith` take where the sections are: a directory (today's code) or the sections in memory (the decoded tables in a block of `OpenBlock`'s layout with the two section areas empty, the documents and lexical sections used in place; then the same `Engine.openWith`). Public `openDetached` (as `open`) and `openScopedDetached` (as `openScoped`).
4. `filename_field.zig`: `load` reads the two files and calls a new `loadBytes`, which holds today's checks and decode.
5. `scope.zig`: `Loads` may hold the source and file-name sections' bytes instead of their files; the first use then checks and decodes the bytes (same checks).
6. `cli.zig` and `main.zig`: the `search` command; `runQuery`/`runEvidence` split into an open and an answer step so `search` uses the very same answer code over the detached engine.

That is a moderate change to five core files with no format, wire, C ABI or Dart change, so **I take the preferred in-memory path, not the temporary-directory fallback**. The library (`abi.zig`) reaches `apply.zig`, `indexer.zig`, `snapshot_open.zig`, `filename_field.zig` and `scope.zig`, so its bytes will change; nothing a binding can call or see changes (no exported symbol, no JSON field, no error code).

### 2. Specification against the code (ruling 2), and readings

`searchd search <folder> "<query>" [--top-k N] [--json] [--evidence] [--search-field content|filename|both] [--max-file-bytes N] [--max-total-bytes N]`: open the folder, walk and read it by `index`'s rules (above), build the generation in memory with analyzer v2, the default chunker sizes and the caps given (defaults 10 MiB / 512 MiB, `index`'s), open it in memory the way `query`/`evidence` open a directory for that field, answer with their code, exit.

Readings, named so they can be ruled on:

1. **Same answers, generation included.** The detached build uses generation 1, which is what `index <folder> --out <new dir>` publishes, so even `index.generation` in the filename/both envelope is equal; the comparison needs to take nothing out. Nothing in any output names the index directory.
2. **What `--evidence` and `--json` mean.** `search … --evidence` answers as `evidence X`; `search … --json` as `query X --json`; neither as `query X` (text). `--evidence --json` is accepted and answers as `evidence X --json` does (evidence is always JSON).
3. **The file-name channel is built only when it is asked for.** `--search-field filename|both` builds it (so the sections are what `index --filename-index` publishes); `content` does not build it, since a content answer never reads it (the equivalence tests compare `content` answers against `index --filename-index` too, as the ruling words it). This saves work on the common path; to be measured and stated.
4. **Usage errors** are exit 2 and one stderr line, nothing on stdout: a missing folder and a path that is not a folder are judged when the folder is opened (by `runSearch…`, as S5-T11's refusal); an empty query (no bytes, or only white space) and invalid UTF-8 are judged by the parser. Any other failure to open or read (for example permission denied on the folder itself) stays exit 1, as for `index`.
5. **Files left out** (over `--max-file-bytes`, unreadable, past `--max-total-bytes`) are left out exactly as `index` leaves them out; since no index report exists for a direct search, one stderr line counts them when any were left out (exit 0, stdout unchanged). An empty folder answers with no results and exit 0.
6. **`--top-k`** is `query`'s (a positive whole number, default 10).

**Reading 3 withdrawn after measuring (`3237695`).** The stage profile of one `search` over the 10,000-file timing corpus (`SEARCH_SIMPLI_APPLY_STAGES=1`, `ReleaseSmall`, one run each, 5-minute load about 4.4) put the file-name channel at about 12 ms of 606 (`filename_build` 7.8, `filename_validate` 3.4, `manifest_bind` 1.2) and peak memory at 156 MB with it against 140 MB without. Saving 2 % of the time was not worth sections that differ from `index --filename-index`'s for `content`, so `search` always builds the channel and every field's answer comes from exactly the sections `index --filename-index` publishes. The same profile shows where a direct search spends its time: `build_documents` (chunking and tokenizing) 405 ms, reading the files (`changes`) 120–138 ms, the lexical build 38 ms, encoding the sections 26 ms.

### 11. Deviations and open questions

1. **A stderr line for files left out** (reading 5): `search` has no index report, so it counts left-out files on one stderr line when there are any. `index` prints its own report instead; stdout is equal.
2. **`--evidence --json`** is accepted and prints the evidence answer (always JSON), as reading 2 says.
3. **An empty or whitespace-only query is a usage error** (ruling 2, reading 4), where `query` on an index accepts both (`main`'s `searchd query <index> ""` and `"  "`: exit 0, a header line, no results). 4. **`@constCast`** in `snapshot_open.loadEngineMemory`: `publication.LoadedSnapshot` holds `[]u8`, the sections are `[]const u8`; the decoders only read them. Changing `LoadedSnapshot` to `[]const u8` would be cleaner and touches the publication code; left for the verifier's judgement.
