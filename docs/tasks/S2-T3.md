# S2-T3 · Rank only the chunks that matched

**State:** ready · **Series:** S2 (research doc, learning 3) · **Depends on:** S1-T8 · **Size:** S · **Builder:** Sonnet 5 · **Tester:** Opus

Every query sorts the whole corpus three times, lexical mode included
(`zig/src/hybrid.zig:143-151`): a sampling profile puts about 94 % of query
time in `std.sort.pdq` and about 0 % in postings scoring. Measured p50 at
10,000 chunks: 8.0–11.6 ms on the M1 (0.36–0.85 ms at 1,000). Luxir's
block-max/MaxScore pruning would save nothing here; plain top-k selection
removes most of the cost.

## Acceptance criteria
1. Lexical ranks are assigned over the chunks with a nonzero lexical score
   only (a sort of the matched set, or a bounded selection when `candidate_k`
   is smaller); the semantic pass is skipped entirely in lexical mode and when
   the snapshot has zero vector dimensions; fusion runs over the union of the
   two candidate sets with the same `document_index` tiebreak
   (`hybrid.zig:231-236`); per-query scratch shrinks from three corpus-sized
   arrays (`zig/src/abi.zig:296-302`) to sizes proportional to the matched set
   plus `candidate_k`.
2. **Bar (a):** `ss_query` output is **byte-identical** to the current library
   for every judged fixture query, the ABI goldens (`zig build test-abi`), and
   200 random 1–6-word queries drawn from the 10k corpus vocabulary
   (`scripts/gen_timing_corpus.py`), in all three retrieval modes where
   vectors exist (the hybrid case on the existing vector fixtures). Paste the
   comparison method and counts.
3. **Bar (b):** lexical p50 at 10,000 chunks **≤ 2 ms** for each of the four
   queries the research doc's M2 used, on the shipped ReleaseSmall build
   through the same ctypes harness (Appendix A of the research doc; M1).
4. **Bar (c):** no query slower than today at 1,000 chunks.
5. **Plant:** with the matched-set selection reverted, the p50 test fails
   (it measures against a threshold; say how it stays robust to machine load:
   take the best of five runs and assert growth, not only an absolute).
6. All five suites green after the Report; libraries rebuilt last with
   `tool/build_native.sh`.

## Report (builder fills in)

**Builder:** Sonnet 5.5 · **Branch:** `task/S2-T3`

### What was done
- `zig/src/hybrid.zig`: new `searchSparse`. Lexical channel ranks only chunks with a nonzero, authorized, in-scope score, via a bounded heap of `min(candidate_k, documents)` (a total order, `document_index` tiebreak, so the survivors are the first K of a full sort); semantic channel runs only when mode is not `lexical` and the query vector is non-empty (the ABI passes an empty vector for zero-dimension snapshots), also a bounded heap; fusion runs over the union (sort by document, merge, sort by fused score with the same tiebreak). A chunk ranked by one channel only still reports its score in the other (lexical via `scoreOf`, semantic recomputed), as the dense path did. The dense `search`/`searchWithLexicalScores` are untouched and kept as the reference oracle.
- `zig/src/postings.zig`: `resolveQuery` + `SparseScorer` (one cursor per query term, merge by ascending `document_index`, contributions summed in query-term order, so each score is bit-identical to the dense array entry; `scoreOf` by binary search). `lexical_build.zig`: `resolveTokens`.
- `engine.zig`: `queryTokenized` is sparse for both analyzer paths and lost its `lexical_score_output` argument; `service.zig`, `rpc.zig` (`Workspaces.lexical_scores`), `main.zig`, `cli.zig`, `abi.zig` and the tests that called them were updated. `abi.zig` edits are the query scratch only.
- `scripts/capture_query_outputs.py` (bar a capture), `scripts/qbench.py` (research-doc harness), `tests/test_query_latency.py` (criterion 3-5 test), unit test "sparse ranking equals the dense reference on random tie-heavy inputs" (400 random rounds: modes, path prefix, labels, tied scores/vectors, empty and zero vectors, candidate_k 0-70).

### Not done
- No block-max/WAND, no format change (out of scope). `Engine.query` (dense, ASCII) and `hybrid.search*` dense functions remain as reference/oracle and for `benchmark.zig`, `postings`/`publication`/`importer` tests; they still sort the corpus. The `searchd serve` result/evidence workspaces in `main.zig` are still sized by the corpus once per process (not per query).
- Posting lists must be strictly ascending by document (the segment decoder already rejects anything else); a hand-built `Index` violating that would mis-merge.
