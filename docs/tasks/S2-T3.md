# S2-T3 · Rank only the chunks that matched

**State:** verified · **Series:** S2 (research doc, learning 3) · **Depends on:** S1-T8 · **Size:** S · **Builder:** Sonnet 5 · **Tester:** Opus

Every query sorts the whole corpus three times, lexical mode included
(`zig/src/hybrid.zig:143-151`): a sampling profile puts about 94 % of query
time in `std.sort.pdq` and about 0 % in postings scoring. Measured p50 at
10,000 chunks: 8.0–11.6 ms on the M1 (0.36–0.85 ms at 1,000). Luxir's
block-max/MaxScore pruning would save nothing here; plain top-k selection
removes most of the cost.

## Acceptance criteria
1. Lexical ranks are assigned over the chunks with a nonzero lexical score
   only (a sort of the matched set, or a bounded selection when `candidate_k`
   is smaller); the semantic pass is skipped entirely in lexical mode and when
   the snapshot has zero vector dimensions; fusion runs over the union of the
   two candidate sets with the same `document_index` tiebreak
   (`hybrid.zig:231-236`); per-query scratch shrinks from three corpus-sized
   arrays (`zig/src/abi.zig:296-302`) to sizes proportional to the matched set
   plus `candidate_k`.
2. **Bar (a):** `ss_query` output is **byte-identical** to the current library
   for every judged fixture query, the ABI goldens (`zig build test-abi`), and
   200 random 1–6-word queries drawn from the 10k corpus vocabulary
   (`scripts/gen_timing_corpus.py`), in all three retrieval modes where
   vectors exist (the hybrid case on the existing vector fixtures). Paste the
   comparison method and counts.
3. **Bar (b):** lexical p50 at 10,000 chunks **≤ 2 ms** for each of the four
   queries the research doc's M2 used, on the shipped ReleaseSmall build
   through the same ctypes harness (Appendix A of the research doc; M1).
4. **Bar (c):** no query slower than today at 1,000 chunks.
5. **Plant:** with the matched-set selection reverted, the p50 test fails
   (it measures against a threshold; say how it stays robust to machine load:
   take the best of five runs and assert growth, not only an absolute).
6. All five suites green after the Report; libraries rebuilt last with
   `tool/build_native.sh`.

### What was done

Lexical channel ranks only chunks with a nonzero, authorized, in-scope score, via a bounded heap of `min(candidate_k, documents)` (a total order, `document_index` tiebreak, so the survivors are the first K of a full sort); semantic channel runs only when mode is not `lexical` and the query vector is non-empty (the ABI passes an empty vector for zero-dimension snapshots), also a bounded heap; fusion runs over the union (sort by document, merge, sort by fused score with the same tiebreak). ### The tiebreak
On `main` (`hybrid.zig` `channelComesBefore`/`comesBefore`) the order is score descending, then `document_index` ascending, for each channel and for the fused list. Only `score > 0` gets a rank, and ranks above `candidate_k` are dropped. The new `candidateBefore` and `fusedBefore` use the same key. It is a total order on non-NaN scores, so the heap's survivors are the first K of the full sort. A chunk in both lists is merged into one entry before fusion. The tie-heavy groups above are identical. **Plant:** I reversed the `document_index` comparison in `candidateBefore` only. My tie cases then differed in 11,918 of 20,334 calls, and `zig build test` failed `sparse ranking equals the dense reference on random tie-heavy inputs` (112/113). I restored the line, and the source is identical to the branch.

### Scope and risks
- **Callers.** `queryTokenized` has 4 callers, `service.zig`, `cli.zig`, `bm25_conformance_test.zig` and `incremental_indexing_test.zig`, plus `import_analyzer_test.zig` from `main` (fixed in the merge). `searchKnowledge` has 2, `abi.zig` and `rpc.zig`, and `rpc.Workspaces` is built only in `main.zig` and the RPC tests. All compile and pass. `searchd serve` and the CLI are byte-identical (above).
- **Dense path kept as the oracle.** `Engine.query` and `hybrid.search`/`searchWithLexicalScores` are unchanged and still used by `benchmark.zig`, the `importer`/`engine` tests and the new equivalence test. `searchd benchmark 2000 16 50 hybrid` builds and runs (p50 57 µs).
- **`searchd serve` allocation.** It still allocates `results`/`evidence`/`sources` by corpus size once per process. That predates this task, and the `lexical_scores` array is gone. Each request runs in its own arena (`main.zig`), so the sparse scratch is freed per request.
- **Strictly ascending postings.** `lexical_segment.decode` ends with `validatePostingOrder` (`<=` previous → `InvalidPosting`). I tested it with a temporary unit test (removed afterwards). I encoded a valid index, swapped two posting document ids and resealed the section checksum, and `decode` returned `error.InvalidPosting`. A duplicated id gave `error.InvalidPosting` too. Without the reseal it is `ChecksumMismatch`. A hand-built index that bypasses the decoder (`[2, 0, 2]`) makes `SparseScorer` yield 3 matches, doc 2 twice, then stop. So it mis-merges but does not hang or crash. Every `next()` advances at least one cursor, so it always terminates.

### Findings (none blocking)
1. **NaN cosine scores are ordered differently.** The ABI and RPC accept any finite query vector, and import accepts any stored vector. When a squared norm overflows f32 (components ≥ about 1.8e19), `cosineSimilarity` returns NaN. Both libraries then rank NaN chunks and serialise the score as `"nan"`, but in a different order. On a 120-chunk probe, query vectors `[1e30,1]`, `[1e20,0]` and `[1e18,1]` against stored `1e30` components differed in 111 of 120 calls (old ranks 4, 5, 10 vs new 1, 2, 3 for the same chunks). Ordinary vectors were identical in 120 of 120 calls. Neither order is meaningful, because `pdq` with a comparator that NaN breaks has no defined result, so byte-identity there cannot be a requirement. The fix belongs to its own task. Either treat a non-finite cosine as 0, or reject vectors whose squared norm overflows, at import and at query. That would change `main`'s output too. No embedding model produces such vectors.
2. **The `main` move needed a source edit in the merge** (above). Any S2 branch cut before `67c2fb9` that calls `queryTokenized` will need the same edit when it merges after this one.
3. **`benchmark.zig` still measures the dense reference path**, not what `ss_query` runs. Its numbers (`ranking_p50_us`) no longer describe the shipped query.
4. **Vector mode still resolves the lexical terms.** It tokenises the query and scans the dictionary, then ignores the result. `findTerm`/`findExact` are linear over the vocabulary. That cost is small, but it is wasted work. Vector mode on a zero-dimension 1k snapshot takes about 0.4 ms in both libraries, and I expect most of that is this lookup, though I did not profile it.
5. **The latency test's margins.** On the old library the growth assertion fails by about 1.4× for three of the four queries (10.9–12.7 against the cap of 8). The absolute 2 ms check fails by 4–7×. On the merge, `the and of to in` sits at growth 5.1–5.4 against 8. Under my 8-core load it held in both directions. A heavier oversubscribed machine could push the merge's 10k p50 toward 2 ms, since it took 0.75 ms under my load.
6. **The semantic channel is still a full scan.** Hybrid and vector modes compute a cosine for every in-scope chunk (O(N), now about 0.3 ms at 10k with 8-d vectors). Only the sort is gone. That is expected with no ANN, and the criteria do not cover it.
7. **The Report checks out.** The digest `fb509ee5…a1d` and the counts reproduce exactly. Its "113/113" and "80 tests"/"23" were on the pre-S2-T1 base; the merge has 116, 82 and 35. All five commits carry exactly one `Co-Authored-By: Claude Sonnet 5.5` and no `Claude-Session:` line.
