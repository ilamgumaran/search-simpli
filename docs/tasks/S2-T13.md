# S2-T13 · A cosine that is not a number must not reach the ranker

**State:** built · **Series:** S2 (found by the S2-T3 verifier, finding 1) · **Depends on:** S2-T4 · **Size:** XS · **Builder:** Sonnet 5 · **Tester:** Opus

A query vector whose components are finite but large (around 1.8e19 and
above) passes the finite check, and the cosine then overflows to NaN. NaN
breaks the sort comparison, so the order of the affected chunks is undefined:
the S2-T3 verifier saw 111 of 120 such calls ranked differently from the dense
path, against 120 of 120 for ordinary vectors. Neither order is wrong by the
contract because the contract never said; this task says. The app pins
lexical mode, so nothing on the phone is exposed today.

## Acceptance criteria
1. At the ABI, a query vector whose L2 norm is not finite (overflow, NaN, ±inf
   in any component) is rejected with `SS_ERR_INVALID_ARGUMENT` and a one-line
   message, in every mode that reads it (lexical mode still ignores the vector
   and still reports `vector_ignored`; say in the Report whether lexical mode
   validates it anyway, and why).
2. On import (`ss_import_json`, `searchd import-json`) and on folder indexing
   with vectors, a document vector whose norm is not finite is rejected with
   the same error and nothing is published.
3. The cosine itself is computed so that finite inputs cannot overflow
   (normalise before the dot product, or accumulate in `f64`): a unit test
   with components at `f32` extremes shows a finite score.
4. **Bar (a):** query output for every valid vector is byte-identical to the
   previous library on S2-T3's semantic and tie-heavy sets and on the 10k
   hybrid capture (`scripts/capture_query_outputs.py`, profile off and on).
5. **Plant:** with the norm check removed, the rejection test fails; with the
   overflow-safe cosine reverted, the extremes test fails.
6. Header, `docs/zig-engine-api.md` and the Dart `query` doc say what a valid
   vector is. Contract unchanged (an error on an input that never had a
   defined result).
7. All five suites green after the Report; libraries rebuilt last.

The squared norm of the 1.8e19 vector is just below the `f32` maximum; 2e19 overflows, the cosine is `inf/inf = NaN`, and the whole call ranks nothing. The undefined order of S2-T3's finding 1 needs stored vectors that are NaN for some chunks and not for others; I did not rebuild that 120-call probe. The new unit test shows the NaN source directly (see criterion 3).

**What was done.**
- `scoring.zig`: new `isValidVector` (all components finite, and the sum of squares accumulated in `f32`, the way the cosine does, is finite: norm below about 1.8e19; all zeros is valid). `cosineSimilarity` keeps the original `f32` loop and returns its result whenever the two sums of squares, the dot product and the denominator are all finite; otherwise it recomputes in `f64` (`cosineWide`), clamped to [-1, 1], never NaN.
- `abi.zig` `queryImpl`: in vector and hybrid mode on a snapshot with vectors, an invalid query vector returns `error.VectorNormNotFinite`; `ss_query` sets `ss_query: invalid query vector: a component is not finite or the L2 norm overflows float32 (VectorNormNotFinite)` and returns `NULL`. The same error is in `errorCode` as `SS_ERR_INVALID_ARGUMENT` for import. (Before: non-finite components gave the misleading `VectorDimensionMismatch`.)
- `rpc.zig` `parseQueryVector` (the `searchd serve` / `search_knowledge` path): the same norm rule, as "Invalid params" like its existing non-finite check.
- `importer.zig`: every non-empty document vector goes through `isValidVector` before dimensions are compared and before any file is written: `VectorNormNotFinite`, `SS_ERR_INVALID_ARGUMENT`, nothing published. The importer is shared by `ss_import_json` and `searchd import-json`.
- Header, `docs/zig-engine-api.md` (new section "What a valid vector is"), Dart `query` doc; `bindings_generated.dart` regenerated with ffigen (doc comments only).
- Tests: Zig `scoring` (extremes, ordinary-vector exactness, `isValidVector`), Zig `abi` (`S2-T13: a vector whose L2 norm is not finite ...`), Dart (`a valid query vector (S2-T13)`). `scripts/capture_query_outputs.py` gained a `--profile` flag (adds `"profile": true` to every query) to capture profile-on.

**Deviations to check.**
1. *Query door and `SS_ERR_INVALID_ARGUMENT`:* `ss_query` returns a pointer, so it has no numeric code; it returns `NULL` with the message above. `ss_import_json` returns the real `SS_ERR_INVALID_ARGUMENT` (-1). Both use one error name, `VectorNormNotFinite`.
2. *What "L2 norm is finite" means:* the norm is measured with the `f32` sum of squares, so the limit is about 1.8e19 (not "any finite `f32`"). A norm computed in `f64` would never fail for finite inputs and criterion 1 would only reject NaN and infinity. This follows the task's own text (1.8e19 and above).
3. *Lexical mode does not validate the vector.* It never reads it, so a bad vector there cannot hurt, and today's contract (S2-T4: "any vector passed, including a NaN one, no error") says it is ignored and reported with `vector_ignored`; an error would break callers (the app pins lexical mode and may pass any vector) for an input that has no effect. The unit test sends all six bad vectors in lexical mode: results, `vector_ignored` present. A snapshot with zero vector dimensions behaves the same.
4. *Folder indexing:* `searchd index` and `ss_index_folder` store `vector = &.{}` for every chunk (`indexer.zig`), so there is no vector to check; criterion 2 holds for `ss_import_json` and `searchd import-json` only.
5. *The hybrid with an all-zero vector* (S2-T4 finding T3: no depth cut and no `vector_ignored`) is unchanged; an all-zero vector is valid.
6. *Cosine arithmetic.* It did **not** change for any pair with finite sums of squares, dot product and denominator (bit for bit, the same `f32` instructions; a unit test compares to the inline original). The `f64` path is taken only when one of those overflowed, which happens only for stored vectors in snapshots written before this task (or components of about 1.8e19 and more). Such a pair used to give NaN, or 0 when the dot product was finite and only the denominator overflowed; it now gives the true cosine. Those inputs are not valid vectors, so bar (a) does not cover them.
