# S2-T13 · A cosine that is not a number must not reach the ranker

**State:** verified · **Series:** S2 (found by the S2-T3 verifier, finding 1) · **Depends on:** S2-T4 · **Size:** XS · **Builder:** Sonnet 5 · **Tester:** Opus

A query vector whose components are finite but large (around 1.8e19 and
above) passes the finite check, and the cosine then overflows to NaN. NaN
breaks the sort comparison, so the order of the affected chunks is undefined:
the S2-T3 verifier saw 111 of 120 such calls ranked differently from the dense
path, against 120 of 120 for ordinary vectors. Neither order is wrong by the
contract because the contract never said; this task says. The app pins
lexical mode, so nothing on the phone is exposed today.

## Acceptance criteria
1. At the ABI, a query vector whose L2 norm is not finite (overflow, NaN, ±inf
   in any component) is rejected with `SS_ERR_INVALID_ARGUMENT` and a one-line
   message, in every mode that reads it (lexical mode still ignores the vector
   and still reports `vector_ignored`; say in the Report whether lexical mode
   validates it anyway, and why).
2. On import (`ss_import_json`, `searchd import-json`) and on folder indexing
   with vectors, a document vector whose norm is not finite is rejected with
   the same error and nothing is published.
3. The cosine itself is computed so that finite inputs cannot overflow
   (normalise before the dot product, or accumulate in `f64`): a unit test
   with components at `f32` extremes shows a finite score.
4. **Bar (a):** query output for every valid vector is byte-identical to the
   previous library on S2-T3's semantic and tie-heavy sets and on the 10k
   hybrid capture (`scripts/capture_query_outputs.py`, profile off and on).
5. **Plant:** with the norm check removed, the rejection test fails; with the
   overflow-safe cosine reverted, the extremes test fails.
6. Header, `docs/zig-engine-api.md` and the Dart `query` doc say what a valid
   vector is. Contract unchanged (an error on an input that never had a
   defined result).
7. All five suites green after the Report; libraries rebuilt last.

**What was done.**

4. *Folder indexing:* `searchd index` and `ss_index_folder` store `vector = &.{}` for every chunk (`indexer.zig`), so there is no vector to check; criterion 2 holds for `ss_import_json` and `searchd import-json` only.
5. *The hybrid with an all-zero vector* (S2-T4 finding T3: no depth cut and no `vector_ignored`) is unchanged; an all-zero vector is valid.
6. *Cosine arithmetic.* It did **not** change for any pair with finite sums of squares, dot product and denominator (bit for bit, the same `f32` instructions; a unit test compares to the inline original). The `f64` path is taken only when one of those overflowed, which happens only for stored vectors in snapshots written before this task (or components of about 1.8e19 and more). Such a pair used to give NaN, or 0 when the dot product was finite and only the denominator overflowed; it now gives the true cosine. Those inputs are not valid vectors, so bar (a) does not cover them.

### Findings (non-blocking)
1. **No test covers the `serve` check.** With the `rpc.zig` `isValidVector` line removed, all 149 Zig tests pass. My `serve` runs show the check works: −32602 for f32 max, 1.85e19, 2e19, 1e30, 34×3.2e18 and ±1e39 in vector, hybrid and default mode. A future edit there would go unnoticed.
2. **The Dart test checks the exception type, not the message.** The existing `top_k=0` test does the same. I confirmed the message by hand (ruling 1).
3. **The `f32` cosine is inaccurate for very small vectors, and this task does not change that.** When the squares fall into or below the subnormal range (norm below about 1e-19), scores in both libraries differ from the f64 cosine by up to 0.147. A vector whose squares all underflow (for example all 1e-45) is treated as all-zero. Such vectors are valid by the new rule, so they rank. No embedding model produces them.
