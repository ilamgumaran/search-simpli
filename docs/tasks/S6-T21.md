# S6-T21: a caller's own generation number at or below the current one is refused

**State:** filed by the orchestrator, 21 Nov 2026, from `main` after the S6-T20 merge · **Depends on:** [S6-T20](S6-T20.md) (its Verdict's finding 2 and item (a)), [S6-T17](S6-T17.md) · **Plan:** [objective plan](../plans/2026-11-16-objective-plan.md), section B follow-ups and the lifecycle

## Why

After [S6-T20](S6-T20.md) a writer that numbers itself can no longer publish a
number twice or move `MANIFEST` back. A writer that **brings** its number still
can. S6-T20's verifier showed, with real processes, on `main` before and after:

- `searchd index --generation 5` (or an import numbered 5) over generation 9
  publishes 5 and moves `MANIFEST` from 9 to 5;
- `import-json` numbered current + 1, stopped before its lock while two
  rebuilds with `keep_generations = 1` run, publishes 10 again and moves
  `MANIFEST` from 11 to 10.

A number whose section files exist is already refused (`PathAlreadyExists`).
The maintainer decided on 21 Nov 2026: **refuse a caller's number at or below
the current generation, as a documented new refusal**, in its own task.

### What changed

- **The check** (`zig/src/core/generation_alloc.zig`): `requireAboveFloor(allocator, io, dir, generation)` computes
  the floor as `highestGenerationOnDisk` does (the same trace scan, factored into `highestAbove`), except that a
  `MANIFEST` that fails to decode counts as 0 (`decodableManifestGeneration`; a read error is still returned), and
  fails with `error.StaleGeneration` when `generation <= floor`. Its reads go to a local arena (the importer passes a
  general allocator, and `incremental_state.recordedGeneration` does not free: the first run leaked, caught by the
  test allocator). `describeStaleGeneration` formats the line from the same thread-local causes as
  `describeNoFreeGeneration`, through one shared `causeNames`.
- **Where it is called** (ruling 2, the note's placement): `apply.applyParsed`, right after the `expect_generation`
  check, when `dir != null` and `options.generation != null` (under the lease, before any file is read or built);
  `lifecycle.publishSerializedKeepingWithSource`, `publishSerializedWithFilenameKeeping` and `publishSerialized`,
  after the lease and before the publish, with the number decoded from `manifest_encoded` (an undecodable one is left
  to the publish, which refuses it as before). `publishSerialized` takes no allocator, so it uses
  `std.heap.smp_allocator` for the check's reads, freed before it returns; its `core.zig` doc and `docs/core-api.md`'s
  memory paragraph say so (no `api` signature changed).
- **Interfaces:** `abi.zig` maps `StaleGeneration` to `SS_ERR_INVALID_ARGUMENT` and `ss_import_json` sets the line;
  `main.zig` catches it for `index`, `import-json` and `init-demo` (`exitIfStaleGeneration`: one line, exit 1);
  `cli.zig`'s `--generation` comment and usage text.
- **API and documents:** `describeStaleGeneration` in `core.api` (86 names; the checker's pins in
  `tests/test_check_layers.py`, 85 → 86 and the one-name-more case 86 → 87; `docs/core-api.md` from the checker's
  line); `core.zig` docs of `indexFolder`, `importer` and `publishSerialized`; the header's Errors summary and

### The interleavings, observed (task ruling 1)

**How the probe works** (`probe_caller_race.py.txt`):

- **Process A** brings its own number: the folder's generation + 1, or 1 for `init-demo`. It is
  `searchd index --generation 10`, `searchd import-json`, a C program calling `ss_import_json` on the build's dylib,
  or `searchd init-demo` into an empty directory.
- **The stop.** A runs under `lldb --batch` and is stopped once, either before its lease (`tryAcquireWriter` entry)
  or inside it (`publication.publishWithExtrasRecorded` entry, after the check and before any link).
- **Process B** runs to completion while A is stopped. B is one or two full rebuilds (k=1 means
  `--keep-generations 1`), `--update` twice with k=1, an import with the same number or the next one,
  `--generation` with the same number, an import k=1 followed by a rebuild k=1, or `init-demo`.
- **No timing is involved**, and nothing runs in the background.

### The builder's three decisions, my view

- **`publishSerialized` allocating from `smp_allocator`.**
  - *Bounded:* it reads `MANIFEST` and `INDEX-STATE.json` at their file sizes, with no cap. That is the same
    allocation `nextFreeGeneration` makes on every self-numbered rebuild.
  - *Freed:* the reads go to an arena that `requireAboveFloor` frees by `defer` on every path.
  - *Safe on failure:* `OutOfMemory` comes before any link. One caveat, pre-existing: `recordedGeneration` swallows
    every error, `OutOfMemory` included, so under memory pressure `INDEX-STATE.json` silently drops out of the floor,
    here as in `nextFreeGeneration`.
  - *Precedent:* the core already takes scratch from `smp_allocator` and `page_allocator` in `apply.zig`,
    `analyzer_v2.zig` and `lexical_build.zig`, so this is not a new pattern.
  - *View:* acceptable as it is. An allocator parameter would be the cleaner `api` shape and would remove the one
    exception to "Allocates nothing". Its only non-test caller is `init-demo`, so take that when `lifecycle`'s `api`
    is next touched, not as a rework.
- **`init-demo` refused over a non-empty directory.**
  - *The documents are right:* the usage text says "as generation 1 (so into a fresh <dir>)", and
    `zig-rpc-service.md` says the second run is refused and the existing demo serves (run, `checks.txt`).
  - *The message is not:* its tail, "publish a higher number", is advice `init-demo` cannot take, because it has no
    number to choose.
  - *View:* a small wording improvement for later, not a defect.
- **Dart `code` null.**
  - *Consistent:* every `ss_import_json` failure is spelt without `SS_ERR_<CODE>`, and the Dart function drops the
    integer. The CHANGELOG and the Dart doc state it, and the Dart test pins it.
  - *The cost:* a Dart caller can tell `StaleGeneration` apart only by matching the message text.
  - *View:* acceptable for this task, which may not change a contract. Passing the integer code through
    `importSnapshotJson` would be a separate, contract-level change, for the maintainer.
