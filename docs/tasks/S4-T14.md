# S4-T14 · A line map is checked where its file is read: the reader isolates the file, and the writer's open stops walking every map

**State:** ready (starts from `main` after the S4-T13 merge, `c208d3c`) · **Date:** 2026-11-06 · **Depends on:** S4-T10 (the streamed source open and the per-call SHA-256), S4-T13 (the writer's open computes each checksum once; the line-map walk kept and filed) · **Size:** M

**Owner:** the Xcode Mac orchestrator · **Orchestrator:** Claude Fable 5.1 · **Builder:** Claude Opus 5.5 (local) · **Verifier:** Claude Opus 5.5 (local, a different agent)

**Why.** The source section's line maps are checked twice over, both times for the whole folder, and both checks are paid where a phone feels them. **The reader:** the first `read_span` or `outline` on a handle streams the section's text (S4-T10), computes the section checksum, and walks every file's line map against its bytes (`validateLineMap`, `validateLineMapStreamed`); on the 10k corpus that first read costs 9.7–9.8 ms (`ReleaseSmall`, S4-T13's verifier), and S4-T13's scratch split put the line-map walk at about 10.3–10.5 ms of the writer's otherwise identical open, so the walk is most of it. A later `read_span` already checks the one file it reads against its SHA-256 and answers `capacity` naming the check for that file alone (S4-T10), so a per-file guard at the point of use is the section's existing pattern. **The writer:** `apply.openPrevious` walks every line map of the previous generation (about 10.4 ms of its 21.5 ms open, S4-T13 Report), and S4-T13 kept that walk only because the reader refuses a checksum-valid section with one bad line map **whole**, at first use, for every file, and every later update would carry the map again (S4-T13 finding 1; the `03-next.md` row). Checking a line map when, and only when, its file is read removes the reason for both whole-folder walks: a bad map then costs that one file its `read_span` and `outline` until the file changes and is re-scanned, every other file answers, and `index_status` keeps reporting what it reports today, because the section checksum is still computed over the streamed text at first use. No format, manifest, contract or ABI change; the writer's bytes do not change (a check is removed, nothing is encoded differently), so every index stays byte-identical and nothing is rebuilt on any phone.
