# S4-T14 · A line map is checked where its file is read: the reader isolates the file, and the writer's open stops walking every map

**State:** ready (starts from `main` after the S4-T13 merge, `c208d3c`) · **Date:** 2026-11-06 · **Depends on:** S4-T10 (the streamed source open and the per-call SHA-256), S4-T13 (the writer's open computes each checksum once; the line-map walk kept and filed) · **Size:** M

**Owner:** the Xcode Mac orchestrator · **Orchestrator:** Claude Fable 5.1 · **Builder:** Claude Opus 5.5 (local) · **Verifier:** Claude Opus 5.5 (local, a different agent)

**Why.** The source section's line maps are checked twice over, both times for the whole folder, and both checks are paid where a phone feels them. **The reader:** the first `read_span` or `outline` on a handle streams the section's text (S4-T10), computes the section checksum, and walks every file's line map against its bytes (`validateLineMap`, `validateLineMapStreamed`); on the 10k corpus that first read costs 9.7–9.8 ms (`ReleaseSmall`, S4-T13's verifier), and S4-T13's scratch split put the line-map walk at about 10.3–10.5 ms of the writer's otherwise identical open, so the walk is most of it. A later `read_span` already checks the one file it reads against its SHA-256 and answers `capacity` naming the check for that file alone (S4-T10), so a per-file guard at the point of use is the section's existing pattern. **The writer:** `apply.openPrevious` walks every line map of the previous generation (about 10.4 ms of its 21.5 ms open, S4-T13 Report), and S4-T13 kept that walk only because the reader refuses a checksum-valid section with one bad line map **whole**, at first use, for every file, and every later update would carry the map again (S4-T13 finding 1; the `03-next.md` row). Checking a line map when, and only when, its file is read removes the reason for both whole-folder walks: a bad map then costs that one file its `read_span` and `outline` until the file changes and is re-scanned, every other file answers, and `index_status` keeps reporting what it reports today, because the section checksum is still computed over the streamed text at first use. No format, manifest, contract or ABI change; the writer's bytes do not change (a check is removed, nothing is encoded differently), so every index stays byte-identical and nothing is rebuilt on any phone.

## Rulings
1. **Profile first, in the Report, before any change.** `main` at `c208d3c`, the 10k timing corpus (`scripts/gen_timing_corpus.py <dir> 10000`, `corpus_matches_recorded: true`), `ReleaseSmall`, load stated and below 3.0. **The reader:** the first `read_span` on a cold handle (filename channel on, as `scripts/source_read_parity.py time --filename` measures it; 30 samples) split in a scratch build into: the block read (header, file table, maps), the text stream with its checksum, the line-map walk, the sparse index; then a later `read_span` of a small file and of the largest file. **The writer:** `open_previous` and its `source_open` sub-stage from `scripts/s4t4_budgets.py profile` (S4-T13's timers), ten runs, off and on. Numbers in a table, p50 and worst.
2. **The reader checks a line map where it reads the file.** The streamed open at first use (`openStreamed` and whatever `scope.readSource` calls) keeps the manifest and size checks, the header, the file table walk with every rule `TableWalk` applies today (bounds, path validity and order, gap-free text and map offsets, `finish`), the bounds of each map's varints (`varintsEnd`, so a map that runs past its region is still refused whole), and **the section checksum over the streamed text** (so `index_status` still moves from `unverified` to `verified` or `unavailable` on the same evidence as today), and **stops validating line maps against bytes there**. `read_span` and `outline` validate the one file's map against the bytes they have just read and checked by SHA-256 (`fileBytes`, S4-T10), with `validateLineMap`'s rules and error (`InvalidLineMap`), **once per file per handle** (a per-handle record of which files have passed, sized by the file count, counted in the NFR-13 peak), building that file's sparse checkpoints then if the implementation keeps a sparse index per file (the builder decides between a per-file sparse index built at first read and a walk of the map's varints from the start for each call, and states the cost of each at the largest file of `fixtures/family-folder`, 1,133,158 B). A file whose map fails answers `capacity` `"re-index required: source section unavailable (InvalidLineMap)"` through the same path as `SourceFileSha256Mismatch` does today, **for that file only**; every other file still answers; `index_status` is unchanged by it. The resident open (`source.open`, `openIndexed`: `index_folder`'s retention, the tests, the Python reference) keeps validating every map, unless the builder shows the resident path also serves a phone read, in which case it follows the same rule and the Report says where. **Tests:** (a) a 10k-style fixture (the family folder is enough) with one file's line map corrupted and the section and manifest re-sealed: that file's `read_span` and `outline` answer `capacity` naming `InvalidLineMap`, every other file's `read_span` and `outline` answer as before, `find` and `search_knowledge` are unaffected, and `index_status` reports `verified`; (b) the same section with one byte of text flipped and the manifest **not** re-sealed is refused whole at first use as today (`ChecksumMismatch`, `unavailable`); (c) a map that runs past the maps region is refused whole (`InvalidLineMap` from the walk, as today); (d) the second `read_span` of a validated file does not validate again (a counter in a test build, or the timing in ruling 5); (e) the existing damage table in `source.zig`'s tests keeps every case, with the cases that were caught by the whole-section walk moved to the per-file read and the expected error named per case.
3. **The writer's open stops walking every map.** `apply.openPrevious` opens the previous source section with the checks ruling 2 keeps for the reader (checksum once against the manifest, S4-T13; the table walk; each map's varint bounds) and **without** `validateLineMap` over every file. A carried record copies the map as today (`carriedRecord` already bounds it with `varintsEnd`); a fresh or changed file is scanned and hashed as today (S4-T11 ruling 3). **Tests:** (a) S4-T13's 3(b) is inverted and extended: a previous section with one re-sealed bad line map is **carried** by an update that changes another file (generation published; the carried file's `read_span` on the new generation answers `capacity` naming `InvalidLineMap`; every other file answers), and an update that changes **that** file replaces its map (its `read_span` answers); (b) a previous section whose stored checksum disagrees with the manifest is refused (`SourceSectionChecksumMismatch`, kept); (c) a previous section with a map running past its region is refused (`InvalidLineMap`, kept); (d) parity: an untouched previous generation gives a fresh index's sections byte for byte (S4-T13's 2(d)/3(c), kept).
4. **The record in the docs says why this is sound.** `docs/source-section-v1.md`: "Reading" gains what first use checks and what each read checks; "The writer's guard (S4-T13)" is rewritten as "The writer's guard (S4-T13, S4-T14)": the checksum refuses a damaged section, the table walk and the varint bounds refuse a malformed one, and a checksum-valid map that disagrees with its bytes (only a wrong writer makes one) now costs its one file its reads until that file changes, so neither the reader at first use nor the writer at its open walks every map. `docs/incremental-indexing.md`'s source bullet and "The writer's open" paragraph follow. `docs/folder-knowledge-implementation.md`'s `read_span`/`outline` sentence (line 286) names `InvalidLineMap` beside the SHA-256 check as a per-file answer. `docs/requirements/cap-19-folder-knowledge.md`: the NFR-12 line and its status row gain the numbers (bound unchanged). `docs/journey/03-next.md`: a top entry in S4-T13's form; the row *The writer's line-map check of the previous source section (filed by S4-T13)* struck "Done by S4-T14"; a *Consumer app: pin bump to S4-T14* row in the S4-T13 row's form, naming what the phone gains (the first `read_span` or `outline` on a handle, and every save).
