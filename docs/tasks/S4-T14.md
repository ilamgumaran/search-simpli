# S4-T14 · A line map is checked where its file is read: the reader isolates the file, and the writer's open stops walking every map

**State:** ready (starts from `main` after the S4-T13 merge, `c208d3c`) · **Date:** 2026-11-06 · **Depends on:** S4-T10 (the streamed source open and the per-call SHA-256), S4-T13 (the writer's open computes each checksum once; the line-map walk kept and filed) · **Size:** M

**Owner:** the Xcode Mac orchestrator · **Orchestrator:** Claude Fable 5.1 · **Builder:** Claude Opus 5.5 (local) · **Verifier:** Claude Opus 5.5 (local, a different agent)

**Why.** The source section's line maps are checked twice over, both times for the whole folder, and both checks are paid where a phone feels them. **The reader:** the first `read_span` or `outline` on a handle streams the section's text (S4-T10), computes the section checksum, and walks every file's line map against its bytes (`validateLineMap`, `validateLineMapStreamed`); on the 10k corpus that first read costs 9.7–9.8 ms (`ReleaseSmall`, S4-T13's verifier), and S4-T13's scratch split put the line-map walk at about 10.3–10.5 ms of the writer's otherwise identical open, so the walk is most of it. A later `read_span` already checks the one file it reads against its SHA-256 and answers `capacity` naming the check for that file alone (S4-T10), so a per-file guard at the point of use is the section's existing pattern. **The writer:** `apply.openPrevious` walks every line map of the previous generation (about 10.4 ms of its 21.5 ms open, S4-T13 Report), and S4-T13 kept that walk only because the reader refuses a checksum-valid section with one bad line map **whole**, at first use, for every file, and every later update would carry the map again (S4-T13 finding 1; the `03-next.md` row). Checking a line map when, and only when, its file is read removes the reason for both whole-folder walks: a bad map then costs that one file its `read_span` and `outline` until the file changes and is re-scanned, every other file answers, and `index_status` keeps reporting what it reports today, because the section checksum is still computed over the streamed text at first use. No format, manifest, contract or ABI change; the writer's bytes do not change (a check is removed, nothing is encoded differently), so every index stays byte-identical and nothing is rebuilt on any phone.

### The code read (`git diff c208d3c -- zig/src/`)

- **`Section.fileBytes`.** For a streamed section it reads the file's `text_length` bytes
  positionally, checks them against the record's SHA-256 (`SourceFileSha256Mismatch`), and
  then, only when the file's bit is clear, runs `validateLineMap` over a copy of the entry
  whose `bytes` are that buffer. The bit is set (`markChecked`, `fetchOr` with `.release`)
  only after the check returns. A failure returns `unavailable` with `@errorName(err)`,
  the same path as the SHA-256 mismatch, and leaves the bit clear, so every later call
  checks again. `mapChecked` loads with `.acquire`: a reader that sees the bit sees
  everything before it. The maps are immutable bytes of the handle's resident block, so
  the pairing is sufficient. Two threads may both check one file the first time (both
  pass or both fail); neither can set the bit before its own check passes. A resident
  section (`checked` empty) answers "checked": `open` and `openIndexed` validated every map.
- **Where a map is decoded.** `lineOffsets` (whose `next()` calls are `catch unreachable`)
  is called only from `readSpan`, and `readSpan` now calls `fileBytes` first whenever
  `mapChecked` is false, so no unchecked map is ever decoded. `outline` decodes no map (it
  uses `line_count` and the bytes). `find` sets `FileEntry.position` on both branches
  (`withCheckpoints` on the binary search, the counter on the scan) and `file` likewise;
  the service's `readSpan` passes a path, so the entry always comes from `find`. Every
  other line-map user is the writer's `carriedRecord`, which bounds the map again by
  `varintsEnd` (p3 shows it as the second guard).
- **`openStreamedWith`.** The table walk runs first (`walkTable(.bounds)`) and its error is
  held; the text is streamed whole through a buffer of at most 1 MiB for the checksum; a
  checksum mismatch is answered first, then the held walk error, as `open` orders them.
  The record words come from `index_allocator` ((n + 63) / 64 words, zeroed); no sparse
  index is built. The buffer minimum fell from 3 to 1 because no look-ahead remains;
  `drain` handles any size, and a zero-byte text area reads nothing.
- **`TableWalk` with `varintsEnd`.** `walkTable` applies `TableWalk.next` (bounds, path
  validity and order, gap-free text and map offsets) to every record, then adds the map's
  byte length, `mapLength`: `varintsEnd(line_map, 0, line_count + 1)` or
  `InvalidLineMap`. The next record's map offset must equal that sum (`InvalidFileTable`
  otherwise, the Report's finding 1), and `finish` requires the maps region consumed
  exactly (`InvalidLineMap`). So a map that runs past the region, or ends a varint early,
  is still refused whole; only the map's agreement with its bytes moved to the read.
- **`openTable`.** `Index` with offsets only, `residentSection`, `walkTable(.bounds)`,
  `record_offsets` set; no checkpoints and no record (`checked` empty). Its section
  answers `mapChecked` true, which matters only to a reader. The writer reads no span
  from it and copies each map through `carriedRecord`. `openPrevious` calls it after
  `inspect` and the stored checksum against the manifest's, unchanged from S4-T13.
- **`nextBreakCandidate` beside `isBreakAt` (ruling 2).** `isBreakAt` answers non-zero
  only when the byte at the index is 0x0a, 0x0b, 0x0c, 0x1c, 0x1d, 0x1e (width 1), 0x0d
  (1, or 2 before 0x0a), 0xc2 (2 before 0x85, else 0) or 0xe2 (3 before 0x80 0xa8/0xa9,
  else 0). `nextBreakCandidate`'s lanes admit `x −% 0x0a < 4` (0x0a–0x0d), `x −% 0x1c < 3`
  (0x1c–0x1e), `x == 0xc2` and `x == 0xe2`, and its scalar tail the same nine values: the
  sets agree byte for byte. `isBreakAt` still reads its look-ahead from the whole file's
  slice, so a block edge cannot split a break. In `validateLineMap` the skip runs only
  while a line is open (a line start is recorded first), and a candidate that is not a
  break advances by one, as before.
- **The four test cases ruling 2 lists are all in the candidate test.** That test places
  each piece after `gap` filler bytes, three times, for `gap` 0–39, and compares
  `validateLineMap` with `lineStarts`. The scan starts at offset 0, so `gap` 15 puts the
  piece at the first block's last byte. (1) A CR at the last byte of a block with LF at
