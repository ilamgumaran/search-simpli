### Criterion 1 (rework): `max_total_bytes` on a non-`update` run, and the CLI split

`indexer.indexFolder` (`zig/src/indexer.zig`) now carries its own
`total_bytes_processed`/`over_budget` accumulator, mirroring
`indexFolderIncremental`'s: once a file would push the running total past
`caps.max_total_bytes`, that file and every later candidate are left out of
the generation and counted under `budget_exhausted`. Unlike the
incremental path, a full rebuild has no previous generation to carry a
left-over file's chunks forward from, so it is simply absent from the new
generation (same outcome as `too_large`, different field) — documented in
the updated doc comments and `docs/incremental-indexing.md` below.
`indexFolder`'s `added` count now subtracts `budget_exhausted` too.

`added: 3 → added: 0, unchanged: 3`. The tester also checked the update is not

repeated-term file, and a Tamil heading), queried before and after the first
`--update`, give byte-identical JSON — same chunk ids, same line ranges, same

postings path handles a generation published by a full rebuild.

Two hazards probed and **not** reproducible, recorded so nobody re-derives them:
writing state on a full rebuild could in principle let a later `--update` trust
hashes against a generation published by some other route (`carryForward`
appends nothing when the previous engine has no document for that path, which
