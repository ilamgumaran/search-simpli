# S4-T18 · The library's `memcpy` stops copying one byte at a time

**State:** ready (starts from `main` at `60f0e01` or later) · **Date:** 2026-11-06 · **Depends on:** S4-T17 (the finding: its `03-next.md` row "`find`'s remaining `memcpy` is a byte loop" and the counting-`memcpy` method), S4-T16 (the `floor.documents_memcpy` measurement), S4-T14 (the reader's open and read path) · **Size:** M

**Owner:** the Xcode Mac orchestrator · **Orchestrator:** Claude Fable 5.1 · **Builder:** Claude Opus 5.5 (local) · **Verifier:** Claude Opus 5.5 (local, a different agent)

**Why.** The natives are built `ReleaseSmall`, and in that mode Zig 0.16's `compiler_rt` provides `memcpySmall`, a byte-at-a-time loop, as the library's `memcpy` (S4-T17's finding, from the symbols-kept object and a counting `memcpy` in a scratch build). Every copy that reaches `memcpy` therefore costs about a cycle per byte: S4-T16 measured the plain copy of the 9,273,775-byte documents section at 2.42 ms (3.8 GB/s, one byte per cycle), and S4-T17 found `find` sending 2.11 MB through `memcpy` in 73,890 calls for 0.57 ms of its 3.44. The same loop sits under the writer's section encodes (the documents `write` 2.69 ms, the lexical encode, the source copy 2.2 ms), the state encode, the publish's buffers, the reader's open and `read_span`, and `ss_find`'s output copy. A platform `memcpy` (macOS and iOS `libSystem`, Android `bionic`) or a word-wise copy moves tens of bytes per cycle. The library already links libc on every target (`zig/build.zig`, `link_libc = true`), so the question is which `memcpy` the linker binds and why `compiler_rt`'s wins today.
