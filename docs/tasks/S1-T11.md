# S1-T11 · Bundle lookup: the app's own Frameworks folder before the bare name

**State:** verified (2026-10-08; ready 2026-10-08) · **Series:** S1 · **Depends on:** S1-T10 · **Size:** XS · **Builder:** Sonnet 5.5 · **Tester:** Opus 5.5

From the S1-T10 Verdict, findings 1 to 3, 6 and 7. The bare-name step (`DynamicLibrary.open('libsearch_simpli.dylib')`) is tried first, and dyld searches the current directory and `/usr/local/lib` (an rpath the Flutter engine carries) **before** `Contents/Frameworks`. A stray copy in either place would load instead of the one shipped with the app, and would also beat `native/` in a development checkout. Ruling: the app's own copy comes first.

## Acceptance criteria
1. On macOS and Linux the order becomes: the `SEARCH_SIMPLI_LIBRARY_PATH` override; then `<executable dir>/../Frameworks/libsearch_simpli.dylib` (Linux: `<executable dir>/lib/libsearch_simpli.so`); then the bare name; then the existing candidates unchanged. The unit tests' expected order changes accordingly, and the error message lists paths in the new order. Plant: with the two steps swapped back, the order test fails; paste it.
2. **Proof it matters:** in the S1-T10 probe bundle, place a *decoy* `libsearch_simpli.dylib` in the process's cwd (a copy of the real library whose `ss_version()` string is patched, or simpler: a tiny dylib that exports `ss_version` returning `"decoy"`) and show that on `origin/main` the decoy loads (version `decoy`) while on this branch the bundled library loads (version `1.0.0` or whatever `CONTRACTS_VERSION` reads). Both runs pasted, sandbox off (the sandbox hides the cwd decoy, which is itself worth one line in the Report).
3. `tool/bundle_probe.sh` exits non-zero when any run fails to answer, and its entitlement line prints the actual Bool value (`grep -A2` or equivalent) so the off and on runs can be told apart. It removes its temp workdir on exit (trap), and says in a comment that `~/Library/Containers/com.example.probeApp` is left by macOS.
4. `PROJECT-STATE.md`'s loader bullet and the README's "cwd `/`" sentence describe the new order and say that a sandboxed process starts in its container. `docs/zig-engine-api.md`'s paragraph updated to the new order.
5. Dart-only: nothing under `zig/`, `include/`, `contracts/`, `native/`, no stamp change. All five suites green after the Report (`source ~/development/env.sh`; `flutter pub get`; `SEARCH_SIMPLI_LIBRARY_PATH` unset); tails pasted; home and temp paths redacted (`<home>/…`, `<tmp>/…`).

### Findings (none blocking)
1. **(b), judged: inside an app, the loader should refuse a bare-name hit.** Once the exact Frameworks path has missed, every place the bare name can reach in a bundle lies outside what the app ships. That means the cwd (when unsandboxed), the engine's rpaths (`FlutterMacOS.framework/Versions/A/`, `/usr/local/lib`), `Contents/MacOS/`, Xcode's `PackageFrameworks/` and `/usr/lib` (trace above). The README already says an app must ship the library in `Contents/Frameworks`, so a bare-name hit there can only be a stray copy. Today that turns a packaging mistake (the library not embedded) into a silent load of whatever dyld finds. The `ss_version` check is the only guard, and it catches only a different contract string; a stale `1.0.0` build would pass. The simplest fix: when the executable sits in `*.app/Contents/MacOS`, do not try the bare name at all; the `StateError` already tells the developer to bundle the library. Checking the mapped file with `dladdr` after a bare-name hit would also work, at more cost. On Linux the risk is smaller, because glibc's `dlopen` does not search the cwd unless `LD_LIBRARY_PATH` says so; I could not test it. This is for the orchestrator. The criteria as written keep the bare name, and the build meets them.
2. **A development checkout still has the shadowing problem.** Outside an app the Frameworks path is absent, and the bare name still runs before `native/`. A stray `libsearch_simpli.dylib` in the cwd (shown above, both loaders) or in `/usr/local/lib` therefore beats the package's own copy under `dart run` and `dart test`. That is the second half of what this task's opening paragraph named; the ruling fixed the app half. Moving the bare name after the checkout candidates when not in a bundle would close it. README item 3 is headed "inside a built app", which reads as if the bare name did not run in a checkout.
3. **"can never win" is too strong.** The README, the loader's comment and `docs/zig-engine-api.md` say it, and `PROJECT-STATE.md` says "cannot win". It holds only when the app ships its copy. With no copy in the bundle, the stray copy wins (run (b)). "cannot win over a bundled copy" would be exact.
4. **The probe app leaves its snapshot copies.** Each run leaves two `ss_probe_*` folders in `$TMPDIR` and two in the container's `Data/tmp` (the part of S1-T10 finding 4 that criterion 3 did not cover). A `finally` that deletes `dir` in the probe app would end it. I deleted the ones my runs made.
5. Cosmetic: the probe prints `probe workdir (removed on exit): <tmp>//ss-bundle-probe.…` with a double slash, because `$TMPDIR` ends in `/`.
