# S1-T0 · C ABI and library builds for the Zig engine

**State:** built (round A, Thursday 17 Sep, alongside S1-T1) · **Depends on:** ADR 0002 · **Size:** M · **Builder:** Sonnet 5 · **Tester:** Opus 5

## Acceptance criteria
1. `zig/include/search_simpli.h` + `zig/src/abi.zig`: `ss_open(dir) -> handle`, `ss_close`, `ss_status(handle) -> JSON`, `ss_query(handle, text, vec, dims, k, opts JSON) -> JSON`, `ss_evidence(handle, ids JSON) -> JSON`, `ss_import_json(dir, bytes)`, `ss_free(ptr)`, `ss_version()`; every function documented; errors as negative codes + `ss_last_error()`; no global mutable state beyond the handle.

3. A C test harness (`zig/tests/abi_test.c`, built by `zig build test-abi`) opens the demo snapshot, queries, reads evidence, and compares against the golden JSON-RPC results byte for byte.
4. `contracts/CONTRACTS_VERSION` introduced (`1.0.0`) and returned by `ss_version()`; `docs/zig-engine-api.md` gains the ABI section.
5. `zig build test` and the Python tests green; Report has the exact commands.

### Design decisions worth flagging to the tester

- **Handle and allocation.** `ss_open` allocates the handle and every decoded
  workspace from `std.heap.c_allocator` (real `malloc`); `ss_free` is
  literally `std.c.free(ptr)`. This is safe specifically because every
  pointer this library returns was allocated at `u8` alignment, for which
  Zig's `c_allocator` always uses the `.raw` `malloc` path with no header
  (verified by reading `lib/std/heap.zig`'s `c_allocator_impl.alloc`) — so
  the pointer `ss_free` receives is exactly the pointer `free()` expects.
  There is no lookup table and no other global state; `ss_last_error()` is
  a `threadlocal` diagnostic buffer, analogous to `errno`/`strerror`, not
  engine state.
- **I/O without `std.process.Init`.** `ss_open`/`ss_import_json` are library
  entry points with no process-provided `std.Io`. They use
  `std.Io.Threaded.global_single_threaded` — the standard library's
  ready-made synchronous, non-concurrent `Io` — so no thread pool is started
  and no cleanup is required.
- **`ss_query` is byte-identical to the RPC path by construction, not by
  coincidence.** I extracted `rpc.writeSearchResultValue` (the
  `search_knowledge` response's `result` object) and `rpc.writeChunkFields`
  from the existing JSON-RPC code and made both `pub`; `abi.zig` calls them
  directly. `zig build test-abi`'s golden strings are not hand-written: they
  are the literal `result`/`read_chunk` fields of a real
  `zig build run -- init-demo` + `serve` session, pasted below. Because the
  code path is shared, `ss_query`/`ss_evidence` reproduce that output
  exactly rather than approximately.
- **`ss_query`'s signature** matches the task file literally:
  `ss_query(handle, text, vec, dims, k, opts JSON)`. `top_k` (`k`) is a
  direct parameter; `retrieval_mode`, `candidate_k`, `path_prefix`, and
  `principal_labels` live in `opts JSON`, mirroring `search_knowledge`'s own
  parameter set minus `query`/`query_vector`/`top_k`.
- **`ss_evidence`'s `ids JSON`** is an object,
  `{"ids": [...], "path_prefix": ..., "principal_labels": [...]}`, not a
  bare array, so scoped/authorized lookups are possible without a second
  function. Each id is looked up independently through `Service.readChunk`;
  an unknown or unauthorized id never fails the whole call, it just comes
  back as `{"chunk_id": "...", "found": false}` in that position.
- **Error convention.** Pointer-returning functions (`ss_open`, `ss_status`,
  `ss_query`, `ss_evidence`) return `NULL` on failure. `ss_import_json`, the
  one integer-returning function, returns a negative `ss_error_code`
  (`SS_ERR_INVALID_ARGUMENT` … `SS_ERR_INTERNAL`, defined in both the header
  and `abi.zig`). `ss_last_error()` gives the human-readable reason either
  way. This is a direct, literal reading of criterion 1
  ("errors as negative codes + `ss_last_error()`"); I did not invent an
  additional out-parameter convention for the pointer-returning functions.
- **Android needs an explicit libc.** Zig 0.16 has no bundled libc for
  `aarch64-linux-android` (confirmed by hand: `zig build-lib -target
  aarch64-linux-android -dynamic -lc` fails with
  `unable to provide libc for target ...-android.29` and suggests `gnu`/
  `musl` instead). `build.zig`'s `androidLibcFile` reads `SS_ANDROID_NDK`
  and writes a `--libc` paths file pointing at
  `$SS_ANDROID_NDK/toolchains/llvm/prebuilt/<host>/sysroot`, with `crt_dir`
  at API level 29 (an arbitrary modern default — every level from 21 up
  ships under the same sysroot, so this is a one-line change later). Without
  `SS_ANDROID_NDK` set, `zig build lib` prints a warning and skips only the
  Android artifacts; `aarch64-macos` and `x86_64-linux` use Zig's own
  bundled libc and need no extra configuration. Static libraries do not
  strictly need the NDK sysroot at all (verified: `zig build-lib -target
  aarch64-linux-android -static -lc` referencing `std.heap.c_allocator`
  succeeds without `--libc`), but `androidLibcFile` is applied uniformly to
  both linkages for simplicity.
- **`zig build lib`'s Android warning also prints during `zig build test`**
  (visible in the pasted output below): `addAbiLibraries` runs at graph
  configuration time, which Zig always does regardless of which step is
  requested, so the "SS_ANDROID_NDK is not set" note appears even for
  unrelated steps when the variable is absent. It is a `std.debug.print`
  note, not an error, and does not affect `test`'s pass/fail.

### Not done / narrowed scope

- No iOS, Windows, or Linux arm64 library targets — ADR 0002 explicitly
  defers those ("when the app needs them").
- `ss_evidence` does not expose ranking (`lexical_rank`/`fused_score`/...);
  those only exist relative to one query's `Result`, which `ss_evidence`
  does not take. `ss_query`'s own `results` array already carries per-chunk
  ranking; `ss_evidence` is for looking up chunks by id afterward (e.g. from
  a previously stored chunk id), matching `read_chunk`'s scope exactly.
- No Dart/other-language bindings (ADR 0002 step 4) — out of scope for this
  task.
- The `zig build lib`/`test-abi` steps were not asked to run under
  `-Doptimize=ReleaseFast`/`ReleaseSafe`; only the default (Debug) and
  `ReleaseSmall` were measured, since criterion 2 only asks for sizes, not a
  specific optimize mode.
