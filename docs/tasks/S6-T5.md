**Where `content` computes each warning, and from what state.** All of it is collected in a `hybrid.Trace` that only
`ss_query` creates (`abi.queryImpl`), and written by `report.zig`:

| Code | Computed in | From |
|---|---|---|
| `query_term_unmatched` | `Engine.queryTraced` → `lexical_build.resolveTokensTraced` (analyzer-v2) or `postings.resolveQueryTraced` (the ASCII analyzers) | each distinct analysed query term, in query order, that the body dictionary lacks or that `postings.hasInScopePosting` finds in no chunk the trace's scope allows (roots mask, path prefix, labels, set from the options at the top of `queryTraced`). **Chunks alone:** the title field (folders and stem) is not consulted, so under `content` a word only a file's name holds is reported unmatched though the title part scored it (fuzzy-v1's guard 4 keeps it from being expanded). |
| `query_term_grouped` | `Engine.queryTraced` → `computeGroups` (`fold.compute`) → `noteGrouped` | the fold groups, copied into `trace.grouped` (the typed term left out of `members`); analyzer-v2, lexical channel, `options.fold` |
| `query_term_expanded` | the same → `fuzzy.compute` on the ungrouped tokens → `noteExpanded` | the fuzzy-v1 groups, copied into `trace.expanded` |
| `query_empty_after_analysis` | the same resolvers | `trace.unique_terms == 0` |
| `vector_ignored` | `abi.queryImpl` | a vector passed and not used (lexical mode, or no vectors stored) |
| `candidate_depth_cut` | `hybrid.searchSparseTraced` | `trace.lexical_candidates`, `semantic_candidates`, `depth`; in lexical mode only when `candidate_k < top_k`, which `ss_query` refuses |

`report.write` (from `ops.writeSearchResult` when `extras` is given, which only `abi.queryImpl` does) writes the
array: `query_empty_after_analysis`; then each unmatched term's `query_term_unmatched`, followed by its
`query_term_expanded` and its `query_term_grouped`; then the `query_term_grouped` of the grouped terms that are not
unmatched, in query order; then `vector_ignored`; then the depth cuts. An expanded group is only written after its
term's unmatched warning; under `content` that always holds, since fuzzy-v1 triggers only on a word no chunk in
scope holds.

### 2. The plan, and what it is expected to cost (ruling 8, stated before measuring)

**What changes.** `Engine.queryFieldsTraced` (and `queryFields` calls it with no trace) fills a trace under `both`
and `filename` only when `ss_query` asks:

- **`both`:** `bothGroups` notes its fold and fuzzy-v1 groups in the trace before it merges them (the same
  `noteGrouped`/`noteExpanded`); the content resolver (`resolveTokensTraced` / `resolveQueryTraced`, the very code
  `content` runs) records the unique terms and `content`'s unmatched terms; then an unmatched term is dropped when a
  file name visible to the file-name channel holds it (the term in the file-name dictionary with a posting on a file
  that `hybrid.inScope` allows). A term with an expansion is never dropped (an expansion needs no visible title to
  hold the word, so with a title field the case cannot arise; the rule only keeps an expansion from going unreported
  on an engine opened without one).
- **`filename`:** each distinct analysed term (the same spelling and order as `content`'s) is counted, and unmatched
  when no visible file name holds it. No group is computed, so no `expanded` or `grouped` warning can appear.
- `filename_response.writeAbiEvidence` writes the array with `report.zig`'s own `hasWarnings`/`writeWarnings` (made
  `pub`, their code unchanged), so codes, order, messages and member lists are `content`'s. As under `content`,
  `query_empty_after_analysis` and `vector_ignored` follow from the same state (an empty query; a vector passed to a
  lexical request); `candidate_depth_cut` cannot occur (lexical, `candidate_k >= top_k`).
- No other surface changes: `queryFields` without a trace runs as before, and the writers that print no `warnings`
  key are untouched. No schema field, no format, no signature.

**"A visible file name"** is read as the file-name channel's stem, visible as that channel sees it (roots, labels and
the path prefix). A word only a file's **folder** names hold (the title field, not the file-name channel) stays
unmatched under `both`, as it is under `content` today; it is listed in the open questions.

**Expected cost** (warm requests, `ReleaseSmall`, the three 10k corpora; queries of one or two words):

- **`content`: none.** No `content` code path changes (`report.zig`'s two functions only become `pub`). The library's
  layout does change, so `content` cells can move by placement alone, by the amounts `main`'s own controls showed in
  S6-T4 (up to about ±0.3 µs on 3–8 µs cells). If a `content` cell fails the rule, I report it and do not rearrange
  code (ruling 8).
- **`filename`: about +0.2 to +0.6 µs per request**, plus about 0.1–0.2 µs per warning written. The work added: the
  query tokenized once more (analyzer-v2 NFC and fold of a few bytes), per distinct term one binary search of the
  file-name dictionary and a read of that term's postings up to the first visible file (one posting when nothing is
  hidden), an arena copy of each unmatched term, and the warning objects. On `filename` cells of 2–5 µs this is
  5–25 %: it will be beyond the controls' band (clause 2) in most runs, and far below T = 0.010 ms (clause 1).
- **`both`: about +0.3 to +1.0 µs per request**, plus the warnings written: one more tokenization, per distinct
  term one binary search of the body dictionary and one in-scope posting read (`content`'s resolver), the copy of
  the groups' strings into the trace (only for a grouped or expanded word: `system`, `bazecha`, `systems system`),
  and the file-name lookup for each `content`-unmatched term. On `both` cells of 6–700 µs this is under 0.2 % on
  the large ones and up to about 15 % on the 6–8 µs ones; again beyond the band, below T.
- Nothing is kept between requests and nothing is computed for the CLI, JSON-RPC or MCP.
