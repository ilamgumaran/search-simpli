# S2-T11 · A query must never hang: reject invalid UTF-8 at the door

**State:** verified · **Series:** S2 (found by the S2-T4 verifier, finding N2) · **Depends on:** S2-T4 · **Size:** S · **Builder:** Sonnet 5 · **Tester:** Opus

On any `analyzer-v2` snapshot, a query whose text holds a byte that cannot
start a UTF-8 sequence (`\xff`, `\xfe`, a lone continuation byte such as
`\x80`) **hangs forever**, in every retrieval mode, through `ss_query` and
through `searchd`. The likely cause is `nfc.hasAnyCombiningOrDecomposable`
(`zig/src/nfc.zig`, around line 55) walking unvalidated bytes before the
UTF-8 check. Dart always passes valid UTF-8, so the app is not exposed today;
a C caller or a `searchd` user is. On an `ascii-alnum-v1` snapshot the same
query succeeds and echoes `query` as a byte array, which the search-tool
schema rejects (S2-T4 verifier, N3).

## Acceptance criteria
1. `ss_query` validates `query_text` as UTF-8 **before any analysis**, in every
   mode and for every analyzer, and rejects invalid text with
   `SS_ERR_INVALID_ARGUMENT` and a one-line message; nothing else about valid
   queries changes. `searchd query`, `evidence` and `serve` report the same
   rejection (exit status and a line on stderr; a JSON-RPC error for `serve`).
2. The analyzer itself cannot loop on invalid input: `nfc.zig` and the v2
   tokenizer are fixed so that **any** byte string terminates, with a unit
   test that feeds every single byte 0x00–0xFF and 2,000 random byte strings
   of length 1–64 and asserts completion (bounded by the test runner).
3. **Bar (a):** a fuzz run of 100,000 random byte strings (lengths 0–256,
   half of them mutated valid UTF-8) through `ss_query` on a v2 snapshot and
   on a v1 snapshot completes in bounded time with no hang, crash or leak
   (run under the leak-checking allocator in Debug for the Zig path).
4. **Bar (b):** query output for every **valid** query is byte-identical to the
   previous library (S2-T3's capture sets through
   `scripts/capture_query_outputs.py`, profile off and on; the 18 invalid-UTF-8
   cases are the only expected differences, and they now error).
5. **Plant:** with the validation removed, the hang test fails (use a watchdog
   in the test, not the suite timeout) and the byte-array echo returns.
6. Header, `docs/zig-engine-api.md`, the search-tool schema notes and the Dart
   `query` doc say that `query_text` must be valid UTF-8 and what happens
   otherwise. Contract unchanged (an error on an input that was never valid).
7. All five suites green after the Report; libraries rebuilt last.

### What was done
- **Door.** `Engine.validateQueryText` (`engine.zig`: `std.unicode.utf8ValidateSlice`, `error.InvalidQueryText`). `ss_query` calls it right after the null-handle check, before options, vector, top_k or any analysis; `Engine.queryTraced` calls it again first (the last door: `searchd`, `serve` and tests all end there).
- **Analyzer.** `nfc.normalize` validates the whole input first and returns `error.InvalidUtf8`; `hasAnyCombiningOrDecomposable` now walks a validated `Utf8View` (and stops, rather than reaching an `unreachable`, if ever handed bad bytes). `analyzer_v2.tokenize` goes through `normalize`, so it ends on any bytes.
- **CLI.** `cli.parseArgs` judges the text of `query` and `evidence` like every other argument: `searchd: invalid value for query text (not valid UTF-8)`, one line, exit **2** (S1-T8). The message does not echo the bytes.
- **serve.** The JSON line is parsed by `std.json`, which already refuses raw invalid bytes and lone `\udc00` surrogates with `-32700 Parse error` (the request is answered and the server keeps going). I added the same guard in `rpc.handleSearch` (`-32602 "Invalid params: query is not valid UTF-8"`); through a JSON line it is unreachable, so it is defence, and it is exercised only through the engine-level test.
- Tests: `zig/src/query_utf8_test.zig` (registered in `root.zig` twice), a CLI test in `cli_test.zig`, `tests/test_query_utf8.py` (child process per call, 30 s hard timeout, shipped library), a `searchd` process test in `tests/test_cli_process.py` (query/evidence exit 2 + one line on both analyzers; `serve` answers errors for the two bad lines and a result for the next), a check in `zig/tests/abi_test.c`.
- Docs: header (`query_text` clause and the NULL list), `docs/zig-engine-api.md` (new subsection), `docs/tool-protocol.md` (`query` parameter), Dart `query` doc; `bindings_generated.dart` regenerated by ffigen (comment-only diff). `scripts/capture_query_outputs.py` got `--profile` and `--invalid {none,v1,both}`.

### Deviations to check
1. **`ss_query` has no numeric return**, so "rejects with `SS_ERR_INVALID_ARGUMENT`" is implemented as `NULL` plus `ss_last_error()` = `ss_query: query_text is not valid UTF-8 (SS_ERR_INVALID_ARGUMENT)`. 2. **Leak check for the `ss_query` path.** `abi.zig` allocates with `c_allocator` and `ss_free` is `std.c.free`, so the Zig test allocator cannot back it (I tried; 18 tests aborted, reverted). The shipped C-allocator path itself has no leak detector in this test.

In Debug the plant fails by crash. `tests/test_query_utf8.py` is the real-process hang test against the shipped library (the hang is OS-visible), per the new ROLES rule.

  - truncated at the end and in the middle (`\xe2\x82`, `price \xe2\x82`, `\xf0\x9f\x98`, `\xc3`, `café \xf0\x9f`, `\xe2\x82a`, Tamil cut by one byte);
  - lone continuation runs, `hy\0\xff`;
  - 15 valid strings: `café` NFC and NFD, Tamil, emoji, a ZWJ family, a flag, Hangul, BOM, U+FFFE, U+10FFFF, Å/Å, ligatures, NBSP, empty.
- **Results:**
  - **4,512 rejected** (282 per run) with the exact message;
  - **4,352 answered** (272 per run, `query` a string), **byte-identical to the old library**;
  - **0 mismatches** against Python's strict UTF-8 decoder, applied to the text before its first NUL;
  - longest call 0.30 ms; no hang or crash.
- **1 MB timings** (best/median of 5):
  - a 1 MB string with one bad byte at the end: rejected in **1.01 / 1.02 ms** (mixed scripts) and **0.36 / 0.37 ms** (ASCII);
  - a bad byte at the start: 0.34 ms, which is about the cost of `strlen` plus ctypes;
  - so validation is linear and fast.
  - A valid 1 MB query answers identically in both libraries: 5.5 ms on v1, **13.1 s on v2** (the old library takes 13.1 s too; finding 4).

### Non-blocking findings
1. **No Dart test covers the native rejection, and none can through `query`** (ruling 1). `toNativeUtf8` calls `utf8.encode`, which replaces a lone surrogate with U+FFFD. A malformed Dart `String` is therefore searched as U+FFFD silently, not rejected. The doc's "so it always is" is accurate. It could add that lone surrogates become U+FFFD.
2. **The `-32602` guard in `rpc.handleSearch` cannot be reached through JSON, and no test reaches it.** `std.json` refused all 15 invalid lines with `-32700`. The Report says the guard is "exercised only through the engine-level test", but that test calls `Engine.validateQueryText`, not `handleSearch`. This is the S2-T13 pattern again: the `rpc.zig` checks are untested. `zig-engine-api.md` and `tool-protocol.md` name `-32602` as a possible answer, which holds only as defence in depth.
3. **The checks are layered three deep** (the `ss_query` door, `Engine.queryTraced`, the analyzer). This is good, but it means removing one layer does not bring the hang back; the Report's plant removed all three. My layered plants show each layer is load-bearing for what its test asserts.
4. **Pre-existing, both libraries: `analyzer-v2` query time grows quadratically with non-ASCII query length.**

   | Query length | Mixed scripts | ASCII |
   |---|---|---|
   | 64 KB | 58 ms | 3.0 ms |
   | 128 KB | 223 ms | 6.1 ms |
   | 256 KB | 832 ms | 12.2 ms |
   | 1 MB | 13.1 s | |

   A long non-ASCII query blocks the caller for seconds. This is a candidate for its own task: a query-length cap, or a linear NFC/tokenize step.
5. **`Engine.query`** (the dense reference path through `postings.scoreQuery`) does not validate. Only benchmarks and tests call it, and its ASCII scorer does not loop, so no outside door is affected.
6. **The old `searchd query <v2> caf\xff` (ReleaseSmall)** crashed with SIGSEGV (exit 139) here; the Report saw exit 0 with no output. The behaviour is undefined either way and is gone on the merge.
