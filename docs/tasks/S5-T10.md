## Source

The MCP adapter passes conformance and parity tests, which show that the tools return what JSON-RPC returns. They do not show that an agent given those tools and the skill text answers a person's question from the right file and cites it. This task measures that once, reproducibly. **No engine source, contract or native changes.** It adds a frozen task set, a harness, transcripts and a report.

## Rulings

1. **The snapshot.** The J2 fixture as committed at the task's base (`fixtures/j2/`, invented content), indexed by the `ReleaseSmall` `searchd` built from that commit, with the file-name channel on, three roots, and one root or label hidden from the agent's principal. The index's generation, the binary's hash, the source commit and the policy ids are recorded. S5-T8 is extending J2 on its own branch at the same time: this task reads `fixtures/j2/` and does not edit it.
2. **The tasks, frozen before any agent run.** At least 24, in one committed file, written as a person would ask, each with its expected outcome: at least four each of (a) find a file by name, (b) answer from a passage with a citation, (c) a question where the name locates the file and a passage answers, (d) no answer in the folder, (e) the answer exists only in the hidden root (the right outcome is "not found", and nothing of the hidden file is named), (f) after a refresh: a file edited, a file renamed, a file deleted, applied through the allowed write path between runs. Expected outcomes name the file and, for (b) and (c), the lines that support the answer.
3. **The agent is real.** A model session that is given only the MCP tools of `searchd mcp` (default mode, read-only, the principal fixed on the command line) and the skill text, and a task's question. It is not given the fixture, the expected outcomes or this task file. The builder's own session writes the harness and judges; a separate agent session per batch of tasks answers. How the agent reaches the server (a stdio MCP client the harness provides as the agent's only tool, or the agent runtime's own MCP support) is the builder's choice, stated exactly. The model and its version are recorded. Each task is run once; a second run of the whole set gives the spread.
4. **What is checked per task**, by a script from the transcript where it is machine-decidable and by the builder's reading where it is not, with both labelled: the tools called in order; whether a `read_span` or chunk read preceded the answer; whether the cited file and lines exist in the generation named and support the answer; for (a) whether a name match was used to locate and not as evidence of content; for (d) and (e) whether the agent said it found nothing, and whether any hidden path, title or text appears anywhere in the transcript.
5. **The verdict against CAP-13.** The Report applies §9's acceptance gate and §10's line as written and counts: supported answers, unsupported answers, wrong source, negative cases handled, scope failures. **A scope failure of any count is reported at the top.** The task does not change CAP-13's status: it records the evidence and says what a maintainer would need to decide. No threshold is invented.
6. **What is kept.** The task set, the harness, both runs' transcripts (tool calls and results; the agent's free text), and the identifiers of ruling 1, under `docs/evidence/s5-t10/` or the place `EXPERIMENTS.md` conventions name. Transcripts hold fixture content only.
7. **Findings become rows, not fixes.** A tool description that misled the agent, a result field it needed and lacked, or a skill sentence it misread is recorded in 03-next with the transcript reference. Nothing in `skills/`, `contracts/` or `zig/` is edited here.
8. **Documents.** `EXPERIMENTS.md` (hypothesis, setup, observed, limits), `PROJECT-STATE.md`, 03-next, the review's R11 marked with what was measured.
