## Source

`searchd apply` on a directory with no index creates one with the file-name channel off, and takes no option to turn it on. `searchd index --filename-index` and the C ABI's open options can. So `scripts/j2_run.py` first indexes an empty folder (leaving an empty root `r-legacy`) and then applies its real roots. This task gives `apply` the option, for a fresh index only.

### 1. Inventory (ruling 1), written before any code

Read from the source at `54f4919` and probed with a `ReleaseSmall` `searchd` built from it in a scratch copy with fresh caches (`before`).

**Where the capability lives.** The file-name channel is the directory's, recorded per generation: manifest v2.2 flag bit 3 binds a filename catalog and a filename lexical section (`manifest.Meta.filename != null`; `engine.filename_index_enabled` is that test, `apply.zig` `decodeMetadata`). Nothing else stores it. Every generation is written by one function, `apply.applyParsed`, and its setting is `apply.Options.filename_index: ?bool`: `true` builds the two sections (`buildGeneration`, `options.filename_index orelse false`), `false` builds none, `null` keeps the directory's (a directory with no `MANIFEST`: none).

**How each path sets it today.**

| Path | Option | Fresh directory | Existing index |
| --- | --- | --- | --- |
| CLI `index` | `--filename-index` → `Caps.filename_index = true`; absent → `null` | channel on when given | full rebuild with a different setting: `FilenameMigrationRequiresNewDirectory`; `--update`: `FilenameSettingMismatch` (both an uncaught Zig error, exit 1, probed) |
| CLI `apply` | **none**: `runApply` passes only `allow_file_reads`, so `null` | channel off (probed: a fresh `apply` writes no filename sections; a `--search-field filename` query is `FilenameIndexUnavailable`) | keeps the setting (probed: the channel survives an `apply` onto an `index --filename-index` directory). `apply --filename-index` today is `unknown flag for apply` (exit 2, no directory created, probed) |
| C ABI `ss_apply_changes` | `opts_json.filename_index` (`ops.parseApplyOptions` → `apply.Options.filename_index`), contract 2.2.0 and later | on when `true` | `true` on a plain index: `FilenameSettingMismatch`, which `abi.errorCode` does not list, so it surfaces as `SS_ERR_INTERNAL` (by reading; not changed here) |
| C ABI `ss_index_folder` | `opts_json.filename_index` → `Caps` | as CLI `index` | as CLI `index` |
| Dart | `ApplyChangesOptions.filenameIndex`, `IndexFolderOptions.filenameIndex` → the two `opts_json` | as the ABI | as the ABI |
| `serve --allow-write`, `mcp --allow-write` (`apply_changes`) | none: `rpc.zig` and `mcp.zig` pass `allow_file_reads` and the write scope only, so `null`; the tool schema `apply_changes.request` has no such field | not reachable: both open an existing index at start | keep the setting |

So the option exists in the core, the C ABI, the Dart binding and the frozen format document (`docs/filename-field-format-v1.md`, "Process contracts": "Index options add optional boolean `filename_index` … CLI spells it `--filename-index`"); only the CLI `apply` parser lacks it.

**What `apply` does with the directory today.** `runApply` opens `<dir>` with `createDirPathOpen`, so a missing directory (and its parents) is created (probed: `apply new/deeper/idx` publishes generation 1). Then `applyParsed` takes the writer lease (`WRITER.LOCK`, created if absent, never truncated), reads the current generation (`0` when there is no `MANIFEST`), checks `expect_generation`, then the setting: with a `MANIFEST` and `filename_index == null` it adopts the manifest's setting; with a `MANIFEST` and a non-null value that differs it returns `FilenameSettingMismatch` (not a full rebuild) before anything else is opened or written; with the same value it continues, and refuses a channel index whose analyzer differs (`FilenameMigrationRequiresNewDirectory`; the CLI `apply` is always `analyzer-v2`, and without the option such an index fails later as `AnalyzerMismatch`). An empty directory, or one with no `MANIFEST`, takes the fresh path: no previous generation (or `recovered: missing_manifest` when an `INDEX-STATE.json` is left), the generation is `generation_alloc.nextFreeGeneration` (1 in an empty directory; above any leftover trace otherwise, S2-T14), and the roots are exactly the request's. The `r-legacy` root is made only by `indexer.walkAndApply` (the `index` walk), never by `apply`.

### 2. Specification against the code (ruling 2)

`searchd apply <dir> --changes <file> --filename-index` sets `ApplyArgs.filename_index`, and `runApply` passes `apply.Options.filename_index = true` (the same field `ss_apply_changes` sets); without the flag it passes `null` as today. No change-file field, no contract, schema, format, ABI or Dart change: **the option is a CLI flag alone, so ruling 2's stop condition does not arise.** The cases, as the code meets them:

- **Fresh directory, option given:** the fresh path above with the channel built: one publication of exactly the requested roots, generation 1 in an empty or missing directory, the two filename sections in it. No engine change is needed.
- **Fresh directory, option omitted:** `null`, the call is today's. To be checked byte for byte (every file of the directory compared with `before`'s output for the same request; result in section 5).
- **Existing index with the channel, option given:** the setting matches and the call proceeds as without the option. One edge: a channel index built `--analyzer v1` (only `index` can make one) is refused either way, but the error name would differ (`FilenameMigrationRequiresNewDirectory` with the option, `AnalyzerMismatch` without); `runApply` reports the second for the first when the flag was given, so the outcome is the same.
- **Existing index without the channel, option given:** `applyParsed` returns `FilenameSettingMismatch` before reading the previous generation or writing anything; `runApply` turns it into one stderr line naming the reason and exit status 2. The only file such a call can create is `WRITER.LOCK`, and only when absent (every searchd writer, `index`, `apply` and `import-json`, leaves one), as for every other refusal today.
- **Other subcommands:** only the `apply` branch of `parseInner` reads the flag; `index --filename-index` is untouched.

Readings I take, named so they can be ruled on (none contradicts the code):

1. "Usage-class error" = exit status 2 and one line on stderr, nothing on stdout, as S1-T8's usage errors; it is decided after the directory is read, so it is printed by `runApply`, not by `parseArgs`.
2. The option given twice is accepted and means what once means, as every boolean flag of this parser (`--json`, `--allow-file-reads`, `index --filename-index`).
3. "The first generation": generation 1 in an empty or missing directory; in a directory holding traces of a crashed write it is the next free number (S2-T14), and it is still the first generation published there.
4.
