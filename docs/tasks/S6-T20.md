# S6-T20: a full rebuild chooses its generation number under the writer lock

**State:** filed by the orchestrator, 21 Nov 2026, from `main` after the S6-T17 merge · **Depends on:** [S6-T17](S6-T17.md) (its Verdict showed the gap), [S6-T13](S6-T13.md), [S6-T16](S6-T16.md) (the public core API) · **Plan:** [objective plan](../plans/2026-11-16-objective-plan.md), section B follow-ups ("generation numbering in interfaces") and the lifecycle

## Why

[S6-T17](S6-T17.md)'s ruling 2 was "never a number already used". Its verifier
showed, on `main` and on the task's head alike, that two writers can still
republish a used number: a full rebuild chooses its number with
`generation_alloc.nextFreeGeneration` **before** it holds `WRITER.LOCK`
(`interfaces/abi.zig` and `interfaces/cli.zig` call it, then
`indexer.indexFolder` builds, then the publish takes the lock). A second writer
that publishes in between leaves the first with a number that is no longer
free. The verifier's probes saw `MANIFEST` go from 11 back to 10 with
`keep_generations = 1`, and `PathAlreadyExists` in other orders.

An update (`apply.zig`) does not have the gap: it takes the lease first and
reads, numbers, builds and publishes inside it.

The maintainer was asked on 21 Nov 2026 how to close the gap and chose:
**choose the number under the writer lock**, with a design note first. Refusing
a stale number at publish time was the alternative and was not chosen.

The same change answers a follow-up in [core-api](../core-api.md): the
interfaces should not be numbering generations at all.

### Part 2: the change

1. The full rebuild chooses its number inside the lease it publishes under.
   One lease, taken once: no release and retake between choosing and
   publishing.
2. `interfaces/abi.zig` and `interfaces/cli.zig` no longer call
   `generation_alloc.nextFreeGeneration`. If nothing in `ops/` or
   `interfaces/` uses it afterwards, it leaves `core.api`, and
   `docs/core-api.md` is updated from the checker's output.
3. Tests, in `zig/src/core/` or `zig/src/tests/` as fits, using the seam
   S6-T17's tests use where it helps:
   - the verifier's two probes from S6-T17 as tests: with a second writer
     publishing while a full rebuild is between choosing and publishing, the
     second writer is refused with `WriterBusy`, no number is published twice,
     and `MANIFEST` never goes backwards;
   - a caller-supplied number that is not free is refused under the lease,
     and nothing on disk changes;
   - each test fails on `main` (show it: the test run against the code before
     the change, in the evidence) and passes on the head.
4. Documents: `docs/generation-lifecycle.md` (the two-writer section now says
   what is true; remove "known gap" wording only where the gap is closed),
   `PROJECT-STATE.md`, `docs/journey/03-next.md`, the Dart CHANGELOG and
   version if the libraries change (they will).

## Rulings

1. **No number is published twice, and `MANIFEST` never goes backwards,** for
   any interleaving of two writers that both honour `WRITER.LOCK`. This time
   the claim must be shown, not stated: the tests in What 3, and the Report
   says which interleavings are covered and which are argued from the code.
2. **No contract, header or format change.** No new error code, no new field.
   `WriterBusy` is already a documented refusal. If the design needs a new
   refusal, stop and report.
3. **Answers and the read path do not change.** Only writer code changes.
4. **Natives are rebuilt and restamped** (`tool/build_native.sh`,
   `SOURCE-SHA256` in the same commit as any change to its inputs), sizes in
   bytes against `main`'s. The timing rule of 2026-11-17
   (`docs/process/ROLES.md`) applies as written: say what it requires for a
   writer-only change, and do that.
5. **The same tests run,** plus the new ones: both S6-T15 guards pass, and the
   Report gives the count before and after.
6. **Stop before:** changing what `apply` does; changing the lock file or how
   it is taken; any change to pruning; anything in `contracts/` or
   `zig/include/`.

**Argued from the code, not tested:**
- the other writer arriving after the rebuild's publish and before it releases the lease (`INDEX-STATE.json`,
  pruning): the same lease is held, so `WriterBusy`, as at `after_choice`;
- the mirror of `during_walk` (the rebuild running whole inside another writer's unlocked walk): the other writer
  then chooses under its own lease, above the rebuild's number, by the same code (`applyParsed`);
- three or more writers: each self-numbered publish reads `MANIFEST`'s generation and chooses above every trace on
  disk while it holds the lease, and no cooperating writer can move `MANIFEST` without the lease, so by induction
  over publishes `MANIFEST` only goes up and no number repeats (decision 0003, section 2);
- two processes: the tests run both writers in one process. `tryAcquireWriter` opens `WRITER.LOCK` anew and takes
  `flock` on that open file description, which conflicts within one process and across processes alike; the
  cross-process case is not run here (S6-T17's verifier probes ran `searchd` processes on `main`).
- Not covered at all: writers that do not honour the lock, file systems without working `flock`, a folder synced
  between machines, and a caller's own number (next section). Decision 0003, section 6.

### The interleavings, observed (ruling 1)

Process A is a full rebuild (`searchd index notes --out out`, or `ss_index_folder(out, notes, NULL)` from a C program).
It runs under `lldb --batch` and is stopped once at a named function or line. While it is stopped, process B, another
`searchd` not under the debugger, runs; then A continues. The order is fixed by the breakpoint, and no timing is
involved. Each case starts from a folder at generation 9. Every case was run with and without `--keep-generations 1` on
A and on B, against the head's and `main`'s Debug `searchd`. A helper of B's records whether `WRITER.LOCK` is held while
A is stopped (a non-blocking `flock`).

| Where A is stopped | B (separate process) | Head | `main` |
| --- | --- | --- | --- |
| `pre_walk`: `indexer.indexFolder` entry (after the interface, before the walk; lock free) | `index` (full), `--update`, `apply`, `import-json` (number = current + 1) | B publishes 10, A publishes **11**; 9 → 10 → 11 | B 10; A **`PathAlreadyExists`** (it had chosen 10 in `cli.zig`) |
| | `--update` twice | B 10, 11; A publishes **12** | k=1: A publishes **10 again, `MANIFEST` 11 → 10**; without k: `PathAlreadyExists` |
| `walk`: `indexer.zig:106`, inside the folder walk (lock free) | all of the above | as `pre_walk`: A takes the next number above B's | as `pre_walk`: `PathAlreadyExists`, or with k=1 10 again over 11 |
| `choose`: `nextFreeGeneration` entry | all | lock **held**; B `WriterBusy` (each try); A publishes 10 | lock free (this call is in `cli.zig`, before the walk); B publishes, A chooses above it |
| `build`: `apply.buildGeneration` entry (number chosen, nothing published) | all | lock held; B `WriterBusy`; A publishes 10; 9 → 9 → 10 | the same |
| `published`: `incremental_state.savePointer` entry (after the publish) | all | lock held; B `WriterBusy`; 9 → 10 → 10 | the same |
| `release`: `WriterLease.release` entry (published and pruned) | all | lock held; B `WriterBusy` | the same |
| Mirror: A = `--update` stopped in its walk, or `apply` at `applyParsed` entry (before its lease) | one or two full rebuilds | A publishes above every rebuild (11 or 12) | the same |
| Mirror: A = `import-json` (number 10, the host's current + 1) at `tryAcquireWriter` entry | one rebuild, or two without k | A `PathAlreadyExists`; `MANIFEST` stays at B's | the same |
| | two rebuilds, k=1 | **A publishes 10 again, `MANIFEST` 11 → 10** | the same |

### Findings, by severity

1. **Medium: no test guards "one lease, taken once" (Part 2.1). The code meets it; a regression would pass.**
   - *Checked by:* six mutations, each in a fresh archive with empty caches and a full `zig build test`
     (`mutations.txt`).
   - *Caught (3 tests fail each):* choosing the number before the walk, choosing it before the lease, and skipping
     the `WriterBusy` check. Before this task no existing test caught the last two. Skipping the publish's taken-name
     check (`renamePreserve` → `rename`) is caught by the caller-number test and two `publication` tests.
   - *Not caught (590/599 pass):* releasing and taking the lease again **after** the choice, and the same **before**
     the choice.
   - *Why it matters:* the first of these is a real fault. As a `searchd`, stopped between its release and its retake
     while another process runs `--update` twice with k=1, it publishes 10 again and `MANIFEST` goes 11 → 10.
   - *Why the test misses it:* the race test's `after_choice` point fires at the `stat` of `state-10.hybstate`, which is
     inside `nextFreeGeneration`. That is before the choice returns, so nothing runs between the choice and the publish.
   - *Rework I suggest:* a third point after the choice. Either the publish's first section link, or the close of the
     lease's `WRITER.LOCK` handle, which a seam on `fileClose` can see. The maintainer may accept the gap instead: the
     interval is covered by my real-process probes (`build`, `published`, `release`) on the head as it stands.
2. **Medium, pre-existing, for the maintainer: ruling 1 does not hold for a writer that brings its own number, even an
   honest one.**
   - *The case:* a host prepares `import-json` with the folder's generation plus one (10), as it would number it from an
     open. Two full rebuilds with `keep_generations = 1` run before it takes the lock. The import then publishes 10 again
     and `MANIFEST` goes 11 → 10, on the head and on `main` (`mirror.txt`).
   - *The static case (3a):* `--generation 5` and `import-json` with generation 5 over generation 9 publish 5 and move
     `MANIFEST` 9 → 5, the same on both trees (`caller-and-order.txt`).
   - *What the builder disclosed:* the static case (decision 0003 section 4, the Report, `generation-lifecycle.md`, the
     CHANGELOG), scoping ruling 1 to self-numbered writers.
   - *What the Report overstates:* its argued claim that in "the mirror of `during_walk` ... the other writer then
     chooses under its own lease, above the rebuild's number" is true for `--update` and `apply`. It is false for
     `import-json`, which the Report's own table lists as an "other writer" and which chooses nothing.
   - *Why it is not a rework:* closing it means refusing a stale or low number under the lease, a new refusal that
     ruling 2 forbids.

### For the maintainer

1. **3a, a caller's number.** Whether to refuse a free number at or below the current generation under the lease, for
   `searchd index --generation N`, `ss_import_json`/`importSnapshotJson` and `searchd import-json`. *Facts:* on `main`
   and head alike, `--generation 5` or an import numbered 5 over generation 9 publishes 5 and moves `MANIFEST` 9 → 5.
   An import honestly numbered as the current generation plus one republishes a used number (10 over 11) when two
   rebuilds with `keep_generations = 1` run before it takes the lock (finding 2). A number whose sections exist is
   already refused with `PathAlreadyExists`, publishing nothing. Refusing a low one would be a new refusal, on the C ABI
   too, with no existing error that fits (decision 0003 section 4). So ruling 1 holds only for self-numbered writers.
2. **3b, the error order.** Whether `WriterBusy` before `NoFreeGeneration`, and `NoFreeGeneration` after the walk, needs
   more than the CHANGELOG line and `generation-lifecycle.md`. *Facts:* finding 7. No header, contract, Dart or document
   text promises the old order, and the full rebuild now behaves as `--update` already did.
3. **Finding 1's test gap.** A small rework (one more seam point after the choice), or accept it as covered by these
   real-process probes.
4. **The controls' sign (finding 6).** Whether controls that add 248–252 B match a head that removes 256 B. The builder
   stated that reading in the orders before measuring.
