## Source

S6-T3 measured the index at 4.05 times the files on 10,000 prose notes and showed by re-encoding that the lexical section's postings, dictionary and document lengths can be coded in about a fifth of their bytes (22 % of the whole index on the timing and prose corpora, 10 % on Tamil), with no change to what any query returns. This task builds that as lexical format v3, for the content and the file-name lexical sections.

## Rulings

1. **Phase 1, design and measurement, then stop for a ruling.** Written into the Report before any engine code:
   - the v3 format, as a draft `docs/lexical-segment-format-v3.md`: header, sections, every field's coding, validation rules (bounds, strictly rising document numbers, counts that must agree, checksum), and what a reader does with a damaged or truncated section. Positions and offsets sections are **not** recoded in this task (offsets are step 3);
   - how today's reader uses each part (what is read in place, what is decoded at open, what is lazy), from the code;
   - the decode strategy, measured with a prototype on the timing, prose and Tamil 10k corpora (`scripts/gen_prose_corpus.py` and the others, as S6-T3): **(i)** decode everything at open into today's in-memory layout; **(ii)** keep the coded bytes and decode a term's postings when a query first needs them, with and without a small cache; **(iii)** anything better you find (for example skip entries per block so a term decodes without touching others). For each: open time, resident memory after open and after a query set, warm query time on the J2 pack and the timing queries (`content`, `filename`, `both`), `find`, and one-file update, against today's;
   - how the format is identified and how versions coexist: the manifest field or flag that names the lexical version, what an old library does when it meets v3 (it must refuse cleanly, never misread), what a new library does with v2 (reads it; the next publish writes v3), and what that means for the app's indexes on phones at the next pin;
   - whether contracts, the C header, the Dart version or any tool schema must move, with the precedent you followed (S4-T1's checksum flag and manifest v2.1);
   - proposed bars for Phase 2 from your measurements (size per corpus; open; warm query; `find`; one-file update; resident memory), using the placement-control method of S5-T12 for timing cells (two control builds; a cell fails only beyond the band of the controls in both runs, or at +0.010 ms or more whatever the cause).
   Stop after Phase 1 and report. The orchestrator rules on the strategy and the bars before Phase 2.
2. **Phase 2, the build** (after the Phase 1 ruling): writer and reader for v3 for both lexical sections; the v2 reader kept; `import-json`'s v1 path untouched; every existing index readable.
3. **Same answers.** Every query, `find`, outline, read and status result is identical between an index written as v2 (by `main`) and the same folder written as v3, over the J2 pack, the fixtures, the family-folder pack, the timing, prose and Tamil corpora and all three fields, apart from fields that name the format. The J2 gate is clean without re-recording.
4. **Compatibility tests.** A v2 index committed as a small fixture (or built by a pinned `main` binary in the test) opens and answers under the new library; an update of it publishes v3 and the result answers identically; a crash between writing and publishing leaves either the complete v2 generation or the complete v3 one; a v3 section with each kind of damage (truncated, a gap of zero, a count too large, a bad checksum, a front-coded prefix longer than the previous term) is refused with the existing corruption error, never a crash or a misread. A fuzz-style test that flips bytes of a small v3 section must never crash the reader.
5. **Plants**, each in its own scratch copy with its own Zig cache: the tf-in-low-bit rule decoded the wrong way round; the last block or last term dropped by an off-by-one; the v2 reader removed. Each must fail tests.
6. **Natives.** Rebuilt with the documented toolchain and stamped; sizes and the growth of each library stated (a bar for growth is set at the Phase 1 ruling).
7. **Suites and CI.** Zig Debug and ReleaseSmall, C ABI, Python with and without Zig, Dart; layers, requirements and home-path checks; CI green on the final commit, native J2 included.
8. **Documents.** `docs/lexical-segment-format-v3.md` final; `docs/index-size.md` gains a "Landed" note with the measured sizes against its projection; the plan, 03-next row D2-1, `PROJECT-STATE.md`; a migration note for consumers. `README.md` only if a number it states changes. `IMPROVEMENT-BOARD.md` is not edited.
