#### 1. The format (draft: [`docs/lexical-segment-format-v3.md`](../lexical-segment-format-v3.md))

`HYBLEX03`, version 3, an 88-byte header (v2's 80 plus the decoded term-text length before the checksum). Flags:
bit 0 XXH3-64 required, bit 1 "sections 4 and 5 present", so one magic serves the content and the file-name
sections. Section 1: varint lengths. Section 2: front-coded, strictly sorted (shared prefix ≤ 255 and ≤ the previous
length, suffix length ≥ 1, suffix, df, the list's coded bytes). Section 3: per term, `(gap << 1) | (tf == 1)` varints,
a tf varint (≥ 2) when the low bit is 0; first gap absolute, later gaps ≥ 1, every document below the count
(< 2^31). Sections 4 and 5 byte for byte v2's. Checksum over everything, checked before any count; then bounds from
the counts before any allocation; then every count that must agree (Σdf = posting count, Σlist bytes = postings
bytes, term text = header, no byte left over). A damaged or truncated section fails the checksum at open; a section
whose checksum passes but whose content breaks a rule is refused with the existing corruption error, never misread.

Prototype codec tests (in the scratch copy, `zig test` of `lexical_segment.zig`, Debug): round trip with and without
positions; a flipped byte without a new checksum (`ChecksumMismatch`), truncation, a zero gap, a document past the
count, tf 1 stored explicitly, a shared prefix longer than the previous term, counts too large, an unknown flag, the
XXH3 flag cleared — each refused; every byte of two small sections flipped with five masks and the checksum
recomputed: 1,279 refused, 456 accepted as other well-formed sections (a changed tf, letter or average length),
no crash.

#### 3. Decode strategies, measured

**The variants** (one prototype source tree; `-Dlex_lazy` is a comptime option, so the eager build has no lazy
branch):

- `today`, `today-b`: `main`'s library (`fa462d65…`, byte-identical to the committed native) on the v2 index, in
  two processes (process noise; not a placement control).
- (i) `eager-v3`: v3 decoded at open into today's arrays (`TermEntry`, `Posting`, lengths); the decoded term text
  in one exact block; the section bytes stay resident as today.
- (ii) lazy: open decodes the header, lengths and dictionary (with each term's list offset from `list bytes`) and
  keeps section 3 coded; a term's list is decoded at its first use into a per-handle cache (atomic slot per
  term, a lock on the miss path; each query resolves its terms' lists once). `lazy-nocache` drops every decoded
  list at the start of each `ss_query`/`ss_find` (a list is decoded once per request); `lazy-1mib` drops them
  when over 1 MiB; `lazy-keep` never drops.
- (iii) `lazy-all`: no list decoded at open, all of them at the first use of any (memory as eager afterwards);
  `lazy-checked`: every list decoded and discarded at open (step 6 at open, so damage still fails `ss_open` and
  the header text need not change), then as `lazy-keep`.

The three whole walks (statistics for scoped queries, position validation and tables at the first `find`) decode
each list into one scratch buffer without caching it.

**Method.** `bench.py` (ctypes on the ReleaseSmall dylib), one process per (corpus, variant), variants rotated by
run (`run.sh`), the gate before every start. Open: p50 of 30 `ss_open`+`ss_close` after 3 warm-ups. Memory:
`ri_phys_footprint` growth after `ss_open` and after one pass of the whole query set (every query × field, every
`find`). Warm query: per query and field 1 untimed + 20 warm-up + 300 timed calls (J2: 30), lexical, top 10; the
table gives the sum of the per-query p50s per field (15 queries per corpus: S5-T8's eight timing queries, the
corpus's 1st/10th/100th/1,000th words by df, two pairs, the first file's stem; J2: its 283 knowledge queries,
three roots, `content` and `both`). `find`: 9 (timing, prose), 10 (Tamil) or J2's 7 requests (words, phrase,
prefix), 100 timed calls each (J2: 30); the sum of p50s. First query / first `find`: p50 over 11 opens of the first `ss_query` and then the first `ss_find`
after an open. Answers: every query, field and `find`, and `ss_status`, hashed; **0 differ** for every variant on
all four corpora, and for the eager and lazy libraries on the v2 indexes (`answers.txt`). J2 through
`j2_run.py --searchd` with each prototype `searchd`: `j2_gate.py` passes, `--compare` with `main`'s run 0 differ
under `content` and `both` (`j2.txt`).

**What the numbers say.**

- **(i) eager** opens 17–25 % faster than today (timing 7.16 → 5.38 ms, prose 14.28 → 11.57, Tamil 9.49 → 7.83,
  J2 0.18 → 0.15) because it reads 7–15 MB less and decoding the varints costs less than that read and copy;
  holds 6.9–15.1 MB less after open (the smaller section stays resident); answers every warm query and `find`
  within the process noise on all but one cell: eager's worst warm-query cell is +0.006 / +0.001 ms (timing),
  +0.010 / +0.002 (prose), +0.009 / +0.012 (Tamil), +0.001 / +0.003 (J2), against `today-b`'s own +0.002 to
  +0.008; prose `find words the` (a 15 ms request) +0.127 / +0.053 ms, where `today-b` reached +1.2 ms in the
  superseded runs. The one cell above +0.005 ms in both runs is Tamil `filename` and `both` `doc 00000`
  (+0.0085 / +0.0098 and +0.009 / +0.007 ms): a candidate placement effect for Phase 2's controls to settle. The
  first query after an open is 1–3 % faster and the first `find` unchanged (−0.5 % to +1.1 %); whole-process commands are
  6–18 % faster; the one-file update is +0.2 to +4.4 ms (+0.1 to +2.0 %), the v3 writer's varint coding.
- **(ii) lazy** opens 2.0–3.4 times faster than today and 1.7–2.8 times faster than eager (2.4 / 4.2 / 4.6 ms)
  and holds a further 7.7–17.9 MB less (it never builds the `Posting` array: 8 B a posting). Its costs: **no cache** decodes a list on every request,
  +0.05 ms (timing), +0.10 ms (prose), +0.15 ms (Tamil phrase) on high-df cells — beyond the +0.010 ms rule;
  **with a cache** (1 MiB or unbounded, the same on these sets: 0.37–0.85 MB decoded) warm queries are within
  noise on timing and J2 but +0.03 ms on prose cells and +0.045 to +0.049 ms on Tamil content pairs in both
  runs. That Tamil cost is not decoding (`lazy-all`, every list decoded and cached, shows it too): `profile`
  gives `score_us` 257 → 301 for `கீகசை றூகுஞங்கள்` (10,149 matched chunks, two fold groups), the scorer's
  merge loop reading each list through the lazy accessor; not removed in Phase 1. The **first `find`** after
  an open costs +8.5 ms (timing), +20 to +23 ms (prose), +9 ms (Tamil) over eager: positions are validated and
  the position tables built by two whole walks that each decode every list. Whole-process `find` is 13–23 %
  slower than today's (26–38 % slower than eager's) for the same reason; whole-process `read-span` is fastest
  (no lexical work).
- **(iii) lazy, all at first use** moves the whole decode to the first query (+2.9 ms timing, +6.6 ms prose:
  S6-T3's C2b decode cost) and ends with eager's memory: no gain over eager for a query-serving handle.
  **Lazy, checked at open** keeps "a damaged list fails `ss_open`" (the decode-and-discard walk costs what the
  eager decode costs: open 5.2–11.5 ms, about eager's) and keeps lazy's memory; warm queries and the first
  `find` as lazy-keep.

**Recommendation: (i), decode everything at open, for Phase 2.** It is the only strategy with no regression beyond
this bench's noise (one Tamil file-name cell at +0.007 to +0.010 ms and the update's +2 % are for the controls and the
bars to settle): faster open, less memory and a smaller index than today, the same query, `find` and
first-`find` times, validation unchanged in kind (all of steps 1–6 at open, so no header text changes), and the
least code (the reader's arrays and every call site stay as they are; the change is the codec). The lazy
strategies buy a further 8–18 MB and (except checked-at-open) 3–7 ms of open, but each fails a bar that eager meets: per-request decoding
(no cache), Tamil content scoring and the first `find` (cached), and they add a concurrent cache to the engine's
hot path. Lazy remains possible later without a format change if `list bytes` stays (question 2): checked at
open, with one walk for the position tables (an expectation, not measured: about one decode's worth, 2–6 ms,
saved off the first `find`) and the scorer taking resolved lists.

#### 4. Versioning and compatibility

- **Identification.** Manifest v2.3: `HYBMAN02` flag bit 5 `lexical_v3` (`0x20`), set exactly when the lexical
  sections are `HYBLEX03` (both of them; `validateSnapshot` and `validateFilenameSections` refuse a mismatch). This
  follows S4-T1's v2.1 precedent (bit 2 `xxh3_sections`). The magic and version also name it, so the flag is for
  the old reader.
- **An old library meets v3.** Measured: `main`'s library on a v3 index: `ss_open` returns null, `ss_last_error()`
  `"ss_open: UnsupportedFlags"` (`SS_ERR_CORRUPT_SNAPSHOT`), before any section is read. Without the flag it would
  still refuse (unknown magic, `InvalidLexicalSection`, the same code), but only after accepting the manifest.
  Never a misread either way.
- **A new library meets v2.** It reads it as today (measured: the eager and the lazy prototype on the v2 indexes,
  0 answers differ on all four corpora). The next publish (`index --update`, `apply`) writes v3: the content
  section from the decoded previous generation, as every update already rewrites it; the file-name section is
  rebuilt once (the carry needs `HYBLEX03`), then carried again. Cost of that first publish, measured: 176.4 ms
  against 163.6 for `main`'s ordinary update (timing), 241.5 against 214.8 (prose), 236.8 against 225.1 (Tamil),
  +5 % to +12 %; the publish after it is back to 165.4 / 218.9 / 229.8 (§3).
- **The app's indexes on phones at the next pin.** They keep opening (v2 read). The first edit after the pin
  publishes v3, about 22 % smaller on prose-like folders (§1). After that, an app downgraded to an older pin
  cannot open that index (the old library refuses it as corrupt) and must re-index from the files; the previous
  generation kept by `--keep-generations` is v2 but is not what `CURRENT` names. That is the one-way step to put
  in the consumer note.

#### 7. Open questions for the ruling

1. **Strategy:** eager (i), as recommended, or validate-at-open lazy (iii) now, with its first-`find` cost and
   its extra code (a per-handle cache under a lock, an accessor at 12 sites, a per-query list resolution in the
   scorer)?
2. **Keep the per-term `list bytes` field?** It costs 0.4 % of the content section (24,114 B of 5,396,552 on
   timing) and is needed only by a lazy reader. Keeping it means a later lazy reader needs no format change;
   dropping it means v3.1 or v4 if lazy ever comes. I would keep it.
3. **The shared-prefix cap of 255 bytes** (it bounds the term-text allocation by the section's size). Not in the
   prototype; no measured term shares more than 29 bytes. Accept as drafted?
4. **The one-way step for the app:** after the first publish under the new pin, an older pin cannot open the
   index. Is that acceptable for the consumer note, or should the app's pin carry a read-only v3 fallback
   first (a two-pin rollout: read v3 one pin, write it the next)?
5. **The file-name section's carry:** a v2 index's first publish rebuilds the file-name section once. Acceptable,
   or should the writer convert the `HYBLEX01` file-name section without re-tokenizing the names (sort and
   re-encode what it decodes)?
6. **A bar for library growth** (ruling 6): the eager prototype's macOS dylib is 972,888 B against `main`'s 954,120 B
   (+18,768 B, +2.0 %; the v2 writer and the v3 writer both present, prototype code not trimmed); the lazy one
   973,480 B. I propose ≤ +24 KB (§6).

#### 8. Not measured, and limits

- **No placement controls in Phase 1.** Each run has `today` twice (`today`, `today-b`: the same library in two
  processes), which gives process noise only. The bench is Python ctypes with 300 timed calls per cell (J2: 30),
  not S5-T12's harness; `today-b` − `today` reached ±0.03 ms on high-df cells and over 1 ms on prose's
  `find words the` (a 15 ms request). So the per-cell differences in §3 rank the strategies; they are not a
  verdict at ±0.010 ms. The bars in §6 put the controls into Phase 2.
- **Dark wake.** The Mac was in dark wake from 10:47 (`pmset -g log`); it slept 11:20:46–11:35:54, between my
  runs (no run spans it). Timed starts all passed the gate (lock absent, 5-minute load ≤ 4.0). My gate counts a
  toolchain in the top eight only at ≥ 20 % CPU (another session's Python suite sat at a few per cent for
  minutes); every refusal is in `docs/evidence/s6-t4/gates.txt`.
- **Superseded runs.** Two runs (11:10–11:18) used a lazy build whose scorer resolved only the first 16 query
  terms' lists once per query; Tamil content queries (fold groups of more terms) then read the cache once per
  posting and were +0.10 ms on every lazy variant. Fixed (128 terms), rebuilt, answers re-checked, both runs
  repeated; the old rows are kept in `docs/evidence/s6-t4/superseded/`.
- **Single-threaded cache trim.** The prototype's cache budgets (0, 1 MiB) are applied by dropping every decoded
  list at the start of an `ss_query`/`ss_find` when over budget: valid single-threaded only, as the bench is.
  A real cache needs eviction safe against concurrent readers (reference counts or an epoch).
- **Not built:** per-block skip entries (iii's example). Every scored query reads whole lists (BM25 over every
  posting, no top-k pruning). `find` drives by its shortest list and binary-searches the others
  (`find.zig`), the one place skips could save decoding a long list in full; with a per-handle cache that list
  is decoded once, and with no cache the measured cost of decoding it is in §3's `lazy-nocache` row. Not built,
  not measured.
- **Phones not measured.** Open, memory and query numbers are this Mac's (Apple silicon, macOS, ReleaseSmall
  dylib through ctypes). An expectation, not a measurement: the open saving scales with the bytes read and
  decoded, so a phone's is larger in milliseconds.
- **The migration timing** (first v2 → v3 publish) and the whole-process numbers use the eager prototype
  `searchd`; the app's publish path (the Dart binding's `apply`) was not timed.
