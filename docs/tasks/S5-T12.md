## Source

`Engine.bothGroups` builds a visible-collection view before it knows whether any query word needs one. The queue records a warm `both` query with no triggering word (`bazecha`, 10k timing corpus) at about 0.053–0.059 → 0.085–0.090 ms, and a grouped frequent word (`system`) missing its `both` increment bound (+0.065 ms against +0.03). Both are earlier whole-query measurements. The eager view is seen in the source; that it causes the cost is a hypothesis until measured.

## Rulings

1. **Phase 1: measure before any change, and stop.** On current `main`'s engine, with the existing methodology (the 10k timing corpus, `ReleaseSmall`, interleaved rounds under the load gate, raw measurements kept under `docs/evidence/s5-t12/`): `bazecha`, `system`, `hashing` and a two-word question in both word orders, each under `content` and `both`, plus a build with the eager view skipped when no word triggers (a prototype, not shipped code) to attribute the cost. Report what reproduces. **If the `bazecha` overhead no longer reproduces, say so and build nothing for it.** The Phase 1 Report ends with a recommendation and the builder stops for a ruling.
2. **Phase 2, only what Phase 1 supports, one change at a time.** (a) The visible collection built lazily and at most once per query when grouping needs it, with a membership-only check first if that can establish no view is needed. (b) Separately, and only if Phase 1 shows it matters: `filename_field.zig`'s touched-chunk scoring for frequent groups. Each change is measured alone; the two are not mixed into one number.
3. **Nothing observable moves.** Groups, warnings, scores, ties and visibility are identical: every golden byte-identical, every J2 cell on both surfaces unchanged with the gate clean and no baseline re-record, the find and filename equivalence check of S5-T8 (same requests, 0 differ), and a hidden label's file neither searched nor named. No policy id, contract, Dart version or format changes.
4. **The acceptance rule.** The named overhead improves beyond the measured noise (a second build of the before sources gives the noise band), under the same methodology, with the before and after figures and their ranges stated. No query in the measured set gets slower beyond noise. The bounds of S5-T8's Phase 1 ruling 5 still hold. A change that does not meet this is not shipped, and its measurement is kept as a rejected attempt.
5. **Regression test.** A growth-ratio test in the style the repo already uses (ratio of `both` to `content` work, or of counted operations), not a wall-clock threshold. If a counter can show the view is not built when no word triggers, that is the test.
6. **Plants**, each in its own scratch copy with its own Zig cache: the eager build put back (the new test must fail); the lazy view built from the wrong scope (a visibility or golden test must fail).
7. **Natives.** Rebuilt with the documented toolchain and stamped; sizes, digest, `check_native.sh` and the freshness test. The Report says the app needs a pin to carry the change and names the numbers the pin task will need.
8. **Suites and CI.** Zig Debug and ReleaseSmall, C ABI, Python with and without Zig, Dart; the home-path check; CI green on the final commit.
9. **Documents.** The two 03-next rows closed or re-stated with what remains; `PROJECT-STATE.md`; `EXPERIMENTS.md`; R07 marked landed by the verifier. `IMPROVEMENT-BOARD.md` is not edited.

**What reproduces.**

1. **The `bazecha` overhead reproduces, and it is the eager view.**
   - Today's `both` `bazecha` is 0.1383 ms. The queue's 0.053–0.059 → 0.085–0.090 was S5-T3's engine at `top_k` 5,
     before the title field's and fold groups' later work, so the absolute figures are not comparable.
   - The increment is what reproduces: S5-T3 recorded +0.032 ms for the fuzzy work on this query. Skipping the view
     when no word triggers removes **0.0281 ms** [0.0269, 0.0300], against a noise band of at most 0.0022 in any
     round.
2. **It is not `bazecha`'s alone: every `both` query on this corpus pays it.**
   - The no-group queries (`benico`, both orders of `hybrid retrieval`) save 0.028–0.031 ms under `proto`.
   - The grouped ones save as much under `noview` (`system` −0.0310, `hashing` −0.0300, `system systems` −0.0309,
     `systems system` −0.0305).
   - The view costs the same whatever the query: it is a pass over the scope, not over the query's postings.
3. **Why: the work finds nothing to hide.**
   - `ss_query` with `search_field` `both` always passes a root mask (`abi.zig`, from `folder.allowedRoots`), and the
     handle's engine has no statistics groups loaded.
   - So `scope.visibleCollection` walks all 19,959 chunks on every `both` query. Every chunk is visible here, so it
     returns null, and the walk is thrown away.
   - `content` without `roots` passes no mask and never walks (its `proto` and `noview` columns are flat).
   - `filename_field.maskHides` already answers the same question for the filename channel from the mask alone.
   - `visibleCollection` has no such check: it returns early only when there is no mask.
4. **`proto` costs grouped queries nothing.** Its `both` grouped figures are within noise of `main` (−0.0004 to
   +0.0009), as designed: one grouping without the view, then the view as before, with no recompute because the view hides
   nothing here. No query in the set is slower beyond
   noise under either build; the largest `content` median is +0.0009, `noview` `system`.
5. **Term order no longer matters.** `system systems` and `systems system` are 0.2831 / 0.2833 under `both` and
   0.1255 / 0.1257 under `content`. S5-T4 measured 0.17 / 0.25 for the plain query before fold groups; now both
   words fall in the one group, which the body walk scores once.
6. **The grouped word's `both` remainder is small, and is not the view.** With the view gone (`noview`), `both` −
   `content` is +0.093 (`benico`), +0.099 (`bazecha`) and +0.106 (`hybrid retrieval`) with no group, against
   +0.112 (`hashing`), +0.116 (`system`) and +0.126 (the two-word grouped query).
   - So `filename_field`'s walk of a group's touched chunks adds about 0.01–0.02 ms over a no-group word's `both`
     work. The 0.093–0.106 ms common to every `both` query is outside R07's two items: the filename channel, and the
     per-query dense arrays of `scoreQuery` (scores and seen flags over the 19,959 chunks and 10,000 files).
   - I did not profile `filename_field` stage by stage. This is a whole-query attribution by subtraction.

**Recommendation: build (a), not (b).**

- **(a), in two parts, as ruling 2(a) words them.**
  - *First, the membership-only check.* The view is not needed when the mask allows every root that a chunk
    belongs to and `labeled_documents` is false (exactly `count == documents.len` without the walk; `maskHides` is
    the model). On this corpus that is the whole saving for every `both` query, grouped or not: −0.028 to −0.031 ms.
  - *Then the lazy view*, built at most once and only when a group exists, for requests whose scope does hide
    something: there `proto` shows the saving on queries with no group.
  - The regression test of ruling 5 can count `visibleCollection`'s walks (zero for an all-visible `both` query, one
    for a scoped grouped one).
- **(b) is not supported by this phase.**
  - The grouped word's own `both` remainder is about 0.01–0.02 ms.
  - The term-order effect that motivated it is gone.
  - S5-T4's bound (j) is a difference against the engine before fold groups, which already paid the view. Against
    that engine, (a)'s ~0.03 ms off `system`'s `both` would leave about +0.035 against (j)'s +0.03. That is
    arithmetic on S5-T4's +0.065, not a measurement here. Any further closing would need (b) and a stage profile of
    `filename_field`, for about 0.01–0.02 ms.
- **For the 03-next rows.** The "scope view" row closes with (a). The "frequent grouped word" row would be re-stated
  with these figures: no order effect, a remainder of about 0.01–0.02 ms, and (j)'s miss left as recorded.

**Deviations.**

1. **Eight rounds, not six.** With four libraries, an even rotation needs a multiple of four rounds. `run.sh`
   rotates `main, main2, proto, noview` by one each round, so every library takes every position twice.
2. **A fourth library, `noview`, beyond ruling 1's prototype.** It never builds the view; on this corpus that is
   correct, because nothing is hidden. It attributes the grouped queries' cost, which `proto` by design leaves
   untouched. It is an attribution build, not a candidate: it would be wrong under a scope that hides a document.
3. **The two-word question** is `hybrid retrieval` in both orders. The review's "both query-term orders" (S5-T4's
   `system systems` / `systems system`) is measured as well, and `benico` is added as a no-group control from S5-T8's
   set.
4. **One snapshot.** `content` runs on the filename-indexed snapshot, the one `both` needs, not on a separate plain
   one.
