## Rulings
1. **Schemas.** `contracts/tools/<name>.request.schema.json` and `<name>.result.schema.json` (JSON Schema 2020-12, `additionalProperties: false`, every field described) for the nine methods of S3-T4. A standard-library Python validator in `src/search_platform/schema_check.py` (types, required, enums, additionalProperties, array items, integer bounds — the subset the schemas use) validates recorded real responses from the fixture judgments against each schema in `tests/`.
2. **Skill document.** `skills/folder-knowledge/SKILL.md`: the tools and when to use each; the loop (status if freshness matters → `find` for quoted or exact questions, `search_knowledge` for open questions → `read_span`/`read_chunk` to confirm → answer with `[n]` → cite `root/path › section · lines`); the exact negative sentence "I found no matching indexed passages in the selected folders" and the caveat when `pending_files > 0` or `truncated`; never a claim without a returned hit; never `apply_changes`; what `exact_match: null` means. A `skills/folder-knowledge/example_loop.py` (standard library) runs the loop against the RPC server on the fixture with a stub "model" that only follows the skill, and prints cited answers for the UC-007 questions.
3. **Provider wrapping.** `docs/tool-schemas.md` shows how an adapter wraps a request schema into a tool descriptor for three provider shapes (an "input_schema" style, a "parameters" style, and MCP's `inputSchema`) without changing the schema, and states that the result schema is the adapter's own validation target.
4. **Tests.** The schema tests above; the example loop as a test over the fixture (every answer's `[n]` maps to a returned hit; the negative sentence appears for the newt question); `scripts/check_requirements.py` green.
5. **Diff scope.** `contracts/tools/` (new), `src/search_platform/schema_check.py` (new), `skills/` (new), `docs/tool-schemas.md` (new), `tests/`, `PROJECT-STATE.md`.

### Shape findings for the orchestrator (nothing fixed here; no `ops.zig` change)

- **`search_knowledge` results carry no `root_id`, `section_path` or `truncated`/`pending`.** The citation `path` is the record path `root_id/path`; the skill and the loop split it at the first `/` and check the head against `index_status.roots`. That is ambiguous for the legacy root (`r-legacy` paths have no prefix) and fails for a root id containing `/` (ids cannot, by the root-id rule). Section needs an extra `outline` call; the caveat needs `index_status` or `find`. Candidate for a later contract: `root_id` and `section_path` on `search_knowledge` items (as `evidence` has them).
- **`searchd query --json` is not the RPC `search_knowledge` shape** (no `tool`, `index`, `retrieval`, `citation` object or `content`; `path` sits on the item). The schema covers the RPC/tool shape; the CLI report is the core's own and is left as is.
- **`list_files` for a pending file: `chunker` is `null`** (and `size` may be null). The protocol text lists `chunker` without saying so; the schema makes both nullable.
- **`index_status` and `read_chunk`/`list_sources`/`search_knowledge` have no envelope** (as S3-T4 ruled), so their schemas have no `request`/`scope`; the four envelope tools (`find`, `outline`, `read_span`, `list_files`) are closed including the echo.
- `apply_changes` reports `too_large`, `unreadable` and `budget_exhausted` as counts beside their `_paths`; `pruned_files` and `prune_failures` exist in the core struct but are not written to the JSON, so they are not in the schema; `recovered` appears only when set (optional).
- Offsets: `match_offsets` and `snippet_offsets` are codepoint offsets (checked on a Tamil prefix hit, 91 codepoints, 245 bytes).
