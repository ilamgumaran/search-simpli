## Problem

S1-T18 names the first file carrying the highest generation. Its advice, “delete or rename that file to publish here,” is insufficient when multiple traces carry `u64` max. A user can follow the advice and still be blocked by another trace. Complete the diagnostics while preserving the generation-allocation and publication rules.

## Acceptance criteria

1. At an exhausted highest generation, the single-line `NoFreeGeneration` diagnostic lists **every** matching trace among `MANIFEST`, `INDEX-STATE.json`, canonical `documents-N.hybseg`, and canonical `lexical-N.hyblex`, exactly once in that fixed order. Include the numeric generation and file names only. Lower-generation traces, malformed aliases, directories and caller paths are excluded. A single trace remains named; no stale files carry across calls or threads. An overflow after a taken candidate accounts for both taken section files.
2. The CLI and `ss_index_folder`/`ss_last_error` expose the complete list through their existing error channel and buffers, with CLI exit 1 and empty stdout. Give reliable, non-destructive guidance: a fresh output directory is usable; resolving the listed traces needs inspection. Remove the single-file deletion/rename promise. The failed call must leave every original snapshot file byte-identical. No automatic deletion, generation-rule change, contract bump, or query-output change. Update `docs/generation-lifecycle.md` to the actual behavior.
3. Independent regression checks cover the single-file case, all four max traces, tied subsets, lower/noncanonical exclusions, repeated-call reset and thread isolation. Exercise a real CLI and C ABI caller; verify a fresh output directory succeeds and the old snapshot is unchanged after the error. Restore the parent diagnostic in an isolated scratch copy with fresh Zig caches: the new checks must fail on that parent. Do not weaken existing assertions.
4. Rebuild packaged libraries last with pinned Zig 0.16.0 and verified NDK r28c, record sizes/hashes/stamp, and retain contract 1.2.0. Run the original Zig engine, C ABI, Python and Dart checks plus relevant regression checks and the relevance smoke. Report exact executed/passed/failed/skipped/unrun outcomes. Run requirements, path and documentation checks after writing the Report. Verify actual GitHub CI on the published branch.

## Rulings

- This is a repair to existing diagnostics and guidance, without a new retrieval capability or contract; no capability approval is needed.
- `lifecycle.sectionGeneration` already excludes leading-zero and malformed names. Preserve that definition.
- Use bounded, thread-local metadata for the four canonical trace kinds; avoid a second filesystem scan, extra allocation or query-path changes. Keep list order independent of directory iteration order.
- Runtime source ownership is `zig/src/generation_alloc.zig`; CLI/ABI already share its formatter. Extend existing tests at those boundaries rather than adding a competing error channel. Root reviews the implementation before final verification.
- PR #8 remains unchanged and unmerged. The new branch includes its verified Linux fix so native validation can run here.

### 1. The code (read against criterion 1 and the cloud rulings)

- `generation_alloc.zig`: the old 128-byte name buffer is gone. A thread-local `u4` mask of four kinds (`MANIFEST` 1, `INDEX-STATE.json` 2, `documents` 4, `lexical` 8) plus a thread-local `cause_generation`. `highestGenerationOnDisk` calls `resetCause()` first, so each scan starts empty; `recordCause` raises the generation and clears the mask when it sees a higher number, and ORs the bit on a tie. Section files come only from the existing scan (`entry.kind == .file`, `lifecycle.sectionGeneration`, which already rejects leading zeros and malformed names), so no second scan and no allocation. `describeNoFreeGeneration` emits the bits in a fixed order (`MANIFEST`, `INDEX-STATE.json`, `documents-N.hybseg`, `lexical-N.hyblex`) independent of directory iteration order, each at most once, names only.
- The names buffer is 160 bytes; the longest possible list, all four at `u64` max, is `MANIFEST, INDEX-STATE.json, documents-18446744073709551615.hybseg, lexical-18446744073709551615.hyblex` = 8+2+16+2+37+2+35 = **102 bytes**. The full line is **245 bytes** (my CLI stderr was 253 bytes = `error: ` + 245 + newline); the CLI and ABI format it into 384-byte buffers and the ABI's `ss_last_error` holds 511 bytes, so `ss_index_folder: ` + 245 = 262 fits. No truncation path is reachable.
- Message, accepted by ruling 1: `NoFreeGeneration: no generation number above N (traces: …); use a fresh output directory; inspect listed traces before repair`. The "delete or rename that file" promise is gone from code and from `docs/generation-lifecycle.md`, which now says what the line lists, that a fresh directory works, and that removing one listed file may not clear the others.
- The post-scan overflow branch (`nextFreeGeneration`, when `candidate + 1` overflows while walking taken pairs) now sets the generation to the exhausted candidate and the mask to whichever of the two section names is taken. Reading the code, it is reachable only through entries the scan skips: a file trace at `u64` max makes `highest` max and the first `add` fails before the walk, so the walk can reach max only if the max names are directories, symlinks or other non-regular entries (or a file is created between scan and probe). My probe (d) below exercises it in a real process.
- Tests added: two in `generation_alloc.zig` (all four tied plus lower and leading-zero exclusions and a directory, then a second scan in the same thread that must forget the first; a tied section pair above a lower `MANIFEST`), one in `abi.zig` (a real indexed snapshot re-encoded at max with all four traces, exclusions, byte-identical files after the error, a worker thread whose own error must not disturb the main thread's cause, reset between calls, fresh directory succeeds and clears `ss_last_error`), two in `tests/test_cli_process.py` (all four through a real `--generation 18446744073709551615` publish, byte-identical snapshot, fresh `--out` succeeds; tied sections with lower, leading-zero, malformed and directory exclusions, then `INDEX-STATE.json` tied with one section while the other max name is a directory). No existing assertion was removed or weakened: the S1-T18 tests are unchanged in both files and still pass.

**Findings to carry (not fixed here):**
1. Ruling 2's edge, shown in a real process: with traces at `u64` max − 1, a **directory** (or a symlink) carrying an exact canonical name at max is named as a trace by the post-scan overflow branch, while the scan skips it; in a normal low-generation snapshot such an entry is harmless. 3. `describeNoFreeGeneration` tests the mask with literal `1, 2, 4, 8` rather than `@intFromEnum(Cause.…)`; harmless, a drift risk if the enum changes.
