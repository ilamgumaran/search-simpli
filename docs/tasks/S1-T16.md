# S1-T16 · NFC recomposition is quadratic in the text length

**State:** ready (2026-10-10) · **Series:** S1 · **Depends on:** S1-T15 · **Size:** S · **Builder:** Sonnet 5.5 · **Tester:** Opus 5.5

**From the S1-T15 Verdict, finding 1.** The recomposition step in `zig/src/nfc.zig` grows with the square of the text length, and since S1-T15 it reaches Korean: a 256 KB single line holding at least one combining mark went 11 ms → 1.1 s, 1 MB 48 ms → 17 s; `searchd index` on such a file 19 ms → 1,220 ms. Chunks are at most 1,600 characters, so normal text never sees it, but a query or a single very long line can. The M1's S2-T11 listed a "linear NFC step" candidate; this is it.

## Rulings
- Recomposition becomes **linear**: one pass with a bounded look-back (the last starter and the combining classes since it), as UAX #15's canonical composition algorithm describes; no rescans of the already-composed prefix.
- Output byte-identical to today's on every case `scripts/nfc_compare.py` covers (0 differences stay 0) and on the S1-T15 tester's random mix; every golden byte-identical; analyzer id unchanged.

## Acceptance criteria
1. **Bar, written first:** the S1-T15 tester's timings reproduced on `origin/main` (a 256 KB and a 1 MB single Korean line with one mark; `searchd index` on the 1 MB file), then on the branch: ≤ 2× the mark-free time at every size (so ≤ ~25 ms and ≤ ~100 ms), and growth linear between 256 KB and 1 MB (×4 ± 25 %). Best of 3, all runs listed; never a single wall-clock threshold as the only test: the test asserts the growth ratio and a generous absolute ceiling.

## Report (builder fills in)

**Branch `task/S1-T16`. Criteria 1-4 met; output byte-identical everywhere it was compared; no golden moved; analyzer id unchanged; `CONTRACTS_VERSION` 1.2.0.** Sonnet 5.5 built it.

**What changed in `zig/src/nfc.zig`.**
1. `compose` is one pass over the decomposed, ordered codepoints with a write cursor, in place: it keeps the last-starter index and the class of the last codepoint kept after it (the same two variables as before), appends or merges, and never removes from the middle (the old `orderedRemove` was the quadratic step). Same rules, same order of tests, so the same output.
2. Two things beyond the ruling, because "linear" alone left the Korean line at 3x its mark-free twin, over the 2x bar. (a) A precomposed Hangul syllable is no longer decomposed to jamo and recomposed: the round trip is the identity (the three jamo are adjacent, class 0, and always recompose), and a following T jamo still joins an LV syllable in `composedOf`. (b) The slow path runs the algorithm only on regions that can change: ASCII and precomposed syllables are "inert" (class 0, no decomposition, never the second part of a pair; a unit test checks this against every table row), nothing joins two inert codepoints, so text between inert neighbours is copied and a region starts at the inert codepoint before the first non-inert one and ends before the next inert one. Text with no marks still takes the old fast path (`hasAnyCombiningOrDecomposable`). Early outs in `combiningClassOf`, `decompositionOf`, `composedOf` for the Hangul jamo block and syllables (also checked against the tables by a test).
3. Not touched: `canonicalOrder`'s insertion sort is quadratic only in the length of one run of marks with decreasing classes (not reachable from text with a normal mark count); noted, not part of this task.
