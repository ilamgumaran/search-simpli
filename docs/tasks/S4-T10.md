# S4-T10 · `read_span` and `outline` hold only the file they answer about

**State:** ready (starts from `main` after the S4-T9 merge) · **Date:** 2026-11-05 · **Depends on:** S4-T9 (the exact open block; the one-handle and fresh-handle NFR-13 measures) · **Size:** M

**Owner:** the Xcode Mac orchestrator · **Orchestrator:** Claude Fable 5.1 · **Builder:** Claude Opus 5.5 (local) · **Verifier:** Claude Opus 5.5 (local, a different agent)

**Why.** S4-T9 brought the open's peak within 1 MiB of what it reads (10k: 33,567,893 B; 15k: 49,138,697; 20k: 64,782,850, filename channel on) and met NFR-13's 64 MiB at 15k **per fresh handle**, but not **on one handle**, which is the reading that counts (the phone app holds one handle for the life of the process; S4-T9 ruling A): after the first `read_span` or `outline` the handle keeps the **whole source section** (12.4 MB at 15k, the original bytes of every retained file plus the files table and line maps), and after the first filename query its block (4.9 MB), so `list_files`, a filename query and a `both` query on one handle sit at 71 MB at 15k, and the cap on one handle is reached near 14,100 files. The source section's format (`docs/source-section-v1.md`) already carries, per file, `text_offset`, `text_length`, `line_map_offset` and a SHA-256 of the file's bytes, and the files table is sorted for a binary search, so a reader can keep the table and the line maps resident and read one file's bytes per call. Today `scope.readSource` reads the section whole, `source.openIndexed` validates every line map against the file bytes and the section checksum over every payload byte, and `read_span` answers from the resident copy. This task changes how the reader holds the section, not the format, the writer, the checksum or any answer.

## Rulings
1. **First use reads the table and the maps, streams the text.** On the first `read_span` or `outline` (and nowhere earlier: `index_status` keeps reporting `unverified` without touching the file, S3-T4), `scope.readSource` allocates **one exact block from the parent allocator** (S4-T9's ownership, freed at close) for the header, the files table and the line maps, reads them positionally, and **streams the text area through a fixed buffer of at most 1 MiB** to compute the section checksum and to validate each file's line map against its bytes exactly as `source.open` validates today (same rules, same error names, `SourceSectionChecksumMismatch` against the manifest's value), holding none of the text afterwards. `index_status.source` becomes `verified` at the same moment and under the same conditions as today, and `unavailable` on the same failures. State the block's bytes at 10k, 15k and 20k (table and maps) and the first use's wall time before and after at 10k (today about 11.7 ms).
2. **Each call reads its file.** `read_span` and `outline` find the record by binary search in the resident table (`source.Section.find` or its successor), read the file's `text_length` bytes at `text_offset` positionally into a buffer from the **call's** allocator (freed with the call), verify the bytes' SHA-256 against the record (a new per-call check; its cost for the largest file in `fixtures/family-folder` and for a 1 MiB file stated), and answer **byte for byte as today** (lines by the resident line map, the BOM rule, every error and `CAPACITY` message unchanged). A file whose bytes fail the SHA-256 answers the same `CAPACITY` the damaged-section case answers today, naming the check.
3. **The bar.** `nfr13_arena_test.zig`'s **one-handle** scale run at 15k asserts every operation's peak (the open, `find`, `read_span`, `outline`, `list_files`, `search_knowledge`, a filename query, a `both` query, in that order on one handle) **under 64 MiB**; the 20k one-handle peaks are reported, and asserted too if they fit. The fresh-handle guard from S4-T9 stays. The family folder's and both 10k tests' one-handle peaks print before and after (from this branch's runs, beside S4-T9's). A time bar at 10k, `ReleaseSmall`, interleaved rounds, load stated: a second and later `read_span` p50 and `outline` p50 within 2 ms of `main`'s (they now read one file from disk instead of a resident copy: say the numbers for a small file and for the largest fixture file); the first `read_span` within 5 ms of `main`'s; `ss_open`, `find`, `search_knowledge`, filename and `both` p50 unchanged within 0.3 ms (they do not touch the source).
