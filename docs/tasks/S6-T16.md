# S6-T16: a small, documented public core API (plan step B3)

**State:** filed by the orchestrator, 20 Nov 2026, from `main` at `62c954c` · **Depends on:** [S6-T14](S6-T14.md) (the core is a module), [S6-T15](S6-T15.md) · **Plan:** [objective plan](../plans/2026-11-16-objective-plan.md), section B, step 3

## Why

The core is now a module, but its root re-exports every file, so operations and
interfaces can reach any internal. Someone writing a new interface (or a later
binding's wrapper) cannot tell which names are the supported way in, and a
change inside the core cannot tell which names it must keep. The plan asks for
a small public API: open, search, find, read, apply.

## What

1. **Measure first.** A table of every `core` name that operations, interfaces
   and cross-layer tests use today, by file and count, committed as evidence.
   The API is designed from what is used, not from what might be wanted.
2. **The public surface.** `zig/src/core/core.zig` separates a documented
   public part (the names an operation or interface may use, grouped by what
   they are for: open a generation, search, find, read a span, apply changes,
   the formats' identities, errors) from the rest. Each public name has a doc
   comment that says what it does, who owns returned memory, and what errors it
   returns. How the rest is kept reachable for the core's own tests is the
   builder's proposal (for example an `internal` namespace), stated before the
   change.
3. **A guard.** `scripts/check_layers.py` fails when a file in `ops/` or
   `interfaces/` uses a `core` name outside the public part, naming file, line
   and name. Read from Zig tokens as its other rules are. Cross-layer tests may
   use internals; that is stated in the document.
4. **A document.** `docs/core-api.md`: the public names by purpose, with a short
   example of writing a new interface against operations and the core API, and
   the rule for adding a name. `docs/layers.md` and CONTRIBUTING point to it.

## Rulings

1. **No behaviour change.** No function body changes; names move or gain
   aliases and doc comments only. Indexes and every answer surface byte-identical
   to `main`'s on J2 and the fixtures; C header and exports unchanged; contracts
   unchanged.
2. **Small.** If operations and interfaces today use more core names than a
   reader can hold (the builder reports the count), the task does **not** shrink
   their use by rewriting code. It publishes what is used, marks in the document
   which names look like internals that leaked, and lists them as follow-ups.
   Stop and report if the count is so large that "public" would mean "nearly
   everything": that is a design question for the maintainer.
3. **Natives.** Rebuilt and restamped in the same commit as any change under
   the digest's inputs. Expected byte-identical to `main`'s (names and comments
   do not reach the binary); if any native differs, report sizes and the reason,
   and timing by the rule of 2026-11-17 is then owed before a Verdict.
4. **Tests.** The same tests run by name as on `main`; both guards of S6-T15
   pass; the new guard has tests in the place the checker's tests live, and a
   planted use of an internal name from `ops/` and from `interfaces/` fails it.
5. **Stop before:** a contract, C header, format or answer change; a function
   body change; removing a name something uses.

### Design (stated before the change)

**The two parts of `core.zig`.** `core.zig` gains, at its top, one declaration `pub const api = struct { ... };`,
the public core API. Inside it, one namespace per core file that operations or interfaces use (23), named as the
file (`api.engine`, `api.snapshot_open`, ...), each holding exactly the names they use (88), as aliases:
`pub const Engine = internal.engine.Engine;`, with `const internal = @This();` at the root's top level (Zig refuses
`engine.Engine` there as an ambiguous reference, measured in a scratch probe). Every namespace and every name has
a `///` doc comment: what it does, who owns returned memory, what errors come back (each function's error set
read from the compiler, below). The namespaces are laid out by purpose with section comments: open a generation,
search, find, read a span, apply changes, build an index, write a generation by hand, the formats' identities;
the errors are documented on each function and listed together in `docs/core-api.md`. The rest of `core.zig`, the
51 `pub const <file> = @import("<file>.zig");` lines and the test-build `comptime` block, is unchanged and is the
internal part: every core file by name.

Why per file and not flat by purpose: the bodies of `ops/` and `interfaces/` call `engine_module.Engine`,
`scope.Request`, `find.Request`, `manifest.encode`, `segment.encode`; ruling 1 forbids changing them, so each
alias they bind must keep the same member names, and three files share `encode`, two `Request`, three
`policy_id`. A namespace per file is the one shape that keeps every body token as it is.

**How the core's own tests and the cross-layer tests reach internals.** Unchanged. A core file and a core test
import other core files by path inside `core/`. The tests in `tests/` keep `@import("core").<file>`, the internal
part, and may use any `pub` name: the document says so, and the guard does not read `tests/`.

**How operations and interfaces import.** Each `@import("core").<file>` in `ops/` and `interfaces/` becomes
`@import("core").api.<file>`, nothing else on the line changing; the alias keeps its name
(`const engine_module = @import("core").api.engine;`), so no body token changes. That includes the inline import
expressions inside function and test bodies (`@import("core").postings.TermEntry` →
`@import("core").api.postings.TermEntry`), which ruling 1 counts as import lines, as S6-T14 did. A new interface
may write `const core = @import("core").api;` and `core.engine.Engine`.

**The guard** (`scripts/check_layers.py`). For every `.zig` file in `ops/` or `interfaces/` (their tests
included), every core name is read from Zig tokens, through an alias in its block's scope or written inline, as
the chain after `@import("core")`. It fails, naming file, line and name, when the chain does not start with
`api`, names a namespace `api` lacks, or a name its namespace lacks; and when `@import("core")` is used whole. It
also checks `api` itself: each namespace is a file the root exports, each entry is exactly
`pub const N = internal.<namespace>.N;`, and each carries a doc comment. So a public name is always the core
file's own declaration under its own name. Zig enforces the membership too (a name `api.engine` lacks does not
compile); the checker gives the line without a toolchain, and also catches the internal path
(`@import("core").engine`), which compiles.

**Can it change the binary?** Not expected. An alias is evaluated at compile time and is the same type or the same
function; Zig analyses declarations lazily, so `api` is compiled only where named and adds no code; doc comments
and comments reach no binary. What can move is the order in which the compiler first meets a declaration, through
`api` instead of the file. That is the one way the bytes could differ, so the natives and `searchd` ReleaseSmall
are compared with `main`'s (ruling 3) and, if any differs, timed. `SOURCE-SHA256` changes either way (its inputs
change), so the natives are rebuilt and restamped in the change commit.
