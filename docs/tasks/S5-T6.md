## Rulings

1. **R01, the approach.** A dedicated CI job on an interpreter whose `unicodedata.unidata_version` is `13.0.0` (Python 3.9 through `actions/setup-python` is the first thing to try; if the runner image cannot provide it, a pinned-UCD provider is the fallback and the builder stops for a ruling before building one). The job asserts the Unicode version in a step of its own, builds what the generators need (Zig 0.16.0 as `native-linux` installs it), and runs every golden check: the analyzer and Unicode tables, the title, BM25, fuzzy, analyzer-v3 and verb-forms goldens, and the related guards in `test_analyzer_v3.py` and `test_tokenize.py`. **A skip fails the job**: the step counts the tests it expects by name and fails on any skip among them. The 3.11 jobs stay as they are.
2. **R01 on another machine's bytes.** If a golden regenerated on Linux x86_64 differs from the Mac's (a float in a BM25 or title golden is the likely place), the builder does not refresh the file to make the job green. It records the differing values and their cause, and stops for a ruling on a tolerance or a per-platform rule.
3. **R02, the native gate.** In the Linux release job, with the `ReleaseSmall` `searchd` that job builds: `j2_run.py` in `content` and `both`, the expected query count asserted, no fallback to the reference and no skip, then `j2_gate.py` against the committed baseline. The report names the binary, its source commit and the policy ids.
4. **R02 on x86_64 differences.** The baseline was recorded on macOS arm64. Where the x86_64 run differs (the review names `m13` and f32 ties), each difference is listed with its scores and cause. The baseline is not overwritten and the allow-list is not enlarged to hide a difference. If real differences exist, the builder proposes the narrowest honest rule (an explained per-platform tie list, reviewed), and stops for a ruling before adopting it.
5. **The planted regression.** A test or CI step feeds the same gate a deliberately worse native result and shows it fails; `tests/test_j2_gate.py` stays meaningful.
6. **Seeing CI before the merge.** The workflow's `push` trigger gains `task/**`, so a task branch is checked before it merges. Job logs need a sign-in the builder does not have; the public API does not. So each new step reports its failures as workflow annotations (`::error title=…::` lines, one per differing row or skipped test, bounded to 30), which the unauthenticated check-runs API returns. The builder reads run status, job conclusions and annotations through `curl` against `api.github.com`, with a generic client name and no credentials, and never polls in a loop: one request when it needs the state.
7. **Exit, as the review writes it.** Each generated fixture made stale on the branch in turn (in commits that are reverted, on a scratch branch `task/S5-T6-plant` that is deleted afterwards) and the job shown to fail with the annotation naming it; restored, every required check runs and passes. The planted ranking regression fails. Both modes run fully on the native binary.
8. **Documents.** `docs/evaluation.md` (how J2 is gated on each surface), the 03-next rows closed, `PROJECT-STATE.md`, `EXPERIMENTS.md`, and the review's R01 and R02 marked as landed by this task with the commit.
