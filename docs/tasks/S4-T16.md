# S4-T16 · One changed file: the documents pass and the documents section stop re-doing every unchanged file

**State:** ready (starts from `main` after the S4-T15 merge, `aa765d7`) · **Date:** 2026-11-06 · **Depends on:** S4-T11 (the lexical merge and the source encode carry; the sub-stage timers), S4-T12 (an encode validates once), S4-T14 (the open without the map walk) · **Size:** M

**Owner:** the Xcode Mac orchestrator · **Orchestrator:** Claude Fable 5.1 · **Builder:** Claude Opus 5.5 (local) · **Verifier:** Claude Opus 5.5 (local, a different agent)

**Why.** One changed file in the 10k index costs about 58 ms with the filename channel off and 67 ms on (`ReleaseSmall`, p50 of ten, S4-T14's verifier). Its stages (`SEARCH_SIMPLI_APPLY_STAGES`, p50 of 20, S4-T14's Verdict): `open_previous` 10.3 ms, `load_previous` 5.7, `build_documents` 10.5, `build_lexical` 4.8, `encode_sections` 15.3 (lexical 8.8, of which one `validateIndex` is 5.6; documents 4.0; the source copy 2.2, its checksum 0.5, its line maps 0.35), `state_encode` 2.3, `publish` 7.4 (10.7 on). Three of those stages, **20.2 ms together**, are per-file or per-record work done for every one of the 10k files while one changed. **`loadPrevious`** builds `previous_docs`, a path→list map with one `ArrayList` per path over every previous record, then the `work.files` map from the state, then a second map `work.initial` over every file. **The documents pass** (`buildGeneration`'s file loop) looks each file up in `previous_docs` and, for a retained file, in the source section (`section.find`), packs its labels, copies every previous `Document` struct (re-expressing the chunker index), and appends to `documents`, `sources`, `retained` and `state_files`. **The documents encode** `segment.encodeV4` validates every field of every record in `encodedLengthV4`, which the caller runs for the buffer size, and then again inside `encodeVersion` (the pattern S4-T12 removed from the lexical encode), then copies every record's bytes. The files are sorted by record path (`apply.zig`, "Sorted by record path") and each file's chunks are appended in order, so a generation's documents are **grouped by path in path order**: a range per file, not a list per path. A carried, unrenamed file's records are a pure function of fields the carry already holds (path, text, labels, chunker index, section fields, `source_doc_index`), so their bytes in the new documents section equal their bytes in the previous one whenever those fields are equal.

State the documents section's bytes and record count at 10k and the number of distinct paths. Numbers in a table, p50 and worst.
2. **The previous generation's documents are indexed by range.** `previous_docs` maps a record path to one contiguous range `[first, end)` of the previous documents instead of a list per path. One pass at `openPrevious` (or in `loadPrevious`) checks the invariant the writer has kept since the sorted file loop: each path's records contiguous and the paths non-decreasing. A generation that violates it (a hand-built test generation; any writer before the sorted loop) falls back to today's list map, with the same behaviour, and the Report names the fallback's test. Every caller of `previous_docs` (`loadPrevious`, `detectRenames`, `chunkerOf`, the documents pass) takes the range form.
3. **The documents pass does only what the changed file needs, per file.** Where ruling 1's profile shows the cost: the source-section lookup becomes a parallel walk (both the files and the section's table are in path order), the label packing is skipped when neither the root nor the file has labels (the empty result today), the four lists are pre-sized from the previous counts, and `work.initial` is kept only if the report's counts need it (otherwise those counts come from the state entries directly). Every `Document` the pass produces, every `state_files` entry, every `retained` entry and the report's counts are identical to today's (the parity in ruling 5 is the proof); no change to what is carried or re-tokenized (S4-T11's rules).
4. **The documents encode validates once and copies carried records' bytes.** (a) `segment.zig` gains `encodeAllocV4` (the pattern of S4-T12's `lexical_segment.encodeAlloc`): one validation walk computes the length and encodes; `encodedLengthV4`, `encodeV4` and the v3 `encode` keep their behaviour for the readers' tests and `import-json`; every check is kept. (b) For a file whose records are carried (`sources` entry `.carried`, path unchanged, labels equal, the chunker index equal after re-expression, `source_doc_index` equal), the new section takes **the previous section's bytes for that file's records** (the record offsets are recorded at `documents_decode`, one `u32`/`usize` per record, or recomputed from the decoded fields) instead of encoding from the structs; the equality of the five fields is checked per record before the copy, and a record that differs in any field is encoded as today. The bytes are identical by construction (the record is a pure function of its fields, and the format's checksum is over the whole section as today); the compare in ruling 5 proves it. If the profile shows the documents encode's copy and validation together under 2 ms, (b) is dropped and the Report says so with the figure.
