# S4-T16 · One changed file: the documents pass and the documents section stop re-doing every unchanged file

**State:** ready (starts from `main` after the S4-T15 merge, `aa765d7`) · **Date:** 2026-11-06 · **Depends on:** S4-T11 (the lexical merge and the source encode carry; the sub-stage timers), S4-T12 (an encode validates once), S4-T14 (the open without the map walk) · **Size:** M

**Owner:** the Xcode Mac orchestrator · **Orchestrator:** Claude Fable 5.1 · **Builder:** Claude Opus 5.5 (local) · **Verifier:** Claude Opus 5.5 (local, a different agent)

**Why.** One changed file in the 10k index costs about 58 ms with the filename channel off and 67 ms on (`ReleaseSmall`, p50 of ten, S4-T14's verifier). Its stages (`SEARCH_SIMPLI_APPLY_STAGES`, p50 of 20, S4-T14's Verdict): `open_previous` 10.3 ms, `load_previous` 5.7, `build_documents` 10.5, `build_lexical` 4.8, `encode_sections` 15.3 (lexical 8.8, of which one `validateIndex` is 5.6; documents 4.0; the source copy 2.2, its checksum 0.5, its line maps 0.35), `state_encode` 2.3, `publish` 7.4 (10.7 on). Three of those stages, **20.2 ms together**, are per-file or per-record work done for every one of the 10k files while one changed. **`loadPrevious`** builds `previous_docs`, a path→list map with one `ArrayList` per path over every previous record, then the `work.files` map from the state, then a second map `work.initial` over every file. **The documents pass** (`buildGeneration`'s file loop) looks each file up in `previous_docs` and, for a retained file, in the source section (`section.find`), packs its labels, copies every previous `Document` struct (re-expressing the chunker index), and appends to `documents`, `sources`, `retained` and `state_files`. **The documents encode** `segment.encodeV4` validates every field of every record in `encodedLengthV4`, which the caller runs for the buffer size, and then again inside `encodeVersion` (the pattern S4-T12 removed from the lexical encode), then copies every record's bytes. The files are sorted by record path (`apply.zig`, "Sorted by record path") and each file's chunks are appended in order, so a generation's documents are **grouped by path in path order**: a range per file, not a list per path. A carried, unrenamed file's records are a pure function of fields the carry already holds (path, text, labels, chunker index, section fields, `source_doc_index`), so their bytes in the new documents section equal their bytes in the previous one whenever those fields are equal.

### What changed

### The code read (`git diff aa765d7 84f1ad8 -- zig/src/apply.zig zig/src/segment.zig`)

- **`PreviousDocs.build`.** One pass counts the runs of equal paths and requires each run boundary to ascend strictly by
  bytes (`std.mem.order … != .lt` sends it to the lists); a second pass builds one `Range` per run in a hash map sized for
  the runs and keeps the runs in order, breaking to the lists if a path starts a second run (`found_existing`). The lists
  are today's loop (one `ArrayList(usize)` per path, record order). `get`, `contains`, `count` and the iterator answer
  either form; the range form iterates in path order, the list form in the map's order, as before. Under the order check
  the contiguity check cannot fire (strictly ascending runs never repeat a path); it is a harmless second guard, and p1
  needed both removed. `chunkerOf`, `loadPrevious` and the documents pass read indices only through `Indices.len`/`at`,
  which give exactly the list's indices (the unit test checks every path of every case against today's list).
- **`orderedFiles`.** With `order_ascending` (the state's records strictly ascending, checked as they are put), a file is
  placed at `file.order` only while `order[file.order]` is the very slice (`ptr` and `len`) in `file.record`; every other
  file (added, moved: the struct keeps its number but `record` is a new slice; changed or re-put: a new struct with
  `no_order`) is sorted with `lessThanFileRecord` and merged in before the first placed file it precedes. Every
  `work.files` put I read keys the map by the file's own `record` (`applyParsed` at the add/change, move and remove sites,
  and `putLoaded`), so keys are unique by bytes, two files never share a slot, the placed files ascend (they follow
  `Work.order`), and no touched file compares equal to a placed one: the merge of two sorted, disjoint sequences is the
  sort of their union, which is the sort of every file. A state out of order takes the plain sort. (If a later change ever
  put a file under a key other than its `record`, only the Debug `assert(out == files.len)` would notice; recorded as a
  note, not a defect.)
- **`SourceWalk`.** `find(path, in_order)` takes the cursor only when the file is looked up under its own path
  (`prev_record == record`) and the section has record offsets (`record_offsets.len == file_count`, the same condition
  under which `Section.find` binary-searches); otherwise it calls `Section.find`. The files are visited in record order,
  so the in-order lookups ascend, and the section's table is in path order (the binary search relies on it), so advancing
  past smaller paths, returning an equal one and keeping a greater one in `peeked` returns exactly the entry the binary
  search returns; `Section.file(i)` applies the same `withCheckpoints` as `find`. An empty section returns null in both.
- **The `loadPrevious` walk.** `walk` starts as `previous_docs.sorted` and is cleared the first time a state record does
  not ascend strictly; while set, the cursor over the runs advances past smaller paths and pairs an equal one, so
  `walked` is the record's range or null exactly as `get` would answer; the chunker is looked up only when the entry has
  none, from the walk or from `get`. The comment's argument for the skip holds: with `walk` still set, the matched runs are
  distinct and each equals one distinct key put in this loop, so `matched == runs.len` means every previous path is a key
  of `work.files`, and the not-in-state loop would `continue` at its first check for every path. `putLoaded` fills
  `initial` with the same values as `files` at each put, so a path put twice keeps its last values in both, which is what
  the removed walk over `work.files` produced (nothing in `loadPrevious` changes a file after its put).
- **`segment.measure` and `encodeAllocV4`.** `measure` is the old `encodedLengthVersion` body unchanged
  (`vectorDimensions` first, then `DocumentCountOverflow`, then per record `validateCitation`, the five field lengths,
  `validateRequiredLabels`, for v4 the section path's length and `validateSection` mapped to `InvalidSection`, for v3
  `RequiresVersion4`, the checked sums), returning the length and the dimensions. `encodeVersion` runs it once, then
  `BufferTooSmall`, then `writeVersion`, the old write body, which returns `[]u8` (it has no fallible check to drop);
  the old function ran the record walk once and the dimensions walk twice more inside `encodeV4`, after the caller's
  `encodedLengthV4`. `encodeAllocV4` runs `measure` once, allocates exactly and writes. Same checks, same names, same
  order; a refusal allocates nothing.
