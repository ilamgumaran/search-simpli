# S1-T12 · No stray library can win: inside an app only the bundled copy; in a checkout the package's copy first

**State:** ready (2026-10-08) · **Series:** S1 · **Depends on:** S1-T11 · **Size:** XS · **Builder:** Sonnet 5.5 · **Tester:** Opus 5.5

From the S1-T11 Verdict, findings 1 to 3. After S1-T11 the bundled copy beats a stray one, but a bare-name lookup is still tried when the exact `Frameworks` path misses, and everywhere the bare name can reach from inside an app (cwd, the engine's search paths, `/usr/local/lib`, `/usr/lib`) is outside what the app ships; a packaging mistake would silently load a stray copy, and a stale build with the same version string would pass the version check. In a development checkout the bare name still runs before the package's own `native/` copy, so a stray library in the cwd wins under `dart run` and `dart test`.

## Rulings
- **Inside an app** (`Platform.resolvedExecutable` lies under `*.app/Contents/MacOS/`): only the `SEARCH_SIMPLI_LIBRARY_PATH` override and the exact `<executable>/../Frameworks/libsearch_simpli.dylib` are tried. No bare name. If both miss, the `StateError` says the app did not ship the library and names the path it looked at.
- **Outside an app** (macOS and Linux): the override; the package root's `native/<platform>/` copy (via package config); the cwd- and script-relative `native/` candidates; **then** the bare name last. The bare name stays only as the final fallback for a system-installed library.
- Android and the override are untouched.
