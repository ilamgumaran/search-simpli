# S1-T12 · No stray library can win: inside an app only the bundled copy; in a checkout the package's copy first

**State:** verified (2026-10-08; ready 2026-10-08) · **Series:** S1 · **Depends on:** S1-T11 · **Size:** XS · **Builder:** Sonnet 5.5 · **Tester:** Opus 5.5

From the S1-T11 Verdict, findings 1 to 3. After S1-T11 the bundled copy beats a stray one, but a bare-name lookup is still tried when the exact `Frameworks` path misses, and everywhere the bare name can reach from inside an app (cwd, the engine's search paths, `/usr/local/lib`, `/usr/lib`) is outside what the app ships; a packaging mistake would silently load a stray copy, and a stale build with the same version string would pass the version check. In a development checkout the bare name still runs before the package's own `native/` copy, so a stray library in the cwd wins under `dart run` and `dart test`.

## Rulings
- **Inside an app** (`Platform.resolvedExecutable` lies under `*.app/Contents/MacOS/`): only the `SEARCH_SIMPLI_LIBRARY_PATH` override and the exact `<executable>/../Frameworks/libsearch_simpli.dylib` are tried. No bare name. If both miss, the `StateError` says the app did not ship the library and names the path it looked at.
- **Outside an app** (macOS and Linux): the override; the package root's `native/<platform>/` copy (via package config); the cwd- and script-relative `native/` candidates; **then** the bare name last. The bare name stays only as the final fallback for a system-installed library.
- Android and the override are untouched.

## Acceptance criteria
1. The loader implements the two orders above, with the in-app test being a pure function of the executable path (unit-testable with a fake path). Unit tests with a recording opener for: in-app with the library present; in-app with it missing (error names the Frameworks path, and the bare name was **not** attempted); checkout order ending in the bare name; the override short-circuit in both modes. Plant: with the in-app branch removed, the "not attempted" test fails; paste it.
2. **Decoy proofs in a real bundle** (`tool/bundle_probe.sh`, extended with a `--decoy` mode): (a) library bundled + decoy in cwd → `1.0.0` loads (`dladdr`-style proof: print the path the library was loaded from, via `DYLD_PRINT_LIBRARIES=1` or an exported symbol's address resolved with `dladdr` in a tiny helper); (b) **no library bundled + decoy in cwd → the app fails with the StateError, the decoy is never loaded** (on `origin/main` it loads `decoy`; paste both). (c) Checkout: `dart run` of the example with a decoy in the cwd loads the package's `native/` copy, not the decoy (on `origin/main` the decoy wins; paste both).
3. Docs: README, `docs/zig-engine-api.md`, `PROJECT-STATE.md` describe both orders; the sentence "can never win" becomes exact ("inside an app only the shipped copy is ever loaded; in a checkout the package's own copy is preferred, and the bare name is the last fallback").

5. Dart-only: nothing under `zig/`, `include/`, `contracts/`, `native/`, no stamp change. Five suites green after the Report (`source ~/development/env.sh`; `flutter pub get`; `SEARCH_SIMPLI_LIBRARY_PATH` unset); tails pasted; home and temp paths redacted.

### Findings (none blocking)
1. **A bundle with an upper-case extension is not an app to the loader.** `isInsideMacApp` tests `endsWith('.app')` case-sensitively. A5: the same signed bundle renamed `Upper.APP` is classified as a checkout. The loader then reaches the bare name, and an unsandboxed launch from a folder holding a decoy loads the decoy over the bundled copy. That is the S1-T11 shadowing again, for this one naming. Xcode and Flutter always emit `.app`, so it needs a rename by hand. `realpath` keeps the on-disk case (E3c), so typing a different case does not get round the check. A one-line fix: compare the extension case-insensitively, plus a test (`'/X.APP/Contents/MacOS/x'` → true). This is for the orchestrator; the ruling says `*.app`, and the build follows it to the letter.
2. **"The app did not ship" is wrong when it did.** A3: a `Frameworks` copy that exists but cannot be opened (`errno=13`, and by the same path a bad signature or a wrong architecture) still gives the headline "the app did not ship libsearch_simpli.dylib". The detail lines below it then say "It existed but failed to open". The behaviour is right (no fallback, no bare name). Only the first line misleads. A headline like "the app's copy of libsearch_simpli.dylib could not be opened", used when `failures` is not empty, would be exact. The unit test for this case checks the attempts only, not the message.
3. **Two test gaps.** (i) No test pins the `.app` part of `isInsideMacApp`: P4 removes it and all 9 tests pass, so `'/opt/tool/Contents/MacOS/dart'` could become an "app" unnoticed. Adding `expect(isInsideMacApp('/opt/x/Contents/MacOS/y'), isFalse)` would close it. (ii) "a failed earlier candidate does not mask a later one" is now vacuous: `/pkg/` is the first checkout candidate, so it succeeds on the first attempt (`attempts.length == 1`) and nothing earlier fails. The property is still caught by the order tests (P3 fails 3). Returning the library for `/cwd/` instead, and expecting 2 attempts, would restore the test's meaning.
4. **Outside an app and outside a checkout, the bare name is still reached (by the ruling).** E2a, E2b, E2c, E2e and E3b: a `dart compile exe` tool in a plain folder, with no reachable `package_config.json`, loads a decoy from its cwd. This matches the accepted ruling (the bare name is the last fallback for a system-installed library), and the docs' sentence is exact about it. I record it so that nobody reads "in a checkout the package's own copy is preferred" as covering a standalone executable. Other bundle types (`.appex`, `.xpc`, a helper `.app` nested in `Contents/Frameworks`) were not probed (below).
5. Wording: README, `PROJECT-STATE.md` and `docs/zig-engine-api.md` say the executable lies "under `*.app/Contents/MacOS/`". The code requires its directory to *be* that folder: E2b, one level deeper, is a checkout. The loader's own comment says "directory ends in", which is exact.
6. For simpli-helper (no action here): inside an app, nothing from a checkout is consulted any more. A debug macOS build that once found the library through package config, or through the bare name, now needs the `.dylib` embedded in `Contents/Frameworks` or the override.
