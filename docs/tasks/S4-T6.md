# S4-T6 · `searchd serve`: a read after `apply_changes` crashes a release build (a stale allocator across the reload)

**State:** built (Report written) · **Date:** 2026-11-05 · **Depends on:** S4-T5 (merged) · **Size:** M

**Owner:** the Xcode Mac orchestrator · **Orchestrator:** Claude Fable 5.1 · **Builder:** Claude Opus 5.5 (local) · **Verifier:** Claude Opus 5.5 (local, a different agent)

**Why.** Found by the S4-T5 verifier (5 Nov, its Verdict has the steps): with `searchd` built `ReleaseSmall` (also `ReleaseSafe` and `ReleaseFast`), `searchd serve <dir> --allow-write` answers an `apply_changes` request and then dies with signal 11 on the next `read_span`, no reply; `ReleaseSafe` reports "Segmentation fault at address 0x6" inside the allocator call at `zig/src/scope.zig:440` (`Loads.readSource`, the lazy source load of S4-T1) reached from `zig/src/service.zig:483` (`readSpan`). The Debug build does not crash, which is why `zig build test`, `python3 -m unittest discover -s tests` and the Linux CI (both Debug) have stayed green. Reproduced on `a1f96a2`, `2509003`, `596032c`, `b45b1c4` and `f45c06d`; `292cb568` hung on the scripted requests and was not judged, so where it began is not pinned (S4-T1's lazy open is the likely origin: `Loads` keeps an `allocator` that the reload after `apply_changes` replaces or frees). Two Python tests fail under a release `searchd`: `tests.test_folder_surfaces...test_rpc_apply_changes_only_with_allow_write_and_reads_see_it` and `tests.test_tool_schemas...test_apply_changes_report_and_pending`. The consumer app reaches the same code through the C ABI; whether its handle survives an `ss_apply_changes` on the same directory in a release library is untested.

### Ruling 2: the root cause and the fix

**What each pointer in `scope.Loads` refers to, before the fix.**

- `allocator`: the `std.mem.Allocator` that `snapshot_open.openScoped` was
  given, which is `arena.allocator()` of the opener's `ArenaAllocator`, a
  pointer to that `ArenaAllocator` struct (32 bytes: its child allocator and
  its two node lists). Its owner: in `searchd serve` (`zig/src/main.zig`
  `Served`), the first open used `served.arena` in place (stable), but the
  reload after `apply_changes` created a new `ArenaAllocator` with
  `served.allocator.create`, opened the new generation into it, copied it by
  value into `served.arena` and then **destroyed the created struct**
  (`defer served.allocator.destroy(next)`). From then on the new
  generation's `Loads.allocator.ptr` pointed at freed memory. In `searchd
  mcp` (`zig/src/mcp.zig` `run`) the reload opened into a block-local
  `next_arena` and copied it into `context_arena`: the pointer then named a
  stack slot out of scope. In the C ABI (`zig/src/abi.zig` `openImpl`) it is
  `handle.arena` inside the heap `Handle`, which stays put until `ss_close`:
  not affected (ruling 3c measures it). The CLI's one-shot commands keep
  their arena for the whole command: not affected.
- `source_file` (and the two filename section files): descriptors opened by
  `openScoped`, owned by the opened generation, released only by
  `Folder.close`. The serve and MCP reloads never called it, so each
  `apply_changes` leaked them. Measured (Debug `searchd serve
  --allow-write`, five `apply_changes` with a `read_span` after each,
  `lsof`): before the fix 6 `source-N.hybsrc` descriptors held
  (`source-1` … `source-6`), after it 1 (`source-6`); ReleaseSmall after the
  fix: 1.
- `source_buffer`, `documents`, `index`, `document_roots`,
  `filename_reserved`: slices into memory the arena's nodes hold. The nodes
  moved with the copied state, so these stayed valid; only the allocator
  pointer dangled.
- `io`: the process's `std.Io` (from `std.process.Init`), alive for the whole
  process: not affected.

**Why Debug hid it.** `searchd` gets `init.gpa`. In Debug that is Zig's
`DebugAllocator`, which never reuses a freed block's address and does not
overwrite freed bytes, so the destroyed `ArenaAllocator` kept a valid copy of
the moved arena's state; Zig 0.16's arena keeps each node's fill
(`end_index`) inside the node, so allocations through the stale copy landed
in the same nodes as the live one and nothing visible happened (only a load
large enough to need a new node would have linked that node into the stale
copy alone, a leak). On macOS `searchd` links libSystem (`otool -L`), so in
ReleaseSmall, ReleaseFast and ReleaseSafe `init.gpa` is
`std.heap.c_allocator` (`lib/std/start.zig`: the Debug allocator is used in
ReleaseSafe only without libc); `malloc` hands the freed 32-byte block to the
next allocation of that size, whose bytes overwrite the stale child
allocator, and the next lazy load calls a vtable at a small integer (0x6,
0x400): signal 11. (On Linux, where `searchd` does not link libc, the same
file gives ReleaseSmall and ReleaseFast `std.heap.smp_allocator`, which also
reuses freed blocks by size class, and ReleaseSafe the Debug allocator; read
from the source, not measured here: the new CI job runs ReleaseSmall there.)
The Python suites, `zig build test` and the Linux CI all ran Debug.

**The fix (the first of ruling 2's two forms).** `zig/src/rpc.zig` gains
`Generation`: one opened generation and its arena, the `ArenaAllocator`
allocated on the heap and never moved, so the generation's `Loads` stays
bound to its own arena for as long as the generation is served; `close`
releases the generation's files (`Folder.close`) and then its arena. `Served`
(the old `main.zig` struct, moved here so a Zig test reaches it) answers one
line through `handleLineWith` and, after a successful `apply_changes`,
`reload`s: the new generation is opened first (the old one stays served if
that fails), then the old one is closed, so no `Loads` of a closed generation
is reachable after the swap. `main.zig` (stdio and `--http`) uses
`rpc.Served`; `mcp.zig` uses `rpc.Generation` for its open and its reload
(the same defect, ruling 2's "any other pointer"). A full close-and-open of
the whole service was not chosen: the server's scope and permissions and the
request loop do not change across a write, and the old generation must stay
served until the new one opens. With the fix (Debug, ReleaseSmall and
ReleaseSafe, the ruling 1 driver): every probe answered, exit 0, through both
`serve` and `mcp`; the removed file `-32004`.
