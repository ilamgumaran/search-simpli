# S4-T6 · `searchd serve`: a read after `apply_changes` crashes a release build (a stale allocator across the reload)

**State:** ready · **Date:** 2026-11-05 · **Depends on:** S4-T5 (merged) · **Size:** M

**Owner:** the Xcode Mac orchestrator · **Orchestrator:** Claude Fable 5.1 · **Builder:** Claude Opus 5.5 (local) · **Verifier:** Claude Opus 5.5 (local, a different agent)

**Why.** Found by the S4-T5 verifier (5 Nov, its Verdict has the steps): with `searchd` built `ReleaseSmall` (also `ReleaseSafe` and `ReleaseFast`), `searchd serve <dir> --allow-write` answers an `apply_changes` request and then dies with signal 11 on the next `read_span`, no reply; `ReleaseSafe` reports "Segmentation fault at address 0x6" inside the allocator call at `zig/src/scope.zig:440` (`Loads.readSource`, the lazy source load of S4-T1) reached from `zig/src/service.zig:483` (`readSpan`). The Debug build does not crash, which is why `zig build test`, `python3 -m unittest discover -s tests` and the Linux CI (both Debug) have stayed green. Reproduced on `a1f96a2`, `2509003`, `596032c`, `b45b1c4` and `f45c06d`; `292cb568` hung on the scripted requests and was not judged, so where it began is not pinned (S4-T1's lazy open is the likely origin: `Loads` keeps an `allocator` that the reload after `apply_changes` replaces or frees). Two Python tests fail under a release `searchd`: `tests.test_folder_surfaces...test_rpc_apply_changes_only_with_allow_write_and_reads_see_it` and `tests.test_tool_schemas...test_apply_changes_report_and_pending`. The consumer app reaches the same code through the C ABI; whether its handle survives an `ss_apply_changes` on the same directory in a release library is untested.

## Rulings
1. **Reproduce first, in the Report.** The verifier's steps (`searchd apply` of `tests/test_folder_surfaces.fixture_request()` into a fresh directory; `searchd serve <dir> --allow-write`; `apply_changes` removing one file with `expect_generation: 1`; `roots`; `read_span` of the removed file's old lines) under `ReleaseSmall` and `ReleaseSafe` from the tree, with the `ReleaseSafe` stack. Then the same sequence with a read of a *kept* file, with `find`, with `search_knowledge`, and with `outline`: which calls crash and which do not, in a table.
2. **Root cause, named.** Say which allocator `Loads.allocator` (and any other pointer the lazy `Loads` keeps: `source_file`, `source_buffer`, `io`) refers to, who owns it, and what the reload after `apply_changes` (in `rpc.zig`/`service.zig`/`snapshot_open.zig`) does to it. The fix follows the ownership: the reloaded folder gets its own `Loads` bound to its own arena, and no `Loads` of a closed generation is reachable after the swap; or the reload is a full close-and-open of the service. State the choice and why the Debug build hid it (an arena that was not reused).
3. **Tests that would have caught it.** (a) A Zig test in `zig/src/` that opens a directory, applies one batch through the same code path `rpc.zig` uses on `apply_changes`, then calls `read_span`, `find`, `search_knowledge` and `outline` on the reloaded service; it runs under `zig build test -Doptimize=ReleaseSmall` as well as Debug (the verifier runs both, as S4-T4's did), and under the Debug build it also runs with the testing allocator's leak and use-after-free detection so a stale pointer is caught there too. (b) The Python suites under a release `searchd`: `tests/` gain a way to say which binary to use (they already honour `SEARCHD_BINARY`: say so), and `.github/workflows/checks.yml` gains a job (or a matrix row) that builds `ReleaseSmall` and runs `tests.test_folder_surfaces tests.test_tool_schemas tests.test_mcp` against it, failing on a skip. (c) The C ABI: `zig/tests/abi_test.c` gains a case that opens a handle, calls `ss_apply_changes` on the same directory, then `read_span`/`find` through the old handle (state the contract: the old handle keeps answering its generation, or refuses with a stated code; never a crash) and through a fresh handle; run in `ReleaseSmall` too (`zig build test-abi -Doptimize=ReleaseSmall` if the build file allows it; otherwise add it).
4. **Budgets unchanged.** The S4-T4 driver (`scripts/s4t4_budgets.py`) on the 10k corpus, before (`main`) and after, one run: `ss_open` within 0.3 ms, one changed file within 3 ms of before (off and on), NFR-13 arena test green. A fix that costs more than that is explained.
5. **Package, natives, docs.** No ABI or contract change expected (say so). `bindings/dart/search_simpli` 0.3.2 with a CHANGELOG entry (the crash, the fix, "a release library's handle after a write on the same directory" contract). Natives rebuilt on this Mac by the S4-T3 recipe (two builds, fresh caches, byte-identical; `check_native.sh`, `bundle_probe.sh`, `native/SOURCE-SHA256`), sizes in bytes. `PROJECT-STATE.md` entry; `docs/journey/03-next.md`: a row closed if one exists, a consumer row "pin bump to S4-T6" (the app must take this fix before its next phone install: the phones run release libraries); a CI note in `docs/process/ROLES.md` (the Python suites run in Debug and in ReleaseSmall from now on).
6. **Tests and checks.** `zig build test` in both modes, `zig build test-abi` (both modes if ruling 3c allows), `python3 -m unittest discover -s tests` under the Debug and the ReleaseSmall `searchd` (both OK, 0 skipped), the MCP/surface tests, the judgment pack, `scripts/check_no_home_paths.py`; the Linux CI green on the merge (the verifier checks).
7. **Diff scope.** `zig/src/` (`scope.zig`, `service.zig`, `rpc.zig`, `snapshot_open.zig`, `abi.zig` only if the ABI contract needs a code change, the new test file, `build.zig` for the release test steps), `zig/tests/abi_test.c`, `.github/workflows/checks.yml`, `tests/` (only if the binary selection needs it), `bindings/dart/search_simpli/` (version, CHANGELOG, natives, `SOURCE-SHA256`), `docs/` (`03-next.md`, `PROJECT-STATE.md`, `process/ROLES.md`, this file).
