# S6-T4 rework, item 2: the three `find` cells (timing `find words from`,
# Tamil `find words கீகசை`, Tamil `find prefix டூகன*`)

## What differs between a v2 and a v3 index after open (from the code)

- The find path's code is the same for both: `find.zig`, `scope.zig`,
  `postings.zig`'s lookups and position tables are unchanged by this branch
  apart from `postings.decodeList` (open only). No find code branches on the
  format: outside the codec, the format is read only by the manifest checks,
  `filename_field` (carry rule, load check, reservation) and
  `snapshot_open.decodeLoaded` (passes the arena for the term text).
- The arrays `find` reads are the same arrays with the same contents: the
  `TermEntry` table, the `Posting` table and the document lengths are decoded
  into the same open block, element for element as a v2 section's;
  `sorted_terms` is true for both (the v2 content section was already
  sorted), so `find` uses `postings.lookupExact` and the same prefix range.
- Positions and offsets (sections 4 and 5) are byte for byte v2's and are
  read in place in both; only their start within the loaded section moves
  (timing-10k positions at byte 9,000,613 in v2, 1,909,412 in v3: 37 and 36
  mod 64; Tamil 9,339,603 and 2,060,234: 19 and 10 mod 64). Position tables
  are built at the first `find` in both, from the same bytes.
- One thing is placed differently: a v3 section's term text is one block
  from the open arena (allocated during the decode), where a v2 term is a
  slice of the section's dictionary. Each lookup compares the same bytes;
  the block is contiguous where v2's terms are spread through the
  dictionary. Arena allocations made after it (the position tables at the
  first `find`) sit at other addresses.
- No slice became a copy on the find path, no indirection was added, no
  allocation was added per request.

## Why the sign follows the run number

run2.sh (builder) and vrun.sh (verifier) rotate the same five libraries by
one place per run, so `main` always runs immediately after the head: head
4th and main 5th in run 1, head 3rd and main 4th in run 2. For `find words
from` the 4th place was the fastest place and the 3rd the slowest, averaged
over the four runs (below), so head - main is negative in both run 1s and
positive in both run 2s whatever the head's own cost. The same libraries'
`find` cells taken together show nothing: the median of head - main over every
`find` cell of a corpus is within +-0.005 ms in all four runs (the same median
for main2 - main, the same bytes as main, runs from -0.0123 to +0.0036 ms).

## The format alone (an investigation, not a bar run)

`format_ab.sh`: this branch's library (the committed macOS native) on the v2
index (written by 98c4a2b) and on the v3 index (by this branch) of the same
corpus, alternated ABBA, four rounds per corpus, the gate before each process
(16 of 16 passed, 5-minute load 1.64-1.81, lock absent; no sleep in
`pmset -g log`; the Mac in dark wake, `UserIsActive` 0). Code placement is the
same for both, so what is left is the format. `find words from`: v3 faster in
all four rounds (median -0.009 ms). The Tamil pair: v3 slower in three rounds
of four (median +0.005 and +0.004 ms, about 0.15 %), the size main2 - main
reached on the same cells (+0.0145, +0.0166, +0.0275 ms), with no mechanism in
the code above. Every warm query cell: median v3 - v2 0.0000 ms (timing and
Tamil, 45 cells each).
